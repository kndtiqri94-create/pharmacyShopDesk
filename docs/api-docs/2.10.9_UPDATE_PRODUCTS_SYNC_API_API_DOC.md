## Conventions
- There is no HTTP layer in this repo. The "API" is an in-app service (`PosProductSyncService`) that talks to a server through an abstract boundary (`ProductSyncServer`). The boundary mirrors what one REST call per batch would be, so a real HTTP client can replace the simulated server with no change to the service or its results.
- Field names are camelCase. Money is whole cents (integers). Stock is a whole number.
- Audit fields (`isArchived`, `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `archivedAt`, `archivedBy`) are never part of the sync records or results.
- DEV ONLY: the server boundary has no authentication (A42). Production authentication is S-2.10.11 and is a release blocker. Outside mock mode, `ProductSyncServer` is bound to `notConfigured`, so it fails clearly instead of calling anything.
- No history, log, storage or console output is kept (A44, AC-14). The only state is the per-product stock baseline in `ProductSyncStateStore`.

All source paths are under `frontend-app/src/app/core/`.

## Operation 1: `PosProductSyncService.sync(onProgress?)`

- **Source:** `services/pos-product-sync.service.ts`
- **Purpose:** Run a whole-list two-way product sync in batches of 500 and report total products, batch count and the status of every batch.
- **AuthZ:** the live session user must have `canWrite(POS)` (Admin, Manager, Cashier, Pharmacist; FR-POS-12). Re-checked on every call inside `PosWriteGuard.run` (scope `pos-product-sync`). No caller-supplied user is trusted.
- **Tenant-scoped:** No (single shop app).
- **Idempotent:** Yes. Stock changes carry an operation id; running again never applies a change twice (see Idempotency).
- **Single flight:** a second call while one is running returns `busy`.

### Input
| Name | Type | Required | Description |
|---|---|---|---|
| onProgress | `(progress: ProductSyncProgress) => void` | N | Called after every batch (completed or failed). |

`ProductSyncProgress`
| Field | Type | Notes |
|---|---|---|
| completedBatches | number | Batches completed so far. |
| totalBatches | number | Batches in this run. |
| batch | `ProductSyncBatchResult` | The batch that just finished. |

### Result: `Promise<ProductSyncResult>`
`ProductSyncResult = ProductSyncSuccess | ProductSyncFailure | PosFailureResult`

`ProductSyncSuccess` (`ok: true`)
```json
{
  "ok": true,
  "totalProducts": 1200,
  "batchCount": 3,
  "batches": [
    { "batchNumber": 1, "productCount": 500, "status": "completed" },
    { "batchNumber": 2, "productCount": 500, "status": "completed" },
    { "batchNumber": 3, "productCount": 200, "status": "completed" }
  ],
  "message": "Synced 1200 products in 3 batches."
}
```
| Field | Type | Nullable | Notes |
|---|---|---|---|
| ok | `true` | N | |
| totalProducts | number | N | Products in the app list when the run started. Server-only products added during the run are not counted. |
| batchCount | number | N | `ceil(totalProducts / 500)`, minimum 1. |
| batches | `ProductSyncBatchResult[]` | N | One entry per batch, in order. |
| message | string | N | Fixed human-readable text. |

`ProductSyncBatchResult`
| Field | Type | Notes |
|---|---|---|
| batchNumber | number | 1-based. |
| productCount | number | Products in the batch (500, except the last). |
| status | `'completed' \| 'failed' \| 'not-run'` | `not-run` = skipped because an earlier batch failed. |

`ProductSyncFailure` (`ok: false`)
```json
{
  "ok": false,
  "reason": "batch-failed",
  "message": "Batch 2 could not be synced. Synced batches: 1. Failed batch: 2.",
  "totalProducts": 1200,
  "batchCount": 3,
  "batches": [
    { "batchNumber": 1, "productCount": 500, "status": "completed" },
    { "batchNumber": 2, "productCount": 500, "status": "failed" },
    { "batchNumber": 3, "productCount": 200, "status": "not-run" }
  ],
  "succeededBatches": [1],
  "failedBatch": 2
}
```
| Field | Type | Nullable | Notes |
|---|---|---|---|
| ok | `false` | N | |
| reason | `'empty' \| 'invalid' \| 'unreachable' \| 'batch-failed'` | N | |
| message | string | N | Fixed text; never contains product names, prices or raw server errors. |
| totalProducts | number | N | 0 for `empty` and `invalid`. |
| batchCount | number | N | 0 for `empty` and `invalid`. |
| batches | `ProductSyncBatchResult[]` | N | Empty for `empty` and `invalid`. |
| succeededBatches | number[] | N | Batch numbers already applied (they stay applied). |
| failedBatch | number | Y | Null for `empty` and `invalid`. |

`PosFailureResult` (from `pos-sale.service.ts`): `{ ok: false, reason: 'denied' | 'busy' | ..., message }`. The sync returns `denied` (no POS write access, not signed in) and `busy` (another sync running). Nothing changes in either case.

### Status values and error cases
| `reason` | When | Effect on data | Message |
|---|---|---|---|
| `denied` | No signed-in user, or user lacks `canWrite(POS)` (View-only, no access) | None. The server is never called. | `You do not have access to sync products at the till.` |
| `busy` | A sync is already running | None. | `The last action is still finishing. Try again in a moment.` |
| `empty` | App has no products | None. No batch runs. | `There are no products to sync.` |
| `invalid` | More than 50,000 products, or any product with a blank match key or a repeated match key | None. The server is never called. | `There are too many products to sync in one run.` or `Some products have a missing or repeated barcode and code. Fix them before syncing.` |
| `unreachable` | Server cannot be reached at some batch | Batches already completed stay applied; the failing batch changes nothing. If the first batch fails, nothing changes at all. | `The server could not be reached. No batches were synced and nothing was changed.` or `The server could not be reached. Synced batches: 1, 2. Failed batch: 3.` |
| `batch-failed` | Server error, malformed or oversized server reply, or the batch could not be saved locally (for example a server-only product whose code clashes with an existing SKU) | Same as above: that batch changes nothing, earlier batches stay applied. | `Batch 2 could not be synced. Synced batches: 1. Failed batch: 2.` |

A run stops at the first failing batch. There is no automatic retry and no skipping (A38).

### Batch rules
- Products are split in list order into batches of 500, minimum one batch for a non-empty list: 389 -> 1 batch; 500 -> 1; 501 -> 2 (500, 1); 1200 -> 3 (500, 500, 200).
- Batches run strictly one after another. Each batch is read fresh from the product list, sent, validated, then saved as one unit (`ProductDataService.saveAll`, then `save` for new products). A batch that fails validation or saving writes nothing.
- The app-side stock baseline and operation sequence advance only after a batch is confirmed and saved.

### Match key
The product is matched on `barcode` (trimmed). When the barcode is blank, the trimmed `sku` is used. A blank key, or the same key on two products, is refused up front (`invalid`) rather than guessed.

### Conflict rules
| Field | Winner |
|---|---|
| name, category, unit, priceCents, costCents, active | Server value replaces the app value. |
| stock | The app first sends its own stock change since the last sync (`stockDelta`). The app then takes the server's resulting stock. A sale made between sending the batch and saving the reply is preserved (reply stock plus the change made meanwhile) and is sent on the next run. |
| Product only in the app | Sent to the server, which creates it from the app values. |
| Product only on the server | Returned on the final batch and added to the app (`barcode` and `sku` both set to the match key, plain stock, no batches, not shown in the POS quick list). |

Fields not in the sync (generic name, form, manufacturer, reorder level, tax rate, shelf location, batches, and so on) are never changed on existing products.

### Idempotency
- Per product the app keeps `{ lastSyncedStock, opSeq }` (in memory, session only). `stockDelta = currentStock - lastSyncedStock`; with no baseline yet the delta is 0 (the first run never invents a change).
- `operationId = "{matchKey}:{opSeq}"`. The server applies a delta at most once per operation id and replays the stored resulting stock on a repeat.
- The app moves `lastSyncedStock` to the server's returned stock and increments `opSeq` only after the batch is saved. A failed or repeated batch therefore re-sends the same operation id and never applies twice.
- A repeated operation id that arrives with a different delta is refused by the server (`batch-failed`). This is a known limit (see Open items).

## Operation 2: `ProductSyncServer.syncBatch(request)`

- **Source:** `services/data/product-sync-server.ts` (abstract), `services/data/in-memory/in-memory-product-sync-server.ts` (simulated, mock mode only)
- **Purpose:** Apply one batch of up to 500 app records with stock deltas and return the server's values and resulting stock.
- **AuthZ:** None (DEV ONLY, A42). S-2.10.11 adds production authentication.
- **Real-server mapping:** one `POST` per batch with the request body below and the response body below. HTTP status mapping suggested for a real server: network failure -> `ServerUnreachableError`; any other non-2xx -> `BatchFailedError`.
- **Signature:** `syncBatch(request: ProductSyncBatchRequest): Observable<ProductSyncBatchResponse>`
- **Errors (typed):** `ServerUnreachableError` (cannot reach the server), `BatchFailedError` (server refused or could not process the batch). Any other error is treated as a failed batch and its text is never shown.

### Request: `ProductSyncBatchRequest`
```json
{
  "batchNumber": 3,
  "totalBatches": 3,
  "records": [
    {
      "matchKey": "4791000000011",
      "name": "Paracetamol 500mg",
      "category": "Analgesic",
      "unit": "tablet",
      "priceCents": 250,
      "costCents": 180,
      "stockOnHand": 3590,
      "active": true,
      "stockDelta": -10,
      "operationId": "4791000000011:1"
    }
  ],
  "appMatchKeys": ["4791000000011"]
}
```
| Field | Type | Required | Constraints | Notes |
|---|---|---|---|---|
| batchNumber | number | Y | 1..totalBatches | |
| totalBatches | number | Y | >= 1 | |
| records | `ProductSyncRecord[]` | Y | 0..500 items | Same order as the app list. |
| appMatchKeys | string[] or null | Y | null except on the final batch | On the final batch: every match key in the app, so the server can return the products the app lacks. |

`ProductSyncRecord`
| Field | Type | Constraints | Notes |
|---|---|---|---|
| matchKey | string | 1-64 chars, not blank | Barcode, else sku. |
| name | string | 1-200 chars, not blank | |
| category | string | 0-100 chars | |
| unit | string | 0-100 chars | |
| priceCents | number | integer, 0..100,000,000,000 | Selling price in cents. |
| costCents | number | integer, 0..100,000,000,000 | Cost price in cents. |
| stockOnHand | number | integer, 0..10,000,000 | App stock when the batch was built. |
| active | boolean | | |
| stockDelta | number | integer, may be negative | Stock change made only in the app since the last confirmed sync. |
| operationId | string | non-empty | `{matchKey}:{opSeq}`. |

### Response: `ProductSyncBatchResponse`
```json
{
  "batchNumber": 3,
  "records": [
    {
      "matchKey": "4791000000011",
      "name": "Paracetamol 500mg",
      "category": "Analgesic",
      "unit": "tablet",
      "priceCents": 250,
      "costCents": 180,
      "stockOnHand": 3590,
      "active": true
    }
  ],
  "serverOnlyRecords": []
}
```
| Field | Type | Nullable | Notes |
|---|---|---|---|
| batchNumber | number | N | Must equal the request's. |
| records | `ProductSyncServerRecord[]` | N | Exactly one per request record, in the same order, same `matchKey`. `stockOnHand` is the server's resulting stock after applying `stockDelta`. |
| serverOnlyRecords | `ProductSyncServerRecord[]` | N | Server products whose key is not in `appMatchKeys`. Empty unless the request was the final batch; at most 5,000. |

`ProductSyncServerRecord` has the same fields and constraints as `ProductSyncRecord` without `stockDelta` and `operationId`.

### Server behaviour the app depends on
1. For each record: if the product exists, apply `stockDelta` once per `operationId` (floor at 0), return the server's values and resulting stock. On a repeat of the same `operationId` with the same delta, return the stored resulting stock without applying again. On a repeat with a different delta, fail the batch.
2. If the product does not exist, create it from the record (stock = `stockOnHand`) and return it.
3. Reject a batch with more than 500 records or a malformed record (fail the batch, apply nothing).

### Response validation (done by the app before anything is written)
The reply is used only if all hold: `batchNumber` matches; `records` count equals the request and keys match in order; every record has bounded text, finite whole non-negative cents and stock within the limits above, and a boolean `active`; `serverOnlyRecords` is an array, only present on the final batch, at most 5,000, with valid records, keys not already in the app and no duplicates. Anything else fails the batch with `batch-failed` and nothing from that batch is applied.

## Test hooks (simulated server only)
`InMemoryProductSyncServer` offers `simulateUnreachable(boolean)`, `simulateFailingBatch(number | null)` (fails before applying), `simulateFailureAfterApply(number | null)` (applies, then fails), `getRecord(matchKey)` and `recordCount()`. All are off by default and exist only on the in-memory class, which is bound in mock mode only.

## Replacing the simulated server
Implement `ProductSyncServer` with a real client, bind it in `data-providers.ts` for the non-mock case, add authentication (S-2.10.11), and map transport errors to `ServerUnreachableError` and `BatchFailedError`. The service and its results do not change.

## Open items
- OQ41-1: the real server is not identified. This contract is the proposed shape.
- No authentication (A42, release blocker S-2.10.11). No audit log (A44, accepted).
- Baselines are session-only (a page refresh forgets which stock changes were already sent; with no baseline the next run sends delta 0). Accepted with all other in-memory data.
- If a batch was applied by the server but the app did not confirm it, and the same product's stock then changes again before the next run, the server refuses the repeated operation id with a different delta and that batch keeps failing. A real server and a durable baseline (a later story) should resolve this.

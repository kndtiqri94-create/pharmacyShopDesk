## Conventions
- Base path `/api/v1`. All bodies JSON, camelCase, field names and enums identical to the frontend models in `frontend-app/src/app/core/models`. Money is whole cents (integers); quantities are whole numbers; dates are `YYYY-MM-DD`; timestamps are ISO 8601.
- **Auth (stop-gap, F-3.5 replaces it):** every `/api/v1` route needs `Authorization: Bearer <API_AUTH_TOKEN>`. `/health` and `/health/ready` are anonymous. In production the API answers over HTTPS only (`403 https_required` otherwise). There is no per-role enforcement yet.
- Audit fields (`isArchived`, `createdAt` of the row, `createdBy`, `updatedAt`, `updatedBy`, `archivedAt`, `archivedBy`) are never returned. Fields named `createdAt` inside a record (for example `Sale.createdAt`) are business fields of the frontend model and are kept.
- Unknown fields are dropped on write for every collection except `employees` (extra fields kept). `password` fields are never accepted on users.
- Errors always: `{ "error": { "code": "...", "message": "...", "details": [ { "path": "lines.0.quantity", "message": "..." } ] } }`.
- Lists: `GET /{collection}?page=1&pageSize=50` (`pageSize` 1..500) return `{ "items": [...], "page", "pageSize", "total" }`. Date-keyed collections also accept `date=YYYY-MM-DD` or `dateFrom` / `dateTo`. Items are in creation order.
- Write semantics (all collections): `POST /{c}` creates or idempotently re-posts the record whose id is in the body; `PUT /{c}/:id` does the same and requires the path id to equal the body id. `201` = created, `200` = updated or unchanged (`Idempotent-Replay: true` header when nothing changed), `204` for delete.
- Collections marked **posted** are immutable: the same content again is `200` unchanged; different content under the same id is `409 immutable_record`; delete is `409 immutable_record`.
- Day records (`day-openings`, `drawer-sessions`, `counter-reports`, `reload-floats`) use `date` as the id; `opening-dues` uses `customerId`.
- Rate limit 600 requests/minute per client (`429 rate_limited`); body limit 2 MB (`413 payload_too_large`); malformed JSON `400 bad_request`; unknown route `404 not_found`; unexpected failure `500 internal_error` (no detail).

### Common error codes
| Status | `error.code` | When |
|---|---|---|
| 400 | `validation_error` | Body, query or path failed validation (details list each field) |
| 400 | `bad_request` | Unreadable request (malformed JSON) |
| 401 | `unauthenticated` | Missing or wrong bearer token (`WWW-Authenticate: Bearer`) |
| 403 | `https_required` | Plain HTTP while HTTPS is required |
| 404 | `not_found` | Unknown route or record |
| 409 | `duplicate_sku`, `duplicate_bank_account`, `duplicate_username`, `duplicate_employee_code`, `duplicate_invoice_no`, `duplicate_number`, `duplicate_leave_type`, `duplicate_entitlement`, `duplicate_attendance`, `duplicate_payroll_input`, `duplicate_payroll_payment` | A unique natural key belongs to another record (case and surrounding spaces ignored) |
| 409 | `immutable_record` | Posted record changed or deleted |
| 413 | `payload_too_large` | Body above 2 MB |
| 422 | `batch_failed` | Update Products batch repeated an operation id with a different stock change |
| 429 | `rate_limited` | Too many requests |
| 500 | `internal_error` | Unexpected failure |
| 503 | (health only) | `/health/ready` when the store is unreachable: `{ "status": "unavailable" }` |

## Products (stock-aware): `/api/v1/products`
Product shape = frontend `Product` (id, name, genericName, category, form, unit, sku, barcode, manufacturer, costCents, priceCents, reorderLevel, trackBatches, stockOnHand, prescriptionRequired, active, taxRatePercent, shelfLocation, showInPosQuickList, batches[]); `Batch` = `{ id, batchNo, expiryDate ('' or date), quantity, costCents }`.

- Limits (mirror the UI): name 1-120, unit 1-30, sku 1-40 (unique, case-insensitive), barcode/shelfLocation <= 40, genericName/manufacturer <= 120, category <= 60, costCents/priceCents integers 0..1,000,000,000, reorderLevel 0..10,000,000, taxRatePercent 0..100, batches <= 500.
- **Responses always show CURRENT stock:** `stockOnHand` and each `batches[].quantity` = stored base + sum of movements; batches earliest expiry first (no-expiry last).
- `GET /products` (paged), `GET /products/:id`.
- `POST /products` / `PUT /products/:id`: the body carries the stock figures the screen shows. Blank/absent id on POST gets a generated id. Stock figures must be >= 0 here (`400` otherwise). The difference to the server's current figures is recorded as `ADJUSTMENT` movements (a new product's opening stock is one movement); saving the same figures again records nothing. `409 duplicate_sku` on a SKU clash.
- Response: the product with current stock.

```json
{ "id": "prod-1", "name": "Paracetamol 500mg", "sku": "PAR-500", "stockOnHand": 95, "trackBatches": false, "batches": [], "...": "..." }
```

### `POST /products/sync-batch` — Update Products batch (S-2.10.9 contract, OQ48)
Request and response are exactly those of `docs/api-docs/2.10.9_UPDATE_PRODUCTS_SYNC_API_API_DOC.md` (Operation 2). Server behaviour:
- Match key = trimmed barcode, else trimmed sku. For an existing product: server values win (name, category, unit, prices, active are NOT changed by the app record); `stockDelta` is applied once per `operationId` as one `ADJUSTMENT` movement (movement id `opsync:{operationId}`), floored so stock never goes below zero; the response `stockOnHand` is the server's resulting current stock.
- Repeat of an `operationId` with the same delta changes nothing and returns current stock; with a different delta: `422 batch_failed`.
- A product not on the server is created from the record (sku = barcode = matchKey, stock = `stockOnHand`).
- On the final batch (`batchNumber == totalBatches`) with `appMatchKeys` set, `serverOnlyRecords` lists up to 5,000 server products not in `appMatchKeys`.
- Limits: `records` <= 500; `priceCents`/`costCents` integers 0..100,000,000,000; `stockOnHand` 0..10,000,000; `stockDelta` +/-10,000,000; `batchNumber` <= `totalBatches`. Invalid: `400 validation_error`.

Operations on each: `GET /{route}`, `GET /{route}/:id` (`404` if absent), `POST /{route}`, `PUT /{route}/:id`, `DELETE /{route}/:id` (`204`; `404` absent; `409 immutable_record` for posted). Response body of GET/POST/PUT is the record itself.

Field rules mirror the frontend models and UI validation. Highlights:
- **bank-accounts:** bank 2-60, holderName 2-60, accountNo 6-20, branch <= 60, openingBalanceCents integer.
- **users:** role in ADMIN, MANAGER, PHARMACIST, CASHIER; status ACTIVE or DISABLED; no password field exists.
- **sales:** `lines` 1..1000 with quantity >= 1; `payments[].method` CASH, CARD, ONLINE, CREDIT; `cardLast4` exactly 4 digits when present; business rules: sum of line `totalCents` = `subTotalCents`; `discountCents` <= `subTotalCents`; `totalCents` = `subTotalCents - discountCents` (`400` otherwise). Stock is never checked.
- **sale-returns:** sum of line `totalCents` = `totalCents`; settlement CASH_REFUND or CUSTOMER_CREDIT.
- **due-payments:** `amountCents` > 0.
- **leave-requests:** `toDate` not before `fromDate`; status PENDING, APPROVED, REJECTED, CANCELLED.
- **salary-advances:** `amountCents` > 0. **payroll-inputs / payroll-payments:** `month` `YYYY-MM`.
- **employees:** required id, code (1-40), name (1-160), status, salaryType MONTHLY or DAILY, basicSalaryCents, allowances[]; all other frontend fields are kept as sent.

### Posting with stock movements: `POST|PUT` on `grns`, `sales`, `sale-returns`, `product-adjustments`
The body is the record plus an optional top-level `movements` array (max 500). Record and movements are stored in ONE transaction. The response is the record plus `movements: { "recorded": n, "duplicates": n }`.

`Movement`:
| Field | Type | Constraints |
|---|---|---|
| id | string | 1-64, device-generated; recorded once |
| productId | string | 1-64 |
| batchId | string | '' = product level |
| type | `SALE`, `RETURN`, `GRN`, `ADJUSTMENT` | |
| qtyDelta | integer | non-zero, +/-10,000,000 (negative reduces stock) |
| refId | string or null | e.g. the sale id |
| userId | string or null | |
| deviceCode | string | 2-4 capital letters or digits |
| createdAt | string | device time |
| seq | number, optional | accepted and ignored; the server assigns its own order |

```http
POST /api/v1/sales
{ "id": "sale-1", "invoiceNo": "AB1-0001", "...": "...", "movements": [ { "id": "mov-1", "productId": "prod-1", "batchId": "", "type": "SALE", "qtyDelta": -2, "refId": "sale-1", "userId": "usr-1", "deviceCode": "AB1", "createdAt": "2026-11-23T09:00:00.000Z" } ] }
```
```http
201 Created   (200 + Idempotent-Replay: true when sent again)
{ "id": "sale-1", "...": "...", "movements": { "recorded": 1, "duplicates": 0 } }
```
A sale is never rejected for stock reasons (OQ47 proposal). Sending `movements` to an endpoint that does not accept them is `400`.

## Stock ledger
- `POST /stock-movements` body `{ "movements": [Movement x 1..500] }` -> `{ "recorded": n, "duplicates": n, "results": [ { "id", "status": "accepted" | "duplicate" } ] }`. A movement id already recorded is `duplicate` and not applied.
- `GET /stock-movements?productId=&refId=&sinceSeq=0&limit=200` -> `{ "items": [ Movement + seq ], "nextCursor": n }` ordered by `seq`.
- `GET /stock/products/:id` -> `{ "productId", "stockOnHand", "batches": [ { "batchId", "quantity" } ] }` (current stock).
- `GET /stock/negative` -> `{ "items": [ { "productId", "productName", "batchId", "quantity" } ] }` stock below zero, for review.

## Derived reads
- `GET /customers/dues` -> `{ "items": [ { "customerId", "name", "owedCents" } ] }`: opening due + credit sales - due payments - CUSTOMER_CREDIT returns; only amounts above zero.
- `GET /cash-book?date=YYYY-MM-DD` -> `{ "date", "openingCents", "entries": [CashEntry], "rows": [ { "entry", "balanceCents" } ], "cashInCents", "cashOutCents", "expectedCents" }`. Cash kept from a sale = CASH payments - `changeCents`; refunds are CASH_REFUND returns; due payments with method CASH.

## Sync
### `POST /sync/push`
```json
{
  "deviceCode": "AB1",
  "changes": [
    { "changeId": "c1", "entity": "sales", "op": "put", "id": "sale-1", "data": { "...": "record" }, "baseSeq": null },
    { "changeId": "c2", "entity": "stockMovements", "op": "put", "id": "mov-1", "data": { "...": "Movement" } },
    { "changeId": "c3", "entity": "suppliers", "op": "delete", "id": "sup-1", "baseSeq": 41 }
  ]
}
```
| Field | Type | Notes |
|---|---|---|
| deviceCode | string | 2-4 capital letters or digits |
| changes | array | 0..500, processed in order, each in its own transaction |
| changeId | string | unique id per change (device-generated); outcome remembered |
| entity | string | a frontend table name from the registry (`products`, `sales`, `grns`, ... , `documents` for settings with ids `app-settings`, `payroll-settings`, `role-matrix`) or `stockMovements` |
| op | `put` or `delete` | movements and posted records cannot be deleted |
| id | string | record id; must equal the id inside `data` |
| data | object | the record exactly as the frontend stores it (for `products`: the device's stored row, i.e. BASE quantities) |
| baseSeq | integer or null | the server `seq` of this record the device last saw; null/absent if never synced |

Response `200`: `{ "results": [ { "changeId", "status": "accepted" | "duplicate" | "rejected", "reason"?, "message"? } ] }` in request order.

| status | reason | Meaning |
|---|---|---|
| accepted | (none) | Applied |
| accepted | `unique_key_clash_flagged` | Posted record kept but its number clashes with another record; review it |
| duplicate | `already_processed` / a remembered reason | This `changeId` was handled before; nothing changed |
| duplicate | `movement_already_recorded` | Movement id already in the ledger |
| duplicate | `unchanged` | Server already holds identical content |
| duplicate | `server_wins` | Server version is newer (or posted record differs); device should adopt the pulled version |
| duplicate | `already_deleted` | Record already gone |
| rejected | `validation_error` | Failed schema or business rule (message names the problem) |
| rejected | `duplicate_sku`, `duplicate_bank_account`, ... | Master-data unique key held by another record |
| rejected | `unknown_entity`, `invalid_change`, `id_mismatch`, `unknown_document`, `document_cannot_be_deleted`, `movement_cannot_be_deleted`, `immutable_record` | Malformed or not allowed |

The whole batch can be resent: every outcome is remembered per `changeId`, so nothing is applied twice. A bad envelope (`deviceCode`, over 500 changes) is `400`. A server failure mid-batch is `500`; changes already handled stay recorded and the resend reports them as duplicates.
Product rows: master fields are replaced (when the device is not out of date), but existing server stock figures are never overwritten; only a new product or new batch takes the device's base. Stock moves only through movements. Settled stock rule: two devices selling the same item both reduce stock.

### `GET /sync/pull?cursor=0&limit=200`
`limit` 1..500, `cursor` >= 0. Response:
```json
{
  "changes": [
    { "entity": "suppliers", "id": "sup-1", "op": "put", "seq": 12, "data": { "...": "record" } },
    { "entity": "suppliers", "id": "sup-2", "op": "delete", "seq": 13, "data": null },
    { "entity": "stockMovements", "id": "mov-1", "op": "put", "seq": 14, "data": { "...": "Movement incl. seq" } }
  ],
  "nextCursor": 14,
  "hasMore": false
}
```
Changes are in ascending `seq`; send `nextCursor` as the next `cursor`; repeat while `hasMore`. Deletions arrive as `op: "delete"` with `data: null`. Product `data` is the stored BASE row; stock arrives as movements. Internal bookkeeping records are never sent.

## 1. Story
As a **shop owner or manager running ShopDesk on more than one device**, I want **one central place that safely stores all of the shop's data and exchanges changes with every till and back-office device** so that **every device sees the same products, stock, sales and staff records, nothing is lost or counted twice when a device reconnects, and stock stays correct even when two tills sell the same item at the same time**.

## 2. Business Context
Phase 2 of ShopDesk (PRD 5.10, 7.2) keeps data on each device first (F-3.2) and now needs the shop's central record. The central record must hold every module's data, check every change before accepting it, keep stock as a history of movements so it can be audited, and let devices send their pending work in batches and collect other devices' work. Screens do not change. Real sign-in and permissions on the server (F-3.5), the device-side sending logic (F-3.4) and hosting (F-3.6) come later.

## 3. Scope
### 3.1 In Scope
- **S-3.3.1 Foundation.** The central service starts from configuration kept outside the code, reports whether it is alive and ready, answers every problem in one clear, consistent way, checks every request before acting on it, talks only over secure connections in production, and has automated checks that run on every change.
- **S-3.3.2 Master data.** Products and their batches, suppliers, customers, bank accounts, users and roles, and settings are stored centrally with the same checks as the screens (for example a repeated product code or a repeated bank plus account number is refused).
- **S-3.3.3 Stock history and stock-in.** Goods received notes, purchase orders and stock adjustments are stored centrally. Stock is worked out from an ordered history of stock movements. A movement that carries an identity already seen is recorded only once.
- **S-3.3.4 Point-of-sale records.** Sales, returns, quotations, held bills, the cash book, counter close and customer dues are stored centrally. Sending the same sale again never creates a second sale or a second stock reduction. A sale is never refused because of stock; stock that goes below zero is flagged for review (proposal OQ47, still awaiting confirmation).
- **S-3.3.5 Staff records.** Employees, attendance, leave, salary advances, nopay entries and payroll inputs and payments are stored centrally with the same checks as the screens.
- **S-3.3.6 Exchange with devices.** A device can send a batch of pending changes and is told, for each change, whether it was accepted, was already known, or was refused with a reason. The whole batch can be sent again safely. A device can collect everything that changed since it last asked. When two devices change the same record, the central version wins, except stock, which is always combined from movements. The existing Update Products refresh keeps working against the central service (OQ48 reconciliation).

### 3.2 Out of Scope (explicit)
- Real sign-in, passwords, sessions and the Full / View / No access rules enforced per role on the server (F-3.5). Until then a single shared secret protects the service.
- The device-side queue and automatic sending, the sync indicator and the "Needs attention" list (F-3.4).
- Hosting, domain, backups and monitoring (F-3.6).
- Changes to any screen, rule or role.
- Final decisions on open questions OQ42 (stack), OQ47 (what may be refused) and OQ48 (fate of Update Products), which remain open with the Product Owner; this delivery records the working assumptions.

## 4. Acceptance Criteria (Given/When/Then)

- **AC-1** — Given the service is configured, when it starts without its required settings or with an insecure combination in production, then it refuses to start and says what is wrong without revealing any secret.
- **AC-2** — Given the service is running, when anyone asks whether it is alive or ready, then it answers without needing to sign in and without revealing internal detail; when the data store is unreachable it says it is not ready.
- **AC-3** — Given any request that is invalid, unauthorised, too large, unknown or fails unexpectedly, when the service answers, then the answer has the same clear shape every time and never shows internal details.
- **AC-4** — Given production settings, when a request arrives over an insecure connection, then it is refused.
- **AC-5** — Given a product with a code already used by another product (ignoring capital letters and surrounding spaces), when it is saved, then it is refused with a clear reason; the same holds for a repeated bank plus account number, user name, employee code and the other repeated-number rules the screens enforce.
- **AC-6** — Given values outside what the screens allow (empty name, negative price, impossible date, unknown role), when a record is saved, then it is refused and each faulty field is named.
- **AC-7** — Given stock movements for a product, when stock is read, then it equals the product's recorded starting quantity plus all its movements, per batch where batches are tracked, and batches list earliest expiry first.
- **AC-8** — Given a stock movement with an identity already recorded, when it is sent again (alone, inside a goods received note, a sale, a return or a batch of pending changes), then it is not applied a second time and the sender is told it was already known.
- **AC-9** — Given a goods received note, when it is saved with its movements, then stock rises once; sent again, stock does not rise again.
- **AC-10** — Given a sale, when it is saved (once or many times), then exactly one sale exists and stock fell once; a sale whose arithmetic does not add up is refused; a posted sale cannot be changed or deleted.
- **AC-11** — Given a sale that takes stock below zero, when it is saved, then it is accepted and the product appears in a list of negative stock for review.
- **AC-12** — Given sales, returns, due payments and the day's opening balance, when the cash book for a day and the customers' dues are requested, then they equal what the till screens show (cash kept from sales plus due payments, less cash refunds; dues are credit sales plus opening dues less payments and credit returns, never below zero).
- **AC-13** — Given leave, salary advance, nopay and payroll records, when saved, then the same checks as the screens apply (leave end date not before start, advance above zero, one payroll input and payment per employee and month).
- **AC-14** — Given a batch of pending changes, when it is sent, then each change is reported as accepted, already known or refused with a reason; sending the identical batch again changes nothing.
- **AC-15** — Given two devices that each sell the same item, when both send their sales and movements, then both sales exist and stock fell by both quantities.
- **AC-16** — Given two devices that changed the same non-stock record, when the second sends from an out-of-date copy, then the central version stands and the sender is told so; a device that had the latest copy is accepted.
- **AC-17** — Given a product row sent by a device, when it is applied, then names, prices and other details are updated but the central stock is never replaced by the device's total.
- **AC-18** — Given a device that last collected changes up to a point, when it asks again, then it receives every later change (including deletions and stock movements) in order, in pages, and never misses or repeats one.
- **AC-19** — Given a posted sale whose invoice number clashes with another sale from a different device, when it is sent, then it is kept (a real sale is never lost) and flagged for review.
- **AC-20** — Given the Update Products refresh with its existing batch shape, when a batch is sent, then the app's stock change is applied once per operation, server values win, products only on the app are added, products only on the server are returned on the last batch, and stock does not drop below zero.

## 5. Security & Privacy Notes (business-level only)
- The service holds sales, customer dues, staff pay and personal details; they must be readable and changeable only by authorised shop systems.
- Credentials and customer or pay data must never appear in logs or error messages.
- Passwords are never stored by this workstream.
- Per-role access (who may see pay or change prices) is enforced in F-3.5; until then the whole service is protected by a single shared secret that is not suitable for production go-live on its own.

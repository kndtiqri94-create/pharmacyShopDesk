## 1. Story
As a **candidate**, I want to **view the advertised role and submit a complete application (name, email, CV, optional cover note) with clear feedback at every step** so that **I know my application was received, can fix mistakes before submitting, and can retry if something goes wrong, without losing what I've already entered**.

## 2. Business Context
This is the candidate-facing entry point for HireFlow's first demo slice: a single advertised role and its application form. The business goal is to demonstrate a complete, trustworthy application experience — validation, submission, success confirmation, and failure/retry — end to end, so a candidate never wonders whether their application went through or loses their input due to a reload or a failed save (PRD Goals G1–G4).

## 3. Scope
### 3.1 In Scope
- Presenting the advertised role and its application form with the following applicant inputs: full name, email address, CV, and an optional cover note with a visible remaining-character count (up to 500 characters).
- Validating that full name, email, and CV are provided, and that the email is in a valid email format, before allowing submission.
- Showing the candidate clear, specific error feedback (per field, plus an overall summary) when they attempt to submit with missing or invalid information, and keeping submission blocked until everything is corrected.
- Showing the candidate a clear "in progress" indication while their application is being saved, and disabling repeat submission attempts during that time.
- Confirming successful submission with a clear "Application sent" confirmation, and letting the candidate start a new, blank application from that confirmation.
- Showing a clear, visible message if saving the application fails, with a way for the candidate to retry without re-entering their information.
- Ensuring that once an application has been successfully submitted, reloading the page shows the candidate their confirmed submission rather than a blank form.

### 3.2 Out of Scope (explicit)
- Candidate accounts, login, or authentication (PRD NG1).
- Any multi-step/multi-page application flow — this is a single-page application experience (PRD NG2).
- Any email or other notification sent to the candidate or a hiring manager as a result of submission (PRD NG3).
- Browsing, searching, or listing other open roles, or navigating away to a roles list (PRD NG4).
- Any interaction between this experience and a backend service — this application's data is not sent to or retrieved from any server-side system in this phase (PRD NG5, PRD Constraints).
- A mobile-specific variant of this experience (tracked separately, not part of this story).

## 4. Acceptance Criteria (Given/When/Then)

- **AC-1** — Given a candidate opens the advertised role page, when the page loads with no prior submission on that device, then the candidate sees the role information and an empty application form with fields for full name, email, CV, and an optional cover note showing a remaining-character count starting at 500.
- **AC-2** — Given the candidate has not yet attempted to submit, when they are still filling in the form, then no validation errors are shown for fields they haven't finished with yet.
- **AC-3** — Given the candidate attempts to submit with one or more required fields (full name, email, CV) missing, when they trigger the submit action, then each affected field shows a specific inline message, an overall summary message appears, and the submission does not proceed.
- **AC-4** — Given the candidate has entered an email address that is not in a valid email format, when they attempt to submit, then an inline message specific to the email field is shown, and the submission does not proceed until a valid email format is entered.
- **AC-5** — Given the candidate corrects a previously invalid or missing field, when the correction is made, then the error message(s) for that field clear without requiring another failed submit attempt.
- **AC-6** — Given all required information is present and valid, when the candidate submits, then the candidate is shown a clear "in progress" indication and cannot trigger another submission until that attempt finishes.
- **AC-7** — Given a submission attempt completes successfully, when the candidate is shown the outcome, then they see a clear "Application sent" confirmation and are offered an action to start a new, blank application.
- **AC-8** — Given the candidate uses the "start a new application" action from the confirmation, when they choose it, then they are returned to an empty form ready for a new submission.
- **AC-9** — Given a submission attempt fails to save, when the candidate is shown the outcome, then they see a clear, visible explanation that the submission failed (not a silent failure) and are offered a retry action.
- **AC-10** — Given a failed submission, when the candidate chooses to retry, then the retry attempts to save the same information they already entered, without requiring them to re-enter any of it.
- **AC-11** — Given a candidate has previously completed a successful submission on this device, when they reload or revisit the page, then they see their confirmed "Application sent" state rather than a blank form.
- **AC-12** — Given the optional cover note field, when the candidate types into it, then the remaining-character count updates live and the candidate cannot enter more than 500 characters.

> **Assumption on demonstrating a submit failure (relates to PRD Open Question OQ1):** Because this is a demo experience with no live backend and no realistic way to force a genuine storage failure on demand, this story assumes the demo build includes a built-in, clearly-labelled way to bring about a failed-submission outcome for demonstration purposes (for example, an occasional or intentionally triggerable "failed to save, please retry" outcome), so that AC-9 and AC-10 can be exercised and shown. This is a reasonable low-risk default chosen so the workstream is not blocked, but it is **not yet confirmed by the stakeholder** — PRD OQ1 remains open and should be confirmed/adjusted before this behaviour is treated as final. If the stakeholder later specifies a different trigger for the failure state, AC-9/AC-10 remain valid (they describe the *outcome* the candidate sees, not the trigger); only the underlying trigger mechanism would need to change.

## 5. Security & Privacy Notes (business-level only)
- Sensitive data involved: the applicant's personal contact details (full name, email address) and their submitted CV and cover note content. The CV itself is only referenced by its name and size for this demo, not by its full content.
- Only the candidate submitting the application, on their own device, should be able to see their own in-progress or submitted application in this experience. There is no shared or administrative view of applications in this story.

## 6. Dependencies
- Upstream stories / workstreams: None — this is the first story for Workstream E-1/F-1.1.
- External systems: None. This experience works entirely on the candidate's own device and does not depend on any other system or service (PRD Constraints, NG5).
- Related, non-blocking workstream: F-1.2 (standalone backend persistence demo) is a separate, non-integrated artifact and is not a dependency of this story.

### 9.4 Completion Notes
- **New Angular scaffold:** No `frontend-app` existed in this repo; scaffolded fresh with Angular CLI 20.3.34 (latest stable compatible with the installed Node 20.19.0) per Plan §2/R2 — standalone components, routing, SCSS, strict mode, no SSR. Coding-standard patterns (component file separation, service shape, `local-storage.service.ts`-style wrapper, `sample-form`-style component) were taken from `docs/development-standards/template/frontend-app/`; its Angular Material/MSAL/Bootstrap dependencies and versions were intentionally NOT carried over (no auth in this screen; design tokens come from `docs/design/`, not Material theming).
- **Test runner:** The scaffold's default unit-test runner is Karma/Jasmine (Angular CLI 20's stock `ng test`), not Vitest as FRONTEND_STANDARDS' Technology Stack section names for the existing `frontend-app`/`mobile-pwa` apps. Jasmine's `describe`/`it`/`expect` API is what the spec files use and is compatible with the standards' testing rules (Sonar S2699 assertions, `toHaveLength`/`toBeNull` matchers, etc.); switching the builder to Vitest was judged out of scope for this frontend-only demo slice and can be revisited if the team standardizes on Vitest for this app. Flagging for Team Lead awareness rather than blocking.
- **OQ1 demo failure-injection mechanism (assumption, not yet stakeholder-confirmed):** Implemented in `job-application-submit.service.ts` as a reserved trigger email address (`fail@demo.hireflow.test`, exported as `DEMO_FORCED_FAILURE_EMAIL`). Submitting with that exact email fails the *first* attempt (demonstrating AC-9) and succeeds on the very next attempt with the same data, i.e. clicking the form's "Retry" button (demonstrating AC-10) — all without touching `localStorage` on the simulated-failure branch. The mechanism is fully isolated behind `JobApplicationSubmitService.submit()`, so swapping it later (e.g. for a random-failure rate, a query param, or removing it once OQ1 is resolved) requires no changes to the form, page, or validators. No visible UI affordance was added (keeps the design pixel-for-pixel matching `docs/design/Job Application Page.dc.html`); QA/demo operators trigger it by using the reserved email.
- **"Start again" clears the stored submission:** Not explicitly specified by AC-8, but implemented as `startAgain()` calling `storageService.clear()` before returning to the blank form — otherwise a reload immediately after "Start again" (before a new submission) would still show the old "Application sent" confirmation (AC-11), which would be a confusing result for a candidate who explicitly asked to start again. Reasonable low-risk default consistent with AC-8's intent; flagged here for Product Owner/Team Lead awareness rather than treated as a blocking ambiguity.
- Retry re-uses the same "Send application"/"Retry" submit button (no separate retry control) — since the form component keeps its own reactive-form state across `submitting`/`error` states, clicking it again naturally resubmits the already-entered data (AC-10) without any extra plumbing.
- All 12 acceptance criteria (AC-1 through AC-12) and the Plan §6 Threat Model mitigations (Tampering / Information Disclosure / DoS) are implemented and evidenced in `docs/checklists/1.1_JOB_APPLICATION_FORM_STORY_DOD.md`.

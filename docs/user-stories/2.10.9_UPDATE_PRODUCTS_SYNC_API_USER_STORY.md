# User Story 2.10.9 — Update Products Sync API

- **Workstream:** 2 — Dashboard and Products (sub-task S-2.10.9, POS extras)
- **Traces to PRD:** FR-POS-25, FR-POS-13, FR-POS-12 (role access)
- **Status:** Ready
- **Author:** Thilina (BA)
- **Created:** 2026-11-13

## 1. Story
As a **shop user with POS access (Admin, Manager, Cashier or Pharmacist)**, I want **the product list to be synchronised with the server in batches, with the total number of products, the number of batches and the status of each batch reported back** so that **my product details and stock levels match the server without losing any sale I made since the last sync, and I can see exactly how far the sync has got or where it stopped**.

## 2. Business Context
The shop keeps its product list in the app, while a server holds the master copy. Staff need a safe, repeatable way to bring the two in line (FR-POS-25). This story delivers the capability that does the synchronising and reports progress; the screens that start and show it are a separate story (S-2.10.10).

## 3. Scope
### 3.1 In Scope
- Synchronising the whole product list with the server, in both directions (the app sends and receives).
- Splitting the work into batches of 500 products, minimum one batch (A41), and reporting total products, batch count and per-batch status.
- Product details synchronised (A40): product code/barcode (used to match products), name, category, unit, selling price, cost price, stock quantity, active/inactive status.
- Conflict rule: for every detail except stock, the server value wins. For stock, quantity changes made only in the app since the last sync (for example POS sales) are sent to the server first, then the server's resulting stock is brought back.
- Products that exist only in the app are sent to the server; products that exist only on the server are added to the app.
- Stopping the run with a clear message when a batch fails or the server cannot be reached (A38); batches already applied stay applied and the message names which batches succeeded and which failed (A43).
- A clear message when there are no products to sync.
- Running the sync again is always safe: it continues correctly and never applies the same stock change twice (A43).
- Access follows the POS role rules (FR-POS-12).
- Automated tests covering the criteria below.

### 3.2 Out of Scope (explicit)
- Any screen, button, confirmation dialog or progress display (S-2.10.10).
- Production-grade authentication (S-2.10.11). For now the sync runs without authentication, for development only (A42); this must not be released to production.
- The per-product quick edit (S-2.10.6), which is unchanged.
- Any kept history, log or audit trail of sync results (A44).
- Automatic retry or skipping of a failed batch (A38).
- Connecting to a real server: its identity is still open (OQ41-1) and is not a blocker for this story.

### 3.3 Assumptions (confirmed or agreed for this story)
- **No real server exists yet.** The sync works against a simulated server holding sample product data. It is built behind a clear boundary and its behaviour is documented in the API documentation so a real server can replace the simulation later without changing what the app expects.
- **Delivery form.** The repository is currently a standalone, front-end-only app (no separate backend). For this story the "API" is therefore a service inside the existing app that offers the documented behaviour (lightest approach). A separate backend service is not created now.
- **Sending and receiving.** In each batch the app sends its products and any stock changes made only in the app; the simulated server answers with its own values. The record of which stock changes have already been sent is kept by the app, so repeating a run never applies a change twice.
- A40, A41, A43 and A44 are treated as confirmed by the user's earlier "go ahead with the recommended way". A42 is a user decision. OQ41-2 is therefore treated as answered; OQ41-1 (real server) stays open.

## 4. Acceptance Criteria (Given/When/Then)

- **AC-1 (summary)** — Given the app has products, when a sync is run, then the result states the total number of products, the number of batches, and a status for every batch.
- **AC-2 (batch size, small)** — Given 389 products, when a sync is run, then there is exactly 1 batch containing all 389 products.
- **AC-3 (batch size, large)** — Given 1,200 products, when a sync is run, then there are exactly 3 batches (500, 500 and 200 products).
- **AC-4 (boundary)** — Given exactly 500 products, then there is 1 batch; given 501 products, then there are 2 batches.
- **AC-5 (progress)** — Given a multi-batch sync in progress, when each batch completes, then its status shows as completed and the number of completed batches out of the total can be read at that point.
- **AC-6 (server wins)** — Given the same product has a different name, category, unit, selling price, cost price or active status in the app and on the server, when a sync completes, then the app shows the server's value for each of those details.
- **AC-7 (sale not lost)** — Given a POS sale reduced a product's stock in the app since the last sync, when a sync completes, then the sale is reflected in the server's stock and the app ends with the server's resulting stock, which includes that sale.
- **AC-8 (new products both ways)** — Given a product exists only in the app, then after a sync it also exists on the server; given a product exists only on the server, then after a sync it also exists in the app.
- **AC-9 (failed batch)** — Given a sync of several batches in which one batch fails, when the failure happens, then the run stops with no further batches processed, batches already completed stay applied, and the error message names the batches that succeeded and the batch that failed.
- **AC-10 (server unreachable)** — Given the server cannot be reached, when a sync is run, then it stops with a clear message that the server is unreachable, and no product or stock data in the app is changed.
- **AC-11 (empty list)** — Given there are no products to sync, when a sync is run, then it returns a clear "no products to sync" message and no batches are run.
- **AC-12 (role access)** — Given a signed-in Admin, Manager, Cashier or Pharmacist, when they run a sync, then it is allowed; given a user without POS access (FR-POS-12), then it is refused with a permission message and nothing changes.
- **AC-13 (re-run is safe)** — Given a sync already applied some or all batches (including after a failure), when the sync is run again, then it completes correctly and each stock change made only in the app is applied exactly once, never twice.
- **AC-14 (no leftovers)** — Given a sync has finished (successfully or not), then no history, log or audit record of the run is kept beyond the result returned for that run.
- **AC-15 (contract documented)** — Given the story is complete, then the documented behaviour of the sync (inputs, results, error cases) exists in the API documentation, so that a real server can later replace the simulated one.

## 5. Security & Privacy Notes (business-level only)
- Sensitive data involved: product prices (including cost price) and stock levels, which are commercially sensitive. No customer or patient information is part of the sync.
- Who may run it: only users with POS access (FR-POS-12). Running without sign-in verification of the server is acceptable for development only (A42) and must be replaced before production (S-2.10.11).

## 6. Dependencies
- Upstream: S-2.10.6 (quick edit, done) and the existing product and POS stock data; FR-POS-12 role rules.
- Downstream: S-2.10.10 (sync UI) consumes the results of this story; S-2.10.11 (production authentication) must follow before release.
- External systems: a master product server (business dependency only). Not yet identified (OQ41-1); simulated for now.

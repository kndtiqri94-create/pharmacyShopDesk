# User Story 2.1 — Foundation

- **Workstream:** 2 — E-2 ShopDesk back office frontend, Feature F-2.1 Foundation (stories S-2.1.1 to S-2.1.7)
- **Traces to PRD:** FR-FND-1, FR-FND-2, FR-FND-3, FR-FND-4, FR-FND-5, FR-FND-6, FR-FND-7, FR-SHELL-1, FR-SHELL-2, FR-SHELL-3, FR-AUTH-1, FR-AUTH-2, FR-AUTH-3, FR-AUTH-4, FR-PROD-3, FR-GRN-5, FR-USR-2, FR-SET-3 (PRD v0.2)
- **Status:** Ready
- **Author:** Thilina (BA)
- **Created:** 2026-10-03

## 1. Story
As a **pharmacy owner or staff member (Admin, Manager, Pharmacist or Cashier)**, I want **to sign in to ShopDesk and land in a consistent, themed, responsive back office that only shows the modules my role allows, filled with realistic sample data** so that **every later module (Dashboard, Products, GRN, Purchase orders, Suppliers, Employees, Reload & Utility, Users, Settings) is built on one trusted look, one set of building blocks, one set of sample data and one set of access rules**.

## 2. Business Context
ShopDesk is the quiet back office of a one-shop pharmacy. Every later screen depends on this foundation, so it must deliver the shared look and feel in light and dark, the reusable screen building blocks, the sample business data, the main frame of the app with its sync indicator, sign-in, and per-module access by role. This serves PRD goals G1, G2, G4, G5 and G6. Colour values are approximate until the exact ones are supplied (PRD OQ1).

## 3. Scope
### 3.1 In Scope
- **S-2.1.1 Look and feel.** The full ShopDesk visual language in a light and a dark theme (colours, typefaces, spacing on a 4px grid, corner rounding, depth, interaction states), a way to switch theme, and the base responsive layout rules.
- **S-2.1.2 Icons and core building blocks.** The complete icon set plus buttons, badges, cards, summary stat cards, avatars and alerts.
- **S-2.1.3 Data and form building blocks.** Data tables with pagination, filter chips with live counts, tabs, labelled form fields on a responsive 12-column grid, toggles, breadcrumbs and a progress bar.
- **S-2.1.4 Sample data.** Realistic in-memory sample data for products and batches, GRNs, purchase orders, suppliers, employees, users and roles, reload activity, settings and sync state, using the design's sample conventions. All data access is isolated so a real data source can replace it later without changing screens.
- **S-2.1.5 Main frame.** Grouped dark sidebar (collapses on small screens), top bar, UI-only sync indicator, theme switch, and one separately loaded area for each of the nine modules.
- **S-2.1.6 Sign-in and session.** Sign-in screen, mock session, redirect of signed-out visitors to sign-in, and sign-out.
- **S-2.1.7 Role access.** Full / View / No access per module and role, applied to navigation, direct page access and the visibility of create/edit/destructive actions, driven by one permission matrix.
- Accepted assumptions: OQ2 (the signed-in Admin is shown with the label "Owner"), OQ3 (one sample user per role, derived from the design's sample data), OQ4 (non-core buttons such as Import CSV, Export, Print, Daily report, Statement, Forgot password, Quick PIN and Edit roles are shown but do nothing real and give a clear "sample only" message), OQ8 (the global search with its Ctrl K hint is shown as a visual control for now and does not search data; see Open Items in the hand-off).
- Desktop-first layout at 1280px and wider, and responsive on smaller screens, as a hard requirement.

### 3.2 Out of Scope (explicit)
- The content of the nine module screens (Dashboard, Products, GRN, Purchase orders, Suppliers, Employees, Reload & Utility, Users, Settings). Those are features F-2.2 to F-2.5; here each module only needs to be reachable as an empty placeholder page.
- Any backend, real authentication, real credentials, real tokens or storage beyond the current session and in-memory sample data.
- Real offline sync, queueing or conflict handling; the sync indicator is display-only.
- Real printing, file import/export, reports, SMS or payment integrations.
- Multi-branch features; there is no branch selector anywhere.
- Dedicated mobile mockups or a native/installable mobile app; responsiveness comes from reflowing the desktop design.
- Languages other than English.
- Exact colour values and exact dark theme values (pending the user's design file, OQ1); approximate values are accepted for now.
- Numeric performance targets and the exact smallest supported width (PRD OQ5, OQ6 unset); sensible values are chosen in the Plan and reviewed with the stakeholder.

## 4. Acceptance Criteria (Given/When/Then)

### 4.1 Look and feel and themes (S-2.1.1)
- **AC-1** — Given any screen in the app, when I view it in the light theme and then the dark theme, then colours, text, borders, buttons and status colours all change consistently, with no part left in the wrong theme and no raw one-off colours.
- **AC-2** — Given either theme, when I look at the sidebar, then it is dark in both themes.
- **AC-3** — Given either theme, when I read text and use controls, then ordinary text meets a 4.5:1 contrast ratio and control borders and the focus outline meet 3:1.
- **AC-4** — Given I use the theme switch, when I change theme, then the whole app changes immediately and my choice is kept for the rest of my session.
- **AC-5** — Given any screen, when I view it, then text uses the design's typefaces, codes (SKU, batch, GRN/PO numbers) appear in the monospaced face, stacked numbers line up in columns, spacing follows the 4px grid, and there are no gradients, glass effects or tinted left-border cards.
- **AC-6** — Given any interactive element, when I hover, focus or disable it, then hover on rows and outline buttons shows the sunken shade, hover on primary buttons shows the darker primary, focus shows a clear 2px ring with a 2px gap (white on the sidebar), disabled elements look 55% faded and do not respond, and nothing animates by default.

### 4.2 Responsive behaviour (S-2.1.1, S-2.1.3, S-2.1.5)
- **AC-7** — Given a window 1280px wide or more, when I open any screen, then I see the 232px sidebar and a fluid content area.
- **AC-8** — Given a window narrower than desktop (laptop, tablet, narrow window), when I open any screen, then the sidebar collapses behind a clearly labelled menu control, content uses the full width, and nothing is cut off or requires zooming.
- **AC-9** — Given a table wider than the screen, when I view it on a small screen, then it either scrolls sideways or stacks, and the key columns stay readable and usable.
- **AC-10** — Given a form laid out in columns, when I view it on a smaller screen, then the fields reflow into fewer columns and any side summary area moves below the main form.
- **AC-11** — Given a row of cards or summary tiles, when the screen gets narrower, then they reflow into fewer per row without overlapping.
- **AC-12** — Given the sidebar is collapsed on a small screen, when I open the menu, choose a module and the page changes, then the menu closes and I can reach every module my role allows using keyboard or touch.

### 4.3 Icons and core building blocks (S-2.1.2)
- **AC-13** — Given the design's list of icon names, when a screen needs any of them, then every name is available in one consistent line style, at three sizes, in the colour of the surrounding text.
- **AC-14** — Given an icon used on its own without a word, when it is a row action, then it has an accessible name; icon-only use outside row actions is not offered.
- **AC-15** — Given buttons, when I see each variant (default, primary, soft, danger outline, ghost), each size (small, medium, large), with an icon, full-width, or disabled, then each matches the design; danger buttons are outlined and never filled; large buttons are 46px tall.
- **AC-16** — Given a status badge, when it is shown, then it always carries a word (with a dot, or plain for counts) in the right tone, so status is never shown by colour alone.
- **AC-17** — Given cards, summary stat cards, avatars and alerts (info, warning, success), when they are shown, then they follow the design: stat card tone tints only the icon chip, avatars show initials, cards are never nested, and a table card can run edge to edge.

### 4.4 Data and form building blocks (S-2.1.3)
- **AC-18** — Given a data table, when it shows data, then numbers are right-aligned, money columns are headed "(Rs.)" with two decimals, the first cell has a name over a smaller code or subtitle, codes are monospaced, and there are at most three row actions, each with an accessible name.
- **AC-19** — Given a table with 10 or fewer rows, when it is shown, then no pagination appears; given more than 10 rows, then pagination appears with a "Showing a–b of N" summary and I can move between pages.
- **AC-20** — Given filter chips with live counts, when the data changes, then the counts update and I can pick one chip at a time; tabs are limited to five and used for sections, chips for list filters.
- **AC-21** — Given a form field, when it is marked required, shows a hint, a prefix or suffix (such as "Rs." or a unit), or has an error, then each displays as designed, and an error replaces the hint, turns the border red, and says what to fix.
- **AC-22** — Given a toggle, a breadcrumb and a progress bar, when I use or view them, then they follow the design and a toggle shows clearly whether it is on or off with a visible label.
- **AC-23** — Given any text the foundation shows (buttons, headings, empty states, errors), when I read it, then it follows the content rules: plain shopkeeper language using "you", verb-led sentence-case buttons (never "Submit" or "OK"), noun headings with a one-sentence subtitle, formats like `Rs. 84,250`, `21 Sep 2026`, expiry `Mar 2027` (inputs `03/2028`), empty states that say what to do next, no emoji and no exclamation marks.
- **AC-24** — Given I use only the keyboard, when I move through buttons, fields, tabs, chips, toggles, tables and pagination, then every control can be reached and operated and the focus is always visible.

### 4.5 Sample data (S-2.1.4)
- **AC-25** — Given the app has just started, when any module asks for data, then realistic pharmacy sample data is available for products with batches and expiry dates, GRNs, purchase orders, suppliers, employees, users with roles, reload transactions and float, settings, and sync state, using Sri Lankan rupees and the design's named people and suppliers.
- **AC-26** — Given a product that tracks batches, when its batches are listed, then they are ordered earliest-expiring first; given a product with batch tracking off, then it holds a single stock figure with no batches.
- **AC-27** — Given the sample data, when it is read for different business needs, then it contains at least one product of each status (out of stock, low stock, expiring soon, in stock), at least one overdue purchase order, a purchase order in each status, GRNs in each status and payment state, an owing supplier and an inactive supplier, and a reload float both above and below the low-float level.
- **AC-28** — Given I change sample data during a session (for example receive a GRN or record a payment in later features), when I move between screens, then the change is still there; given I refresh or start a new session, then data returns to the original sample set.
- **AC-29** — Given a screen needs data, when it gets it, then it never reaches data any other way than through the single data-access layer, so that replacing the sample data with a real source later needs no change to the screens.
- **AC-30** — Given settings values that influence other modules (expiry alert window, default reorder level, low-float threshold, sidebar low-stock count), when another part of the app needs them, then it reads them from the sample settings with their default values (60 days, per design, and Rs. 10,000 float threshold).

### 4.6 Main frame (S-2.1.5)
- **AC-31** — Given I am signed in on a wide screen, when I look at the sidebar, then I see the brand block ("S" tile, "ShopDesk", "Main Shop"), the groups OVERVIEW (Dashboard), INVENTORY (Products, GRN, Purchase orders, Suppliers), PEOPLE (Employees, Users), SERVICES (Reload & Utility) and SYSTEM (Settings), and the footer text "ShopDesk 1.0 · Offline ready".
- **AC-32** — Given the sidebar, when Products or GRN has a count to show, then a count badge appears beside it, and the current module is clearly highlighted.
- **AC-33** — Given the top bar, when I look at it on any screen, then I see a short page title, the search box with "Search products, GRN, suppliers…" and a Ctrl K hint, the sync indicator, a notification bell, and my initials, name and role (the Admin shown as "Owner").
- **AC-34** — Given the search box or Ctrl K, when I use it, then it does not search data and instead gives a clear "sample only" message without breaking the screen (accepted assumption OQ8).
- **AC-35** — Given any screen, when I view it, then the sync indicator is visible and shows exactly one of online, syncing or offline, and offline also shows the number of changes waiting; it is driven by sample state only and never blocks or disables any screen.
- **AC-36** — Given I click a sidebar module, when the page changes, then that module opens as its own page with its own web address, loaded only when first needed, and the sidebar lists exactly nine modules, with no second navigation row, no footer bar and no branch selector.
- **AC-37** — Given a module whose screens are not built yet, when I open it, then I see a page with the module's heading, a one-sentence subtitle and a clear message that the module is coming, inside the normal frame.
- **AC-38** — Given a web address that does not exist, when I open it, then I see a clear "page not found" message with a way back to the first module my role allows.

### 4.7 Sign-in, session and sign-out (S-2.1.6)
- **AC-39** — Given I am signed out, when I open the app on any address, then I am taken to the sign-in screen and, after signing in, I arrive at the address I originally wanted if my role allows it, or the first module my role allows otherwise.
- **AC-40** — Given the sign-in screen, when I view it, then it shows one card on a dark navy ground with the brand block, "Welcome back", a username or email field, a password field with show/hide, a "Forgot password?" link, a "Keep me signed in on this device" option, a full-width large primary "Log in" button, an outline "Show on-screen keyboard" button, and the footer "Works offline · last synced today 09:12".
- **AC-41** — Given a valid sample username and password, when I choose Log in, then I am signed in and see the main frame with my name and role.
- **AC-42** — Given a wrong password or unknown username, when I choose Log in, then an error appears under the password field telling me to check my password and try again, I stay on the sign-in screen, and the error does not reveal whether the username exists.
- **AC-43** — Given an empty username or password, when I choose Log in, then each empty field shows an error saying what to enter.
- **AC-44** — Given the sign-in screen, when I use the show/hide control, then the password toggles between hidden and visible and the control has an accessible name.
- **AC-45** — Given I choose "Show on-screen keyboard", "Forgot password?" or similar, when I do so, then a clear "sample only" message appears and nothing else changes (accepted assumption OQ4).
- **AC-46** — Given I am signed in, when I choose Sign out, then my session ends, I return to the sign-in screen, and going back or opening a module address sends me to sign-in again.
- **AC-47** — Given I am signed in, when I reload the page within the same visit, then I stay signed in; given "Keep me signed in on this device" was not chosen and I start a new visit, then I must sign in again. Sample sign-in only, with no real credentials.
- **AC-48** — Given the sample users, when I look at the sign-in details provided for testing, then there is exactly one sample user for each of Admin (shown as "Owner", Nimal Perera, initials NP), Manager, Pharmacist and Cashier, and the sign-in details for them are documented for testers (accepted assumption OQ3).
- **AC-49** — Given the sign-in screen at a narrow width, when I view it, then the card fits the screen and the Log in button remains large and easy to tap.

### 4.8 Role and permission gating (S-2.1.7)
- **AC-50** — Given the permission matrix for the four roles, when each role signs in, then it matches: Admin has Full on every module; Manager has Full on Dashboard, Products, GRN, Purchase orders, Suppliers and Reload & Utility, View on Employees, and No access to Users and Settings; Pharmacist has View on Dashboard, Full on Products and GRN, View on Purchase orders, Suppliers and Reload & Utility, and No access to Employees, Users and Settings; Cashier has No access to Dashboard, View on Products, Full on Reload & Utility, and No access to GRN, Purchase orders, Suppliers, Employees, Users and Settings.
- **AC-51** — Given a module where my role has No access, when I look at the sidebar, then that module does not appear.
- **AC-52** — Given a module where my role has No access, when I type its address directly or follow an old link, then I am stopped and shown a clear message that I don't have access to that area, with a button back to a module I can use; the module's content is never shown.
- **AC-53** — Given a module where my role has View only, when I open it, then create, edit and destructive actions are hidden or disabled, and read-only content is still fully visible. Given Full access, then those actions are available.
- **AC-54** — Given a signed-in user, when the permission matrix changes during the session (for example an Admin edits roles in a later feature), then what that session can see and reach updates to match without signing in again.
- **AC-55** — Given the Cashier, when they sign in, then they land on the first module they are allowed to open and not on a blocked page.
- **AC-56** — Given the access rules, when I view the matrix as a single source, then sidebar items, page access and action visibility all agree with each other for every role and module (no module is hidden but still reachable, or visible but blocked).

## 5. Security & Privacy Notes (business-level only)
- Sensitive data involved: sample sign-in details and the signed-in person's name and role. No real passwords, personal data, or financial data are used in this phase; all sample data is fictional.
- Who should/shouldn't be able to see or change this: only a signed-in person sees any back-office content. Each person sees and acts only on the modules and actions their role allows. People without access to a module must not see it listed, reach it by address, or see any of its content. The password is never shown on screen unless the person chooses to reveal it, and error messages never reveal whether a username exists.
- The sample sign-in is for testing only and must not be treated as real security; real sign-in arrives in a later phase.

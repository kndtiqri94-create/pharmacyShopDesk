- **Workstream:** 3 — F-3.2 Local data services (S-3.2.1, S-3.2.2, S-3.2.3, S-3.2.4, S-3.2.5, S-3.2.6)

## 1. Story
As a **pharmacy staff member (cashier, Pharmacist, Manager or Admin)**, I want **everything I record in ShopDesk (sales, returns, stock, products, customers, staff records and so on) to be saved on the device I am working on and read back from it, so that screens respond the same with or without internet** so that **I can keep selling and doing back-office work when the network is down, and nothing I have recorded is lost or counted twice when I reload or restart**.

## 2. Business Context
The pharmacy must keep selling when the network drops (PRD section 5.10, user direction 2026-11-23: the site must work both offline and online). F-3.1 made the application itself open offline; this workstream makes the business data work offline. Every read and write goes to the device first (FR-OFF-2). Screens, forms, rules, roles and design do not change (assumption A48), and the existing sample (mock) data behaviour remains available for development and testing. No server is needed; this workstream can start now. Sending changes to a server and showing real sync status come later (F-3.4); the server itself comes in F-3.3.

## 3. Scope
### 3.1 In Scope
- **S-3.2.1 Safe local storage foundation.**
  - Business data is kept on the device and survives page reload, closing the browser and restarting the device.
  - Future versions of the app can change how data is stored without losing what staff have already recorded.
  - The app asks the browser to keep the data permanently; if the browser refuses, the user sees a clear, visible warning that data could be cleared.
  - Every sale, return, stock movement and every other newly created record gets a unique identity on the device at the moment it is created, without needing the network.
  - The app can be built to use either the device-stored data or the existing sample data, so development and testing are unaffected.
- **S-3.2.2 Master data kept locally.** Products and their batches, suppliers, customers, bank accounts, users and roles, and settings are saved and read locally with the same behaviour and checks as today (for example a duplicate product code or a duplicate bank plus account number is refused exactly as now). No passwords are kept on the device.
- **S-3.2.3 Stock as a movement history.** Every change to stock (sale, return, goods received, adjustment) is recorded as one movement in an ordered history, and the stock shown is worked out from the batch quantity plus that history. Goods received notes and purchase orders use this. The existing earliest-expiry-first selling rule is unchanged. Every stock change in the app produces exactly one movement.
- **S-3.2.4 Point-of-sale transactions kept locally.** Sales, held bills, quotations, returns, invoice numbering, the cash book, counter close and customer dues are saved locally with device-created identities and are ready to be sent to a server later. Invoice numbers must not clash between devices.
- **S-3.2.5 HR records kept locally.** Employees, leave, salary advances, nopay and payroll inputs are saved and read locally with the same behaviour as today.
- **S-3.2.6 Offline proof.** An automated check demonstrates that a sale completed with the network off is still present and counted after reload and after browser restart, and that stock was reduced exactly once.

### 3.2 Out of Scope (explicit)
- Sending changes to a server, the pending-change queue, automatic or manual sync and the real sync indicator (F-3.4).
- The server, its database and its API (F-3.3); real sign-in and first sign-in on a new device (F-3.5); hosting (F-3.6).
- Changes to existing screens, forms, rules, roles or visual design, and removal of the sample data option.
- Offline "needs connection" messages for server-dependent functions (first sign-in on a new device, Update Products sync, user and role administration), unless confirmed as part of offline scope (see Open Questions).
- Data kept on the device being limited by the signed-in role, and offline re-sign-in rules (OQ44), beyond the rule that no passwords are stored.
- Merging conflicting edits between devices (server decides, later workstream).

## 4. Acceptance Criteria (Given/When/Then)

- **AC-1** — Given the app is using device-stored data, when a user records any data (for example a product, a sale or an employee) and then reloads the page, closes and reopens the browser, or restarts the device, then the data is still there exactly as recorded.
- **AC-2** — Given the app has stored data from an earlier version, when a newer version of the app that changes how data is stored is opened, then all previously recorded data is still present and usable.
- **AC-3** — Given the browser grants permanent storage, when the app starts, then no storage warning is shown; and given the browser refuses permanent storage, then a clear visible warning tells the user that locally saved data may be cleared.
- **AC-4** — Given the network is off, when a user creates a sale, return, stock movement or any other record, then it is accepted and gets a unique identity, and no two records created on the same or different devices share an identity.
- **AC-5** — Given the app is built for development or testing with the sample data option, when it is used, then it behaves as before; and given it is built for device-stored data, then every screen reads and writes the device data instead.
- **AC-6** — Given products, batches, suppliers, customers, bank accounts, users and roles, and settings, when a user adds, edits, searches or removes them, then results and validation messages are identical to the current behaviour (including refusal of a duplicate product code and a duplicate bank plus account number).
- **AC-7** — Given users and roles are stored on the device, when the stored data is inspected, then no password is present.
- **AC-8** — Given a sale, return, goods received note or stock adjustment is completed, when stock is checked, then exactly one stock movement exists for that change and the displayed stock equals batch quantity adjusted by the movement history.
- **AC-9** — Given a sale is made for an item with several batches, when the batch is chosen, then the earliest-expiry batch is used first, exactly as before.
- **AC-10** — Given two devices each record a sale of the same item, when their stock movements are later combined, then both sales are counted (stock changes are never stored or exchanged as a replacement total).
- **AC-11** — Given the user completes a sale, saves a held bill or quotation, processes a return, posts a cash book entry, closes a counter or records a customer due payment, when the screen is reloaded, then each is present with the same figures; and each is stored in a way that it can later be sent to a server without being re-entered.
- **AC-12** — Given sales are made on more than one device, when invoice numbers are issued, then no two devices produce the same invoice number.
- **AC-13** — Given employees, leave, salary advances, nopay and payroll inputs, when a user adds, edits or views them, then behaviour and validation are identical to current behaviour and the data survives reload and restart.
- **AC-14** — Given the network is off, when a user completes a sale and then reloads the page and later restarts the browser, then the sale is still present, is still counted in sales totals and cash figures, and the item's stock was reduced exactly once.
- **AC-15** — Given the existing test suite for each data area, when it is run against both the sample data option and the device-stored option, then it passes for both.
- **AC-16** — Given any existing screen, when used online or offline with device-stored data, then screens, forms and rules look and behave exactly as before this workstream.

## 5. Security & Privacy Notes (business-level only)
- Sensitive data involved: customer details and dues, staff and payroll information, sales and cash figures, supplier and bank account details, and user and role records. This data now sits on the device itself.
- Who should/shouldn't be able to see or change this: the same role rules apply as today; no new role-specific behaviour. Passwords must never be kept on the device. Whether the till PC is shared or locked down, and whether device data should be limited by role, are open (OQ44) and not decided here.
- Clearing browser data or losing the device before changes reach a server loses those changes; the permanent-storage warning (AC-3) is the user's signal of this risk.

## 6. Dependencies
- Upstream: F-3.1 PWA shell (done) and the E-2 screens and existing data behaviour that this workstream must match. No backend needed.
- Downstream: F-3.4 (sending changes and sync status) builds on the records being ready to queue; F-3.3 server validation mirrors the same rules.
- External systems: none.

## 7. Open Questions (non-blocking; to be settled at planning or by the Product Owner)
1. **OQ43 first run and seed data:** What does a brand-new device show, and is there real pharmacy data to load? Until answered, the story assumes a new device starts with whatever starting data the sample setup provides today; real data loading and first sign-in on a new device are not part of this story.
2. **OQ45 invoice numbering rule and device count:** How many tills sell at once is unknown. The business need (no two devices ever issue the same invoice number, AC-12) is fixed; the exact numbering format is to be decided at planning with the Product Owner.
3. **OQ46 offline scope:** FR-OFF-3 is still a proposal. This story treats all POS functions, product, GRN and PO entry as working offline; the "needs connection" behaviour for server-dependent functions is deferred.
4. **OQ44 sign-in and privacy:** only the "no passwords stored" part is applied here (AC-7).

### 10.4 Completion Notes
- Definition of Done checklist: `docs/checklists/3.2_LOCAL_DATA_SERVICES_STORY_DOD.md` (all applicable boxes ticked with file:line evidence; backend/API boxes marked N/A with justification).
- Data lives only in IndexedDB (Dexie 4). One object store per aggregate plus `stockMovements`, `documents` and `meta`; rows keep an internal `_ord` insertion counter so lists come back in the same order as the in-memory services, and products keep a `skuKey` index. Both internal fields are stripped on read.
- Stock: each product row keeps base quantities; shown stock is base plus the sum of movements. A product save compares incoming figures with the derived current stock and writes one movement per changed batch (or one product-level movement for non-batch products) in the same Dexie transaction as the product write. Saving unchanged figures writes nothing, so a retry cannot deduct twice. `ProductDataService.save/saveAll` gained an optional `StockChangeContext` (type, refId, userId); sale, return and GRN callers now pass SALE, RETURN and GRN; everything else is ADJUSTMENT. The in-memory service ignores it.
- Record IDs: `nextRecordId` now puts the device code in every id (for example `sale-K7M-001`) once a local device code is active, so records created on different devices never clash; movements use UUIDs (`crypto.randomUUID`, with a `getRandomValues` fallback).
- OQ45 invoice numbering as approved: `INV-<DEVICE>-<NNNN>`; the per-device counter is stored in `meta` and moved in the same transaction as the sale write. The device code (3 characters, generated on first run) can be overridden through `LocalDatabaseProvider.setDeviceCode('T1')`; there is no screen for it (screens must not change), so a settings control is left for Shiham to schedule. Older `INV-NNNN` numbers stay valid and are counted. Held bill numbers get the same device infix. The in-memory build keeps the plain `INV-NNNN` form.
- Build flag: `environment.dataSource` is `'mock'` (dev and tests) or `'local'` (production). `environment.ts` is git-ignored in this repository, so each developer must change `useMockData: true` to `dataSource: 'mock' as 'mock' | 'local'` there; `ClockService` now keys the sample date off `dataSource === 'mock'`, so the production build uses the real date. `provideDataServices(true)` still means in-memory, so existing specs are untouched.
- `ProductSyncServer` stays on the simulated in-memory server in local mode (no server exists until F-3.3); the sync status service is static (F-3.4).
- First run seeds the same sample starting data as the in-memory build (OQ43 assumption) in one transaction, flagged in `meta.seededAt`. Switching a device back to `mock` leaves the local database untouched.
- Write seam for S-3.4.1: `LocalDatabase.afterWrite(entityType, id, operation)` is called from every local write path (collections, products, movements, documents); it is a no-op for now and runs inside the write transaction.
- Shared contracts: the existing in-memory specs were moved into `core/services/data/contract/*.contract.ts` and run against both implementations (in-memory via `in-memory/*.spec.ts`, local via `local/local-data-contract.spec.ts`, using `fake-indexeddb`). Tests that only make sense in memory (reset in a new session, exact `INV-0001` text, exact `prod-011`) stayed in the in-memory specs. A duplicate bank plus account number is now also refused inside the data service on both implementations (`DuplicateBankAccountError`); the existing `BankAccountService` check still gives the same message first.
- S-3.2.6 tooling choice (updated after review iteration 1): the repository has no Playwright tooling, so the check is a Karma integration test (`core/services/offline-sale.e2e.spec.ts`) that runs the real POS sale service against the local database with `fetch`, `XMLHttpRequest` and `navigator.onLine` blocked. It now runs against the real `window.indexedDB` of Karma's ChromeHeadless (unique database name per test, `Dexie.delete` in `afterEach`); reload and restart tear down the injector (which closes the real database) and reopen it. `local-database.spec.ts` (reopen, device code, v1 to v2 upgrade, quota) uses the same real browser store. `fake-indexeddb` stays only for the shared contract suites. Recommended follow-up: a Playwright run against the production build with the network switched off.
- Stock and sale in one transaction (review Security Finding 1, Medium, A04/A08): NOT changed. The stock movement and product rows are written in one Dexie transaction, but the sale, return or GRN record is saved by a different data service (`SalesDataService`, `GrnDataService`) behind the abstract contracts, so one combined transaction needs new cross-service methods on both implementations and a rework of `PosSaleService`, `PosReturnService` and `StockInService`. That is a large refactor beyond this workstream. Mitigation in place: each movement is a delta with a unique id, and a save with unchanged figures writes nothing, so a retry cannot double count the same figures. Residual risk (sale record fails after stock is reduced) is left for the Team Lead to accept or schedule (suggested: `saveSaleWithStock` on `SalesDataService`).
- Startup failure (review Low A05): if IndexedDB cannot be opened, `app.config.ts` throws `LocalStorageUnavailableError` and `main.ts` shows 'This browser cannot store ShopDesk data on this device...' instead of the generic message.
- Environment file: tracked `environments/environment.example.ts` and a `frontend-app/README.md` section list the required keys (`production`, `appName`, `dataSource`, `mockAuthEnabled`). Old local files with `useMockData` must be replaced.
- Pre-existing failing tests: 4 specs (`PosCashBookService Admin only writes` x2, `CashBookDialogComponent ... leaves card out of cash`, `PosComponent Phase B ... bottom bar dialog`) fail identically on a clean HEAD worktree; see DoD.19. A separate backlog task to fix them is recommended.
- Residual risks recorded (Plan section 6): sign-in is still the mock until F-3.5 (OQ44); business data is stored unencrypted in the browser profile and readable on a shared till PC (A02, accepted); getting all products reads the whole movement list (Plan R5/R1 follow-up: add a periodic checkpoint if the history grows large).
- Observability: `LocalDbEvents` keeps an in-memory ring of event codes (`local-db.opened`, `local-db.upgrade`, `storage.persist.denied`, `local-db.quota-exceeded`) because the app has no logging abstraction yet.

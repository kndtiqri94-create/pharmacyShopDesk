### Verdict

### Summary
Reviewed the full F-2.7 frontend change set (new leave models, enums, nine leave utils, `LeaveAdminService`, the Leave application page and its children, the Leave tab and decision dialog, the Employees On leave rewiring, the seed, agreement spec) plus the step-0 stabilisation of the flaky F-2.6 spec, against FRONTEND_STANDARDS, the plan and all 52 ACs. The core engineering is strong. Actor identity comes from the session inside the service and is never an input. `canDecideLeave` blocks the applicant, a non-assigned Manager and anyone who is not the linked ACTIVE approver. Started Approved leave cannot be cancelled and terminal states are final. Overlap and balance are re-validated on fresh data. Service-set fields are never taken from input. On leave is derived consistently from Approved leave for tiles, list status word and attendance fallback. The old `LeaveRecord` and `leave-table` are fully removed. The step-0 spec fix addresses the root cause (no timeout bump) and carries an explanatory comment. The coordinator's build, lint and 1341/1341 test results satisfy DoD.18/19. However, four user-visible acceptance criteria are not implemented (AC-28, AC-33, AC-35, AC-45), and DoD.2 ("every AC is implemented") is therefore inaccurate. No Critical or High security findings.

### Blocking Findings
> Every item blocks approval. Critical/High OWASP findings are also echoed here (none).

1. **[FE]** `frontend-app/src/app/features/modules/employees/leave-requests/leave-requests.component.html` / `.ts` (whole component; only status chips at html:9-15) — *Rule violated:* Story AC-35  
   **Problem:** AC-35 requires narrowing the Leave tab by status AND by employee name or code. There is no search input, no search signal and no search util (`leave-list.util.ts` has only a status filter). The empty-result message exists, but it can only be reset by status.  
   **Required change:** Add a search box (name or code, case-insensitive, length-capped like `SEARCH_MAX_LENGTH`) to the Leave tab. Extend `filterLeaveRows`, reset paging on change, make "no leave requests match" reset clear both search and status, and add specs.

2. **[FE]** `leave-requests.component.html` (table columns `leave-requests.component.ts:105-125`; dialog `leave-decision-dialog/`) — *Rule violated:* Story AC-45 (also AC-39/AC-40 "comment is kept with the request")  
   **Problem:** No view shows the approver, the decision comment or the read-only status text for a decided request. `approverComment` is stored by `LeaveAdminService.runDecide` but is never rendered anywhere in the UI (grep: it only appears in an error-message lookup). A kept comment that nobody can read does not meet AC-45.  
   **Required change:** Add a read-only details view (row details or dialog) for any request showing employee, type, dates, days, reason, approver, status word, decision comment and decided date. It must be available to Manager (View) as well. Render by interpolation only. Add specs.

3. **[FE]** `leave-application/leave-application.component.html` (From/To Date block, lines ~86-116) — *Rule violated:* Story AC-28  
   **Problem:** AC-28 says the number of days is shown before Apply. The page computes days only inside validation and never displays them.  
   **Required change:** Show a live "Days requested: N.00" (using `countLeaveDays` and `formatLeaveDays`) once both dates are valid, with a spec.

4. **[FE]** `leave-application/leave-application.component.html` (`@if (loaded())` form at ~line 19 renders unconditionally) — *Rule violated:* Story AC-33  
   **Problem:** AC-33 requires a clear empty message instead of a blank form when there are no leave types or no employees to choose. The form always renders (the balance card only has a data-table empty state).  
   **Required change:** When `types().length === 0` or `activeEmployees().length === 0`, show an `app-empty-state` explaining what is missing instead of the form. Add specs for both cases.

5. **[FE]** `docs/checklists/2.7_LEAVE_MANAGEMENT_STORY_DOD.md` DoD.2 — *Rule violated:* DoD.2 evidence accuracy  
   **Problem:** DoD.2 is ticked with "AC-1..AC-52 implemented", which is false for AC-28, AC-33, AC-35 and AC-45.  
   **Required change:** After findings 1-4 are fixed, re-confirm DoD.2 with accurate per-AC evidence (spec names or file:line for those four ACs).

### Security Findings (OWASP Top 10 2021)
No Critical or High findings. Lower-severity items (not blocking):

1. **Severity:** Low — **OWASP:** A01 — **[FE]** `core/services/leave-admin.service.ts:54-59` and `core/utils/leave-status.util.ts:55`  
   **Vulnerability:** `decide` is guarded only by "a user is signed in", and `canDecideLeave` returns true for an Admin without checking `canOpenEmployees`. If an Admin's Employees permission were edited down to No access in Users & roles, the service would still accept a decision. The UI is unreachable in that case, so the practical impact is nil. It is a defence-in-depth gap versus AC-50 and Plan §6 EoP "live matrix".  
   **Remediation:** Require `actor.canOpenEmployees` for every actor, including Admin, in `canDecideLeave`.

2. **Severity:** Low — **OWASP:** A09 — **[FE]** `leave-admin.service.ts` (`runDecide` / `runCancel`)  
   **Vulnerability:** The deciding or cancelling actor is not recorded on the request (`decidedAt` only). This is the documented Repudiation limitation in Plan §6 and is accepted. Cancel records no distinct canceller.  
   **Remediation:** None required now. Add `decidedByUserId` when a backend arrives.

They are accepted on merit. The approver rule (linked ACTIVE user with Admin/Manager role) is accepted and consistently enforced in the validation and in `canDecideLeave`.

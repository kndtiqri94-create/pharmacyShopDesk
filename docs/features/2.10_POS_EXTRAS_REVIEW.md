### Blocking Findings
> Every item blocks approval. Critical/High OWASP findings are also echoed here (none this iteration).

1. **[FE]** `frontend-app/src/app/app.routes.spec.ts:228-236` (test "stops a role whose POS access was removed from opening the till by typing the address") — *Rule violated:* Story section 8 / DoD.19 (tests pass), FRONTEND_STANDARDS Testing and Quality Gates; Plan section 6 Elevation of Privilege (a role without POS access must not reach the till).
   **Problem:** The test fails in the working tree both in the full run (excluding only the `beforeunload` spec) and when run on its own (`ng test --include src/app/app.routes.spec.ts`: 22 SUCCESS, 1 FAILED). The router stays on `/pos` and the till renders (View only banner, all the new Phase B dialogs) instead of going to `/access-denied`. The DoD.19 evidence says the suite was "359 of 359 SUCCESS" on a targeted include, so this test was never run. I could not prove whether this was caused by the Phase A or Phase B changes (no routing file is in the diff; the spec file itself is unchanged since commit 08c4e5f). Until shown otherwise it is a red test in the delivered tree and it concerns the access-control path of the module being delivered.
   **Required change:** Run it against HEAD (clean checkout or worktree). If it passes at HEAD, find and fix the regression (look at what `PosComponent`/`PosService` now do on first render that keeps the `/pos` route active, for example the second same-URL navigation being ignored, or a guard no longer being evaluated). If it also fails at HEAD, record it as pre-existing in the story Completion Notes with the HEAD result so the Team Lead and Product Owner can accept it explicitly. Then update DoD.19 with the real full-suite result.

2. **[FE]** `frontend-app/src/app/core/services/data/in-memory/in-memory-sales-data.service.ts:149,181` (`saveReturn`, `saveDuePayment`), `core/services/pos-return.service.ts:105`, `core/services/pos-due.service.ts:46`, `core/utils/pos-cash-ledger.util.ts:120` — *Rule violated:* Story AC-57 ("anyone tries to change that day's ... cash entries, then it is refused with a message that the day is locked"), Plan section 3.3 ("the in-memory implementation REFUSES writes to a locked day's opening, entries, or report"), Plan section 6 Tampering ("locked day modified through a direct service/data call").
   **Problem:** Only `saveDayOpening` and `saveCounterReport` check the lock. After Counter Close, a cash refund on a return and a cash due payment are accepted without any warning and without any refusal (the services never look at the day status). `buildCashEntries` then drops them (`createdAt <= closedAt`), so that cash leaves or enters the drawer and appears in no Cash Book view for any day, and no Counter Close figure. Only a sale after close is allowed by the story (AC-59, with a warning). The story's aim is that the owner can trust the daily cash figures; an untraceable cash-out after close defeats that. Because the lock is a Plan section 6 control, this is a missing control, not a style point.
   **Required change:** Decide with the Product Owner and implement one of the following, then add specs (service and data layer, Admin included):
   (a) Refuse `PosReturnService.complete` for a CASH_REFUND and `PosDueService.takePayment` for a CASH payment while today's counter is closed, with `DAY_LOCKED_MESSAGE`, and make `saveReturn`/`saveDuePayment` throw `DayLockedError` for a cash entry dated on a closed day; or
   (b) Mirror AC-59: require the same confirm-to-continue warning for returns and due payments, and show post-close movements in the Cash Book in a clearly separate "After close" section so no cash movement is invisible. Record the decision in the story (new assumption B-6).

### Security Findings (OWASP Top 10 2021)
> Full scan for A01-A10 plus the insecure-code patterns list.

1. **Severity:** Medium — **OWASP:** A04 (Insecure Design) / A01 — **[FE]** `in-memory-sales-data.service.ts:149,181`, `pos-cash-ledger.util.ts:120`
   **Vulnerability:** Cash refunds and cash due payments made after the counter is closed are neither refused nor reported, so a user can move cash on a "locked" day with no trace in any report (see Blocking 2). Impact: loss of the integrity guarantee the closed day is meant to give.
   **Remediation:** As Blocking 2.

2. **Severity:** Low — **OWASP:** A01 — **[FE]** `core/services/pos-cash.service.ts:42,58`, `pos-due.service.ts:32`, `pos-quotation.service.ts:32`, `pos-records.service.ts:12`, `last-invoice-dialog.component.ts` (reads `SalesDataService` directly)
   **Vulnerability:** The read paths (cash book, dues, quotations, last invoice) do not re-check `canView(POS)` in the service; they rely on the `/pos` route guard and the hidden bottom bar. Plan section 6 only requires the write re-check, which is done, and the route guard is unchanged, so this is not exploitable in the current app. Defence-in-depth only.
   **Remediation:** Optional. Add a `canView(ModuleKey.POS)` check in `PosRecordsService.load` and the read methods so a future caller cannot bypass the route.

3. **Severity:** Low — **OWASP:** A08 — **[FE]** `core/services/pos-return.service.ts:133-134`, `pos-product-update.service.ts:71-73`, `pos-sale.service.ts:63` vs `pos-write-guard.service.ts:19`
   **Vulnerability:** `PosSaleService` keeps its own `busy` flag while `PosWriteGuard` uses named scopes, so a sale save and a return or product update (all read-modify-write on product stock through `saveAll`) are not mutually exclusive. The dialogs are modal, so this needs a concurrent action to trigger, but a lost stock update is possible in principle. Stock write and record write are two awaited calls, not one block as the Plan states ("one synchronous block").
   **Remediation:** Route `PosSaleService.guarded` through `PosWriteGuard` with the same `pos-stock` scope for stock-changing operations. Optional because the in-memory calls are effectively synchronous.

### Non-blocking Suggestions
1. `pos-counter.service.ts` and `pos-records.service.ts` have no `*.service.spec.ts` of their own (FRONTEND_STANDARDS Service Tests naming). Counter close is exercised in `pos-cash.service.spec.ts`; split it into `pos-counter.service.spec.ts` for discoverability.
2. A CASH_REFUND is allowed against a sale that was paid by Card, Online or Credit, so the Cash Book can show cash out that never came in. Consider limiting the cash refund to the cash portion of the original sale, or ask the Product Owner (this is not in B-1 to B-5).
3. `PosReturnService.findInvoice` calls `reset()` and silently discards typed quantities when the user looks up another invoice while a return is in progress (`pos-return.service.ts:68`). Consider the same confirm as AC-15.
4. The `LEAVE` confirm copy says "This bill has items that are not saved" even when the thing being left is a return in progress (`pos.component.ts:97-103`).
5. `LastInvoiceDialogComponent` reads `SalesDataService` directly; a small `PosLastInvoiceService` would match the other dialogs.
6. Write the stock change and the record in one block (or roll back the stock write if the record write throws) in `PosReturnService.complete` and `PosProductUpdateService.save`, as Plan section 6 describes.
7. Open manual checks (DoD "Manual checks NOT verified in a browser"): responsive layout at 1440/1280/1024/768/360, dark theme, print layouts, and F11 on real browsers (Plan R2). Please run them before the release; they are not blocking for code review.
8. The existing `pos.component.spec.ts` "warns the browser before the tab is closed..." test dispatches a real `beforeunload` and breaks the Karma run (disconnect at about 1477 of 2330). Replace the dispatch with a call to the handler or a spy on the window listener so `npm test` can finish.

## 1. Summary
Frontend only, inside `frontend-app/`. Replace the Suppliers, Employees and Users placeholder routes (currently `createModuleRoutes(...)` stubs) with real screens. Suppliers: list card (search, All / Owing / Inactive chips, table) beside a detail panel with Record payment (settles that supplier's Received GRNs oldest first), Recent activity (latest five), Edit (sample only) and New PO (opens `/purchase-orders/new?supplier=<id>`). Employees: four StatCards, Staff / Attendance / Leave tabs, staff table with search and chips, "Today's attendance" card. Users and roles: Users card, Add user side panel, edit-role side panel, lock/unlock with confirmation, and Role permissions card with Edit roles (Save changes / Discard). All data goes through the F-2.1 abstract in-memory data services (session only). Export, Add supplier, Edit supplier, Add employee, Mark attendance and employee row actions show the "sample only" message via `NotificationService` (OQ4). Amount owed to a supplier is always derived from GRNs (`supplier-owed.util.ts`) so the Suppliers screen, GRN "Unpaid to suppliers" tile, PO side card and Dashboard agree (AC-17, AC-51).

## 4. Data Model & Migrations
- No database, no migrations. In-memory models only. Money integer cents, formatted only through `money.util.ts`; dates ISO strings formatted only through `date.util.ts`.
- New models: `SupplierPayment`, `AttendanceRecord`, `LeaveRecord` (above). `Supplier.outstandingCents` removed or unused; owed is derived. `AppUser` and `Employee` unchanged in shape (no password, PIN or "must change" flag on `AppUser`; those live only in the session credential store). `Employee.userId` is the link; "System login" is derived from the linked user.
- Record payment mutates only `Grn.paidCents` (and derived `paymentStatus`, never accepted from input) plus appends a `SupplierPayment`. A payment only touches Received GRNs for that supplier.
- Disabling a user changes only `AppUser.status`; GRN `receivedBy` and other history strings are untouched and the user stays in the list.
- Everything resets on refresh (AC-52). Data services return deep copies.
- Rollback strategy: not applicable.

## 5. API Contract (draft)
No HTTP API. Contract is the abstract data services returning `Observable`s of domain models plus `SupplierPaymentService.recordPayment`, `UserAdminService`, and `RoleAdminService.saveMatrix`. No `docs/api-docs/` document for 2.4.

| Concern | Contract |
|---|---|
| Routes | `/suppliers`: Admin, Manager Full; Pharmacist View; Cashier none. `/employees`: Admin Full; Manager View; Pharmacist, Cashier none. `/users`: Admin Full; others none. |
| Query params | `/purchase-orders/new?supplier=<id>` (validated, Active suppliers only). `/suppliers?supplier=<id>` optional preselect, validated against known ids, invalid falls back to first supplier. |
| Record payment | Amount in rupees from the form, validated then converted once to cents; applied oldest first; returns new owed or typed validation errors. Only entry point that changes `paidCents` from this feature. |
| Users | Create requires an unlinked employee, unique username, password >= 8, PIN empty or 4 digits; edit changes role only; lock toggles status; self-disable and own-role-change rejected. |
| Roles | Save writes the whole matrix with Admin forced to Full on every module. |

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data, client-side gating is UX only (stated in the story). Controls must still be correct so a real backend can enforce the same rules later.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | Creating a user for someone else's employee record or reusing a username to impersonate; `recordedBy` forged; disabled user continuing to sign in. | Username unique (trimmed, case-insensitive) and employee must be unlinked, both enforced in `user-validation.util.ts` and re-checked in `UserAdminService`. `recordedBy` taken from `AuthService.currentUser()` at save time, never from a field or URL. Sign-in refuses non-Active users (`status` re-read on every attempt and on session restore); refusal message is plain and does not reveal passwords. |
| **T**ampering (integrity) | Y | Crafted payment amount (NaN, negative, > owed, huge, scientific notation), forged payment status, double-click on Record payment applying twice, forged `?supplier` / `?supplier` ids, matrix cells with invalid values, Admin column edited by crafted call, shared-reference mutation of seeds. | Amount parsed and bounded in `supplier-payment-validation.util.ts` (> 0, <= owed re-read at confirm time, 2 decimals, max value); payment status always derived; Confirm disabled while processing and owed re-checked inside the service so a second click fails validation. Query/route ids validated against known records with safe fallback. `normaliseMatrix` rejects unknown enum values and forces Admin Full both in the panel and in `RoleAdminService`. Compute all new copies before any save; services return copies. |
| **R**epudiation | Y (low) | No audit trail in this phase; who recorded a payment, created, disabled or re-roled a user, or changed permissions. | `SupplierPayment.recordedBy` and date stored; user `lastSignIn` kept; Disable keeps history. No further audit for a session-only frontend. Documented limitation. |
| **I**nformation Disclosure | Y | Cashier or Pharmacist seeing balances, staff personal data, user accounts or the permission table; temporary password or PIN echoed back or logged; credentials lingering after sign-out; unescaped supplier text. | Each module behind `moduleAccessGuard` (blocks before the chunk loads, AC-47 to AC-49). Write UI hidden with `*appCanWrite`. Password and PIN inputs are `type="password"` (PIN with `autocomplete="off"`), cleared after Create or Cancel, never shown in toasts, never stored on `AppUser`, never in `localStorage` / `sessionStorage`, never in `console`. `SessionCredentialStore` is memory only and exposes no read-back getter. Angular interpolation only; no `[innerHTML]`, no `bypassSecurityTrust*`. No `console.log`. |
| **D**enial of Service | Y (low) | Huge search strings, very long names or passwords, rapid repeated clicks. | Search max 100 chars trimmed; password max 100, username and other text max lengths; lists paginate at 10 (no pagination at 10 or fewer, AC-5, AC-26); computed signals and `takeUntilDestroyed` for subscriptions. |
| **E**levation of Privilege | Y | Typing `/users`, `/employees`, `/suppliers` as the wrong role; Manager or Pharmacist invoking Record payment / create user by calling handlers; changing own role to escalate; disabling oneself; locking Admin out; editing the permission table without Admin. | `moduleAccessGuard` on all three routes (UrlTree to access-denied). `PermissionService.canWrite` re-checked inside `SupplierPaymentService`, `UserAdminService` and `RoleAdminService` (defence in depth). Self-disable and own-role change rejected in the service and the lock action is disabled on the own row (AC-37). Admin column fixed at Full and `USERS` stays Full for Admin so the shop cannot lock itself out. Matrix change applies live through `matrix$`, so removed access takes effect on the next guard run and in the sidebar immediately. |

## 9. Risks & Trade-offs
- R1 **Static mock credentials:** sign-in checks the static `MOCK_CREDENTIALS` list; new users need a session credential store consulted by `AuthService`. Production file replacement (`mock-credentials.prod.ts`) must keep working; store is empty in prod build semantics only if mock auth is disabled. Mitigation: store consulted only when `MOCK_AUTH_ENABLED`.
- R2 **Derived vs stored owed:** removing `Supplier.outstandingCents` touches seed-coverage specs; developer must update them and list the change in Completion Notes.
- R3 **Attendance data is new:** attendance/leave have no existing models; seeds must be consistent with `Employee.status` (On leave employee has an On leave attendance row and a leave record).
- R4 **Permission change applies live:** `PermissionService` already subscribes to `matrix$`; a guard only re-runs on navigation, so an already-open forbidden page stays until the next navigation. Acceptable for the sample; sidebar updates immediately.
- R5 **Own-role change and Admin lockout:** the story only forbids self-disable; this plan also rejects changing your own role and keeps Admin Full everywhere. Flagged as a small safe addition consistent with "the shop can never lock itself out"; reviewer to confirm no AC conflicts.
- R6 **Disabled user display on Employees:** System login for a Disabled user is not specified; plan shows the role with a Disabled marker and counts them in "Can log in" only if Active. Developer must pick this behaviour consistently and record it; if the user wants otherwise, ask Thilina to clarify.
- R7 **Scope size:** three stories, about 60 new files; build order below.

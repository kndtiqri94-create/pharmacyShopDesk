## Iteration 1

### Verdict
**CHANGES_REQUESTED**

### Summary
Reviewed the whole frontend-only F-2.5 change set in `frontend-app/src/app/`: five new pure utils, `ReloadService`, `SettingsService`, the `saveFloat` data-service addition, model/seed changes, the sidebar refresh on `SettingsService.changed`, the Dashboard float rule extraction, both routes, the Reload & Utility page with seven children, the Settings page with five children, and the page, agreement and routes specs. The implementation is high quality and matches the plan. Validation is strict and linear (no regex, no scientific notation, bounded lengths). Services re-check `canWrite`, re-read float and settings at call time, compute copies before saving, and guard against double submit. Settings use a local draft and only `SettingsService.save` writes. Module guards are applied in `app.routes.ts` for both modules. The security pass found no Critical/High issues and all Plan §6 rows are honoured. One blocking standards/plan deviation remains: seven new components have no `.spec.ts`, although FRONTEND_STANDARDS "Component Structure" and Plan §3.3 both require one per component. Backend standards were not applied (no backend work in this workstream).

### Blocking Findings

1. **[FE]** Missing standalone specs for seven new components:
   - `features/modules/reload-utility/mobile-reload-card/mobile-reload-card.component.ts`
   - `features/modules/reload-utility/bill-payment-card/bill-payment-card.component.ts`
   - `features/modules/reload-utility/recent-transactions/recent-transactions.component.ts`
   - `features/modules/settings/shop-profile-section/shop-profile-section.component.ts`
   - `features/modules/settings/currency-region-section/currency-region-section.component.ts`
   - `features/modules/settings/inventory-alerts-section/inventory-alerts-section.component.ts`
   - `features/modules/settings/backup-sync-section/backup-sync-section.component.ts`

   (`operator-tiles`, `reload-float-card`, `top-up-dialog` and `settings-group-list` do have specs.)

   *Rule violated:* FRONTEND_STANDARDS "Component Structure" ("Include corresponding `.html`, `.scss`, and `.spec.ts` files") and "Test File Structure" (`component-name.component.spec.ts`); Plan §3.3 ("each component in its own folder with `.ts/.html/.scss/.spec.ts`"); DoD.6 and Plan §7 Component tests.
   **Problem:** Hasika recorded in Completion Notes that these are "covered through the page specs". The behaviour is in fact well exercised by `reload-utility.component.spec.ts` and `settings.component.spec.ts`, so regression risk is low. However, the standards give no carve-out for this, and the plan explicitly required a spec per component. This was a unilateral deviation not approved by the Team Lead. The only precedent for spec-less components is the two static error pages (`access-denied`, `not-found`), which have no logic. `mobile-reload-card` and `bill-payment-card` own substantial state (submit guard, error clearing, focus-first-error, amount preview, read-only Other box) and are the most important gaps.
   **Required change:** Add a `*.component.spec.ts` beside each of the seven components. The two cards need real specs (inputs, submit result handling for ok/invalid/denied/busy, error clear on edit, focus on first problem, preview, Clear, hidden controls when `canWrite` is false). The five thin presentational components may have short specs (renders required labels, emits the expected event/patch, disabled when `disabled()`, sample-only message on the sample buttons, status badge words and column set for recent-transactions). Alternatively the Team Lead may record an explicit, written waiver for the five thin components; the two cards should not be waived.

### Security Findings (OWASP Top 10 2021)
No Critical, High or Medium findings.

1. **Severity:** Low — **OWASP:** A04 — **[FE]** `core/services/reload.service.ts:136-137,162-163`
   **Vulnerability:** `applyReload` and `applyBill` perform two sequential writes (`saveFloat` then `addTransaction`). If the second write failed, the float would be changed with no transaction row. With the in-memory service this cannot fail, so no exploit exists today.
   **Remediation (non-blocking):** When a real data service replaces the in-memory one, make the float change and transaction insert a single atomic operation (server-side transaction). Note in the plan hand-off for the backend phase.

2. DoD.6 evidence cites `reload-utility.component.ts:70-72` for the sync `ngOnInit`; the hook is at lines 61-63. Correct the line reference when the DoD file is next touched.
3. `reload.service.ts` could expose a single `commitFloatAndTransaction` step in the data service contract so the float change and the transaction row are written together once a real backend exists (see Security Finding 1).
4. Plan §3.3 said transaction ids come from `unique-id.util.ts`; the implementation uses `nextRecordId` from `document-number.util.ts`, which is the better fit (stable `rt-N` ids). No change needed; mention in Completion Notes for accuracy.
5. Accepted deviations from the plan (seed Rs. 15.00 commission on a seed bill row, seed dates) were left unchanged as plan R3 allowed. Fine.

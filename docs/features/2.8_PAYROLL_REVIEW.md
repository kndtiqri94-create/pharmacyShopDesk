## Iteration 1

### Verdict

### Summary
Reviewed the full F-2.8 frontend change set (calculation utils, data service and seed, `PayrollService`, `PayrollAdminService`, `PayrollExportService`, the Payroll page, table, filters, row menu and three dialogs plus the records dialog, and the F-2.8 touch points in permission, module-definition, matrix, routes, Employees page, `LeaveAdminService.applyApprovedDay`, `money.util` and the emp-007 seed) against FRONTEND_STANDARDS.md, the story (AC-1 to AC-70, including the section 3.2 assumptions), the plan (including section 13 decisions) and the DoD file. Functionally this is strong work: the calculation is integer-cents with one documented half-up rule and band-edge tests (I hand-checked the 250,000 gross case: 18,000.00 tax); advance and nopay caps are checked against a gross freshly recomputed inside the service; every `PayrollAdminService` method passes through one `guarded()` whose first line re-checks `canWrite(PAYROLL)`; the quick-leave approver is service-derived and can never be the applicant; Paid has no write path; derived values are never stored; the export checks `canView(PAYROLL)`, uses a column whitelist, neutralises CSV formulas and escapes PDF text; toasts carry no amounts or reasons; the hidden Payroll module is excluded from the sidebar but still gets a matrix row and tolerates legacy matrices. I found no Critical or High security issue and no Threat Model failure. One standards finding blocks approval: the mandatory no-abbreviation identifier naming rule is broken in the two payroll services (inconsistent with every exemplar). It is cheap to fix. Everything else is non-blocking.

### Blocking Findings
> Every item blocks approval. Critical/High OWASP findings are also echoed here.

1. **[FE]** `frontend-app/src/app/core/services/payroll-admin.service.ts:54-57`, `frontend-app/src/app/core/services/payroll.service.ts:29-31` and `:50`, `:55` — *Rule violated:* FRONTEND_STANDARDS "Identifier Naming (no abbreviations)" (injected dependencies must carry the full `...Service` name, e.g. `userAdmin` becomes `userAdminService`; template of `exportService`-style fields in the exemplars; callback parameters should be descriptive).  
   **Problem:** Injected services are named `employeeData`, `leaveData`, `payrollData` and `leaveAdmin` (no `Service` suffix) in both payroll services, while the exemplars the plan cites (`leave-admin.service.ts`, `employee-admin.service.ts`) use `employeeDataService`, `leaveDataService` and so on. `payroll.service.ts` also uses single-letter lambda parameters `i` and `p` in the `inputs.find` and `payments.find` calls.  
   **Required change:** Rename to `employeeDataService`, `leaveDataService`, `payrollDataService`, `leaveAdminService`; rename `i`/`p` to `input`/`payment`; update the specs that reference these private fields if any. Behaviour is unchanged.

### Security Findings (OWASP Top 10 2021)
> Full scan for A01-A10 + insecure-code patterns. Critical/High severity = blocking.

No Critical or High findings. Lower-severity observations (none blocking):

1. **Severity:** Low — **OWASP:** A01 — **[FE]** `frontend-app/src/app/core/services/leave-admin.service.ts:70-75`  
   **Vulnerability:** `applyApprovedDay` is a public method on a root-provided service and only requires `canWrite(EMPLOYEES)`, not `canWrite(PAYROLL)`. Today the only caller is `PayrollAdminService` (which does re-check PAYROLL), and nothing in the UI reaches it otherwise, so there is no exploitable path in this phase. A future caller (or a role with Employees Full and Payroll View) could create an already-Approved leave without a Payroll write permission.  
   **Remediation:** Defence in depth: make `applyApprovedDay` also require `canWrite(ModuleKey.PAYROLL)`, or document that it is Payroll-only. Not required for approval.
2. **Severity:** Low — **OWASP:** A01 — **[FE]** `frontend-app/src/app/core/services/payroll.service.ts:33-75`  
   **Vulnerability:** `getPayrollRows` and `getRecords` do not re-check `canView(PAYROLL)` (only the export does). They are reachable only from the Payroll page, which sits behind `moduleAccessActivateGuard` on `PAYROLL`, so no real exposure; the plan did not require it.  
   **Remediation:** Optional: return an empty list when `canView(PAYROLL)` is false.
3. **Severity:** Low — **OWASP:** A04 — **[FE]** `frontend-app/src/app/core/utils/payroll-validation.util.ts:83-90`  
   **Vulnerability:** The advance and nopay cap is per entry (amount greater than that month's gross is refused), exactly as AC-46 and AC-51 state. Several entries can together exceed gross; net is clamped to 0 and the row shows the shortfall warning, so the figures stay safe.  
   **Remediation:** None needed for this story; consider a cumulative cap as a future story.

### Non-blocking Suggestions
1. **Judged deviations (all accepted on merit, to be confirmed by the Product Owner):**

   - Employer EPF and ETF computed per flag (EPF cost only with Calculate EPF, ETF cost only with Calculate ETF): accepted. It is the more correct reading of AC-7, has no visible effect (no column), and the values are not deducted.
   - emp-007 salary 0 in the seed: accepted. It is the required "no salary at all" employee (AC-17); allowances and overtime rate were cleared with it, and other employees cover allowances, overtime, commission, EPF/ETF, Daily and tax.
   - Payroll PDF builder as a parameterised copy of the Employees one: accepted for now, but about 60 lines of PDF helpers (`toPdfText`, `wrapHeader`, object and xref assembly) are duplicated between `payroll-export.util.ts` and `employee-export.util.ts`. Extract to a shared `pdf-document.util.ts` in a later clean-up story.
   - Payroll reached via a button, not a tab: accepted; AC-61 says "tabs and links" and the plan says "tab or link"; the Payroll button is non-primary so each Employees tab keeps one primary action.
2. Dead or duplicated config: `PayrollSettings.note` and `PayrollSettings.dailyRateDivisor` are seeded but never read (`payroll.seed.ts:20,22`); the sample-values note is hard-coded twice (`payroll.component.html` and `PAYROLL_SAMPLE_NOTE` in `payroll-export.util.ts:19`). Either read the note from settings or drop the unused fields. `employerEpfCents` and `employerEtfCents` are computed but not consumed anywhere (acceptable per AC-7, keep specs).
3. `FRONTEND_STANDARDS` "Managing Files" asks for one interface or type per file; several payroll files declare multiple (for example `payroll-admin.service.ts` result types, `payroll-list.util.ts` `PayrollTab`/`PayrollFilters`/`PayrollPage`, `payroll-table.component.ts` event interfaces). 4. `SalaryAdvanceDialogComponent` injects `PayrollDataService` directly (`salary-advance-dialog.component.ts:29-34`) to read counters; prefer a method on `PayrollService` (for example `getCounters()`) to keep dialogs off the data layer.

6. A Daily row shows Daily Rate plus other components, so on screen the visible components do not literally sum to Gross (Days Worked is shown beside it). Consistent with OQ12; consider a tooltip or caption.
7. Add Leave is shown in the row menu to a role with Payroll Full but no Employees write, then refused with the access message (documented deviation 17). Consider hiding that menu item for such roles.
8. Defence-in-depth items from the Security Findings (applyApprovedDay Payroll check; `canView` in read methods).

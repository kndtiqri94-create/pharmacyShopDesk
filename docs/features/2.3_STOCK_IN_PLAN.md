## 1. Summary
Frontend only, inside the existing `frontend-app/`. Replace the GRN and Purchase orders placeholder routes with real screens: GRN list (3 StatCards, search, status chips with live counts, "This month" date button, table with payment/status badges), New GRN form (delivery details, payment, items table, totals, expiry-under-six-months warning, Save draft, session-kept in-progress entries, Receive stock), Purchase order list (chips, "Last 30 days" button, overdue highlighting, Receive/edit/view actions) and New/Edit purchase order form (supplier side card, items table, "Add all low-stock items", Save draft, Print, Mark as sent). Receiving a GRN is the only thing that raises stock: it appends a batch per line to each product, recalculates stock and status, sets cost price to the GRN cost, and closes or part-closes the linked PO. All data goes through the F-2.1 abstract in-memory data services (session only). Export, Print and Scan item show the "sample only" message via `NotificationService` (OQ4). Dashboard "New GRN", "Create PO" and "Open" actions are wired to the real screens. The GRN and PO models, seeds and in-memory services already exist from F-2.1; this feature extends them.

### 3.3 Frontend — add (under `frontend-app/src/app/`, each component in its own folder with `.ts/.html/.scss/.spec.ts`)
Core utils (pure, each with `.spec.ts`):
- `core/utils/grn-totals.util.ts`: line total = receivedQuantity x cost (free adds nothing to amount), lines/units (units include free), Total = sum less Discount (never below 0), Balance due = Total less Paid now, derived payment status (Paid / Part paid / Unpaid), all in integer cents.
- `core/utils/grn-validation.util.ts`: Supplier and invoice no required (message "Enter the supplier invoice number"), at least one line, per-line batch no required, expiry valid `MM/YYYY` via `parseExpiryInput`, received > 0, free >= 0, cost >= 0, Paid now numeric, >= 0 and <= Total, Discount numeric and >= 0 and <= sum; max lengths; returns field-keyed errors plus first-error order for focus.
- `core/utils/expiry-warning.util.ts`: lines whose expiry is less than six months from today (fixed rule), message "{Product} expires in {n} months (MM/YYYY). Check with the supplier before accepting."; none when valid month beyond window.
- `core/utils/grn-receiving.util.ts`: pure function applying a validated GRN to products (append batch with entered batch no, expiry, quantity = received + free, cost; set product `costCents`; for batch-tracked products append batch, for non-tracked add to `stockOnHand` with no batch; same batch no and expiry on same product merges quantity) and to the linked PO (add received quantity per matching product line; Received when every ordered quantity is met, else Part received; never un-receive). Returns new copies, never mutates inputs. Product selling price is NOT changed (assumption in story).
- `core/utils/grn-list-filter.util.ts`: search (GRN no, invoice no, supplier name, case-insensitive, trimmed, max 100), status filter, date-range filter ("This month"), chip counts reflecting search and range, summary tiles (received this month total plus count of GRNs and suppliers; waiting-to-be-received = POs Sent or Part received, expected within 7 days; unpaid to suppliers = balance on Received GRNs, invoice count, oldest age), pagination slice (10).
- `core/utils/purchase-order-list-filter.util.ts`: search (PO no, supplier), status filter, "Last 30 days" ordered-date range, chip counts, items summary text, overdue flag via existing `purchase-order-overdue.util.ts`.
- `core/utils/purchase-order-totals.util.ts`: line total, Sub-total, Delivery (amount typed), Total, lines/units, latest expected date; low-stock suggestion (`order qty` to bring stock above reorder level, excluding products already on the order and inactive products).
- `core/utils/purchase-order-validation.util.ts`: Mark as sent requires supplier, at least one line, qty > 0, unit cost >= 0 and numeric, Delivery >= 0; Save draft allows no lines.
- `core/utils/document-number.util.ts`: next GRN number (continues from highest, e.g. GRN-0212) and next PO number (PO-0150) derived from existing records; id generation via `shared/utils/unique-id.util.ts`.
- `core/utils/supplier-owed.util.ts`: amount owed to a supplier = sum of balance (Total less Paid) on that supplier's Received GRNs (agrees with side card and Unpaid tile).

## 4. Data Model & Migrations
- No database, no migrations. In-memory models only. Money stays integer cents, formatted only through `money.util.ts`; dates ISO strings formatted only through `date.util.ts`; expiry stored as end-of-month ISO date from `parseExpiryInput`.
- `Grn`, `GrnLine`, `PurchaseOrder`, `PurchaseOrderLine`, `Batch` models already exist; only add fields if truly required (for example `PurchaseOrder.deliveryCents` for the typed Delivery amount and `Grn.purchaseOrderId`; prefer deriving `purchaseOrderNumber` to id lookup). Any model change must update seeds and specs and be listed in Completion Notes.
- PO `totalCents` = Sub-total + Delivery. GRN `totalCents` = line sum less `discountCents`. Payment status is always derived, never accepted from input (`grn-totals.util.ts`).
- New batches on receiving: `Batch.id` generated, `costCents` = line cost; product `costCents` set to the latest received line cost; product status never stored. Batch-tracked products: batches kept sorted earliest-expiry first for display via `batch-order.util.ts`.
- Changes live for the session only; refresh resets to seed (AC-53). Data services return deep copies.
- Rollback strategy: not applicable.

## 5. API Contract (draft)
No HTTP API. Contract is the abstract data services returning `Observable`s of domain models plus `StockInService.receiveGrn`. No `docs/api-docs/` document for 2.3.

| Concern | Contract |
|---|---|
| Routes | `/grn` list, `/grn/new`, `/grn/:id` (Draft reopens, Received read-only): Admin, Manager, Pharmacist Full; Cashier none. `/purchase-orders` list (Admin, Manager Full; Pharmacist View; Cashier none), `/purchase-orders/new` and `/purchase-orders/:id/edit` (Full only), `/purchase-orders/:id` read-only. |
| Query params | `/grn/new?po=<purchaseOrderId>` prefills supplier and lines (validated: id must exist and PO must be Sent or Part received, otherwise ignored with a plain message). `/purchase-orders?status=` and `/grn?status=` optional preselect, validated against enum, invalid falls back to All. |
| Receive | `StockInService.receiveGrn` validates then applies `grn-receiving.util.ts`; returns the saved GRN or typed validation errors. Only entry point that changes stock. |
| Numbers | Next GRN/PO numbers derived from the highest existing number. |

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data, client-side gating is UX only (stated in the story). Controls must still be correct so a real backend can enforce the same rules later.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y (low) | "Received by" is taken from the session user; a crafted value could impersonate another person. | `receivedBy` set from `AuthService` current user at save time, not from a free-text field or URL; field read-only. No new auth surface. |
| **T**ampering (integrity) | Y | Crafted query params (`po`, `status`), route `:id`, or form values (negative, NaN, huge quantities, malformed expiry) corrupt stock, cost prices or PO state; payment status or totals forged; seed mutation by shared references; double-click on Receive stock receiving twice. | All numbers parsed and bounded in `grn-validation.util.ts` / `purchase-order-validation.util.ts` (integers for quantity, cents for money, max values, max lengths). Totals and payment status always derived, never read from input. Saved models built from validated values only (no spreading raw form value). Query/route ids validated against known records, invalid falls back to safe default or not-found. Receive stock disabled while processing and idempotent (a GRN already Received cannot be received again; `StockInService` rejects). Services return copies; receiving computes all new copies before any save. |
| **R**epudiation | Y (low) | No audit trail in this phase; "Received by" is the only attribution. | Record `receivedBy` and received date on each GRN; no other audit required for a session-only frontend. Documented limitation. |
| **I**nformation Disclosure | Y | Cashier seeing GRN, PO, supplier balances or cost data; Pharmacist seeing write UI on POs; draft form values lingering after sign-out; console leakage; unescaped supplier text. | Both modules guarded by `moduleAccessGuard` (blocks before chunk loads). `*appCanWrite`/`PermissionService` hides write UI. Draft stored in memory only (not localStorage/sessionStorage), cleared on sign-out and after Receive or Save draft. Angular interpolation only; no `[innerHTML]`, no `bypassSecurityTrust*`. No `console.log`. Dashboard actions hidden when target not accessible. |
| **D**enial of Service | Y (low) | Huge search input, thousands of lines, huge quantities freeze the UI. | Search max length 100, trimmed; lists paginated at 10; line count capped (for example 200) with a plain message; quantity and money upper bounds; computed signals, no per-keystroke subscription leaks (`takeUntilDestroyed`). |
| **E**levation of Privilege | Y | Typing `/purchase-orders/new` or `/:id/edit` as Pharmacist or Cashier; Pharmacist editing a PO via Receive; calling a receive/send handler without permission; Receive stock without GRN write. | `moduleAccessGuard` plus `moduleWriteGuard` on create/edit routes returning UrlTree to access-denied (AC-51/52). Submit handlers and `StockInService.receiveGrn` re-check `canWrite` before changing data (defence in depth). PO "Receive" only navigates to `/grn/new?po=` and never edits the PO; PO is only updated through a received GRN. Read-only mode uses disabled controls. |

## 9. Risks & Trade-offs
- R1 **Pharmacist and PO:** Pharmacist is View on PO but must use "Receive". Receive navigates to GRN (Full) and never writes the PO from the PO screen; the PO is updated by the GRN receive flow, which is permitted by GRN write access. Confirmed as story assumption.
- R2 **Sidebar badge:** GRN badge counts Draft GRNs (F-2.1 definition) and must refresh after save. Products badge behaviour unchanged (see F-2.2 R2).
- R3 **Receive atomicity:** several services are saved in sequence. Compute all new copies first, then save; on any failure show a plain error and do not partially apply (best effort within in-memory services, documented).
- R4 **Model gaps:** `Grn.purchaseOrderNumber` is a number string, not an id; Part received PO matching uses number lookup. Developer may add `purchaseOrderId` only if lookup by number is shown to be ambiguous.
- R5 **Draft persistence scope:** "kept for the session" is interpreted as in-memory for the browser session; it is lost on page refresh, consistent with AC-53 (refresh returns to sample set).
- R6 **Money inputs:** typed rupees converted with `rupeesToCents` after validation; no floating-point arithmetic on cents beyond that single conversion.
- R7 **Largest-scope risk:** five stories, about 45 new files; build order below.

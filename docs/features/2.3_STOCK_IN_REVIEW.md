### Security Findings (OWASP Top 10 2021)
> Full scan for A01–A10 plus insecure-code patterns. No Critical or High findings.

1. **Severity:** Low — **OWASP:** A04 — **[FE]** `core/services/stock-in.service.ts:51-62` (`receiveGrn`) and `:76-78` (`buildGrn`)  
   **Vulnerability:** Idempotency for a brand-new GRN (`existingId === null`) relies only on the component's `saving()` flag. Two concurrent service calls would both read `getAll()` before either saved. They would produce a duplicate GRN number and double the stock. Not reachable from the UI today (the buttons are disabled while saving). The Plan §6 control "StockInService rejects" is met only for the already-received case.  
   **Remediation (non-blocking):** Add an in-flight guard inside `StockInService` (a single `Promise` lock) or re-derive the number and id immediately before the save.

2. **Severity:** Low — **OWASP:** A04 — **[FE]** `features/modules/purchase-orders/purchase-order-form/purchase-order-form.component.ts` `store()`  
   **Vulnerability:** An existing PO is saved from the in-memory `existing()` snapshot without re-reading the stored status. With session-only data and one tab there is no realistic abuse path. A real backend must enforce "only Draft POs are editable".  
   **Remediation (non-blocking):** Re-read the PO in `store()` and refuse if it is no longer Draft.

No XSS vector (no `[innerHTML]`, no `bypassSecurityTrust*`), no `console.*`, no browser storage use, no `Math.random`, no secrets and no outbound HTTP was found in the new or changed files (grep-verified).

### Non-blocking Suggestions
1. Seed renumbering (cancelled GRN to GRN-0207, draft GRN to GRN-0211) is acceptable. It is needed to satisfy the story's "next GRN is GRN-0212", only numbers changed (ids, amounts, dates and statuses are the same), and all dependent specs were updated (no stale `GRN-0211` or `GRN-0212` expectation found). The new `PurchaseOrder.deliveryCents` field is allowed by Plan §4 and is set to 0 in all five seed orders. Both are recorded in the story, as the plan requires.
2. Date-range deviations are reasonable but not in the story: Draft GRNs and POs ignore the range, the date buttons are display-only, and "Expected within 7 days" counts overdue open POs (AC-2 says "due in that period"). Ask Thilina or the Product Owner to ratify these in the story text so AC-2, AC-8 and AC-33 are not silently reinterpreted.
3. The same `ID_PATTERN` constant is now declared in three form components (grn-form, purchase-order-form, product-form). Extract it to a `core/utils` file (FRONTEND_STANDARDS "No duplication in features").
4. `purchase-order-form.component.ts` `openExisting` navigates away for a non-Draft edit but still returns `true`. The blank form can flash briefly. Return a redirect flag and skip rendering.
5. `grn-validation.util.ts` `validateLines` silently falls back to the product's selling price when the price text is invalid (`parseCents(line.price) ?? product?.priceCents`). The price cell is read-only, so this is harmless, but the fallback hides bad input. Drop it or add an error.
6. `receiveGrn` saves products, then the PO, then the GRN sequentially. A mid-way failure would leave stock raised without a GRN. This is the best-effort atomicity Plan R3 accepts. Consider a rollback of the saved copies in a `catch`.
7. FRONTEND_STANDARDS describes i18n (`en.json` and `no.json`). ShopDesk is English-only by story scope, as in F-2.1 and F-2.2, so no finding was raised. The standards file is a generic one and has not been adapted to this project.
8. Three badge components (`grn-status-badge`, `payment-status-badge`, `po-status-badge`) have no `.scss`. This matches the F-2.2 `product-status-badge` precedent, so it is accepted.

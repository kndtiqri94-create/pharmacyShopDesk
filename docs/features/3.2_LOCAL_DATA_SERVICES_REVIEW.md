### Security Findings (OWASP Top 10 2021)
No Critical or High findings.

1. **Severity:** Medium — **OWASP:** A04 / A08 — **[FE]** `frontend-app/src/app/core/services/pos-sale.service.ts:105-115`, `local/local-product-data.service.ts:60-72`  
   **Vulnerability:** Plan §4 says the movement is written "inside the same Dexie transaction as the originating sale/return/GRN". The implementation writes movement plus product in one transaction (`saveAll`), but the sale, return or GRN record is saved in a second, separate transaction afterwards. If the second write fails (quota exceeded, day-locked, tab closed, power loss), stock stays reduced with no sale record. That is a persistent integrity gap, and a retry can deduct again from the re-read stock. In-memory had the same orchestration, but it was volatile, so the impact is new with durable storage. Not blocking because the movement-level exactly-once and idempotency guarantees hold and the loss window is small. TL should accept it or schedule it.  
   **Remediation:** Add a combined transactional write (for example `saveSaleWithStock`) or an outbox-style compensating movement on failure. Alternatively, record the risk as accepted in the Plan.

2. **Severity:** Low — **OWASP:** A02 — **[FE]** all of `local/`  
   **Vulnerability:** Customer, payroll, bank and sales data is stored unencrypted in IndexedDB. The Plan documents this as an accepted risk (OQ44), and no passwords or tokens are stored (verified).  
   **Remediation:** None now. Revisit with OQ44 and F-3.5.

3. **Severity:** Low — **OWASP:** A05 — **[FE]** `frontend-app/src/app/app.config.ts:24`  
   **Vulnerability:** `await localDatabaseProvider.ready()` runs inside `provideAppInitializer`. If IndexedDB is unavailable or blocked (for example Firefox private mode, or a corrupt DB), app bootstrap rejects. The user would see a blank app with no message. This is a robustness and availability issue.  
   **Remediation:** Catch the open failure and surface a clear "this browser cannot store data" state.

### Non-blocking Suggestions
1. **`environment.ts` is git-ignored (`.gitignore:211`) and now needs `dataSource`.** I judge this not blocking. `environment.ts` was already untracked at HEAD, so a fresh clone could not build before this change either. The production build uses the tracked `environment.prod.ts`, which is correct. But any developer with an old local `environment.ts` (`useMockData`) now gets a TS compile error on `environment.dataSource` for `ng serve` and `ng test`. Add a tracked `environment.example.ts` or a README note (README.md already mentions `environment.ts`) listing the required keys: `production`, `appName`, `dataSource`, `mockAuthEnabled`. Tell the team once.
2. Plan 4 transaction gap (Security Finding 1): decide accept or fix. A combined "sale plus stock" transactional method is the clean fix.
3. `LocalProductDataService.getAll` and `LocalStockLedgerService.sums` read the entire `stockMovements` table on every product list. Add the planned checkpoint or aggregate once history grows (R5).
4. Device code: 3 base-32 chars gives a small but non-zero chance of two tills choosing the same code. Consider a collision check at first sync (F-3.4) or a required readable till label. Also `setDeviceCode` has no UI, so schedule the settings control with Shiham.
5. `LocalDatabaseProvider.open` closes the DB on `versionchange` and never reopens. A second tab running a newer build would leave the first tab with a closed DB. Consider a reload prompt.
6. `BankAccountDataService.create` now throws `DuplicateBankAccountError` in memory too. The behaviour matches AC-6 and the existing service check still produces the same message first, so I accept the change. Mention it in the PR description.
7. Seeding sample products, users and sales into production local DBs follows the OQ43 assumption. Keep it on the OQ43 follow-up list so a real pharmacy device is not left with sample data.
8. The storage banner lives inside `AppShell`, so it only shows after sign-in. That is acceptable for AC-3.

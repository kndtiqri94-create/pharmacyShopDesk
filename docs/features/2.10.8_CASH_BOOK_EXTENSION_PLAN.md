## 4. Data Model & Migrations
- No database, no migrations. In-memory, session only; resets on refresh. Rollback: not applicable.
- Real-source rows (Opening Balance, Invoices, Invoice Returns, cash dues) are derived from existing sales, returns and due records; they are not stored twice. Mock rows are generated, flagged `isMock`, and labelled as sample in the spec and the export note.
- Adjustments and actual balance are the only new stored records; append-only (a new actual balance for the same date supersedes by a new dated entry, prior kept). A closed counter day stays immutable: writes for a locked day are refused (reuse `DayLockedError` / `DAY_LOCKED_MESSAGE`).
- Money in integer cents. All ids, timestamps and actors are service-set.

## 5. API Contract (draft)
No HTTP API. Contract is `PosCashBookService` and `CashBookExportService` plus the extended `PosCashService`. No new route; the Cash Book opens from the till bottom bar as today.

| Surface | Purpose | Access |
|---|---|---|
| Cash Book dialog (view, filter, reset, export) | Show and export range figures | `canView(POS)` |
| Add Actual Balance, Adjustment, Add OB | Record counted cash, signed adjustment, opening balance | Admin role AND `canWrite(POS)`, re-checked in the service |

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data; client gating is UX only. Controls are written as a real backend would enforce them. Sensitive data: daily cash position, expenses, salary advances, loan settlements, adjustments.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | An adjustment, actual balance or opening change attributed to the wrong user, or actor taken from the form. | Actor id and name read from the live session inside the service; ids and timestamps service-set; every write re-checks the live session. |
| **T**ampering (integrity) | Y | NaN, negative or 3-decimal amounts, huge magnitudes, adjustment without a note, reversed or malformed date range, double submit, writes to a locked day, CSV formula injection through the adjustment note, export that differs from what is shown. | One validation util used by UI and service with strict numeric parsing (reject NaN, Infinity, extra decimals, over cap); Balance and Difference recomputed in the util, never taken from the UI; busy guard on every save; locked-day refusal retained; CSV cells starting with `=`, `+`, `-`, `@` are neutralised; export built from the same ledger object as the screen. |
| **R**epudiation | Y | Who recorded the counted cash, adjustment or opening change cannot be shown. | Each record stores actor id, name and time; adjustment stores its note; opening keeps the existing change log; records are append-only. |
| **I**nformation Disclosure | Y | Cash position visible to users without POS access; amounts leaked in toasts; mock data mistaken for real data. | Dialog renders only with `canView(POS)`; toasts name the action not amounts; no `console.*`; no storage, route or query state; no `[innerHTML]` and no `bypassSecurityTrust*`; mock rows labelled sample; exports re-check `canView(POS)`. |
| **D**enial of Service | Y (low) | Huge note text, very wide date ranges, repeated export clicks. | Note and amount length caps; date range span cap; in-flight guard on export and save; key handlers scoped to the dialog and removed on destroy. |
| **E**levation of Privilege | Y | A non-Admin POS user records counted cash, adjustments or opening balance by calling the service or un-hiding buttons. | Admin role check enforced in `PosCashBookService` and in the Add OB entry from the Cash Book (not only in the template), plus `canWrite(POS)`; non-Admin gets a clear refusal message; no Reload and Utility data read and no Reload Commission control. |

### 6.1 Assets & Trust Boundaries
- Sensitive data: cash opening, actual and counted amounts, adjustments, expense and salary mock figures, actor identity on records.
- Trust boundary crossings: dialog input to services, session identity to records, Blob download and PDF generation, keyboard events.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A01 (Admin-only writes enforced in the service), A03 (CSV formula injection, no `[innerHTML]`), A04 (derived figures, append-only records), A08 (service-side recomputation), A09 (audit fields). Reviewer still does a full A01 to A10 pass.

## 7. Test Strategy
- Utils at band edges: ledger row order and count (13 rows plus 3 summary rows), Difference = Actual minus Balance, zero range, Card and Online only, Cash excluded from other payments, validation (amount 0, negative, NaN, 3 decimals, over cap; empty note; reversed range; span cap), CSV injection neutralisation, mock rows flagged.
- Services: `PosCashBookService` (Admin allowed; Manager, Cashier, View-only, unauthenticated refused; stale locked day refused; double submit; actor from session), export service (denied, failed, success file name).
- Components: title "Cash Book", default Today, Filter, Reset to Today, invalid range keeps previous figures and shows message, all rows visible including mock rows, no Reload Commission or Provider TopUp text anywhere, action buttons hidden or disabled for non-Admin while Filter, Reset and exports still work, focus stays in dialog and Esc closes, unsaved bill survives open and close, S-2.10.4 behaviour still passes.
- Negative tests MUST cover: unauthenticated, no POS access, non-Admin role, invalid input (NaN, negative, huge, extra decimals), oversized input, stale or locked day.
- Per project rule, agents do not auto-run the suite; the user runs `npm test` and the build.

## 8. Observability
Not applicable beyond UX feedback: inline alerts for validation, toasts naming the action only. No logging, no analytics, no `console.*`. Audit trail is in the records.

## 9. Risks & Trade-offs
- R1: OQ38 unanswered. Built to A36; semantics isolated in `cash-book-ledger.util.ts` so a change is cheap.
- R2: Mock rows can mislead. Mitigation: `isMock` flag, a visible sample label and the export note.
- R3: Admin-only gating on Add OB changes existing S-2.10.4 behaviour for non-Admin roles within the Cash Book. Mitigation: confirmed requirement (AC-17); existing till-level Add OB button behaviour unchanged unless the user says otherwise (flag to user).
- R4: Existing `cash-book-dialog` specs assert the old layout; updated, not deleted.
- R5: PDF built in-browser; follow the payroll approach to avoid a new dependency.

## 10. Out of Scope
- Reload and Utility in any form, Sinhala or other languages, real backend, real PDF/CSV services, mobile app, payment methods beyond Cash, Card, Online, Credit, linking Cashbook Bank Deposit to real bank accounts.

## 1. Summary
Frontend only, inside `frontend-app/`, session-only mock data. Add a POS till at `/pos` reached from a blue "POS" pill in the top bar (before the avatar). The till: header (date/time, dark-mode toggle, refresh, one real-state fullscreen toggle, Back to back office), bill header (date, Invoice only, generated invoice number, customer select defaulting to Walk-in Customer, optional rep, Create New / Hold), product search (name, generic name, SKU, barcode, scan-style Enter) and bill lines (S/N, SKU, Rep, Barcode, Sale Price, Discount %, QTY, Action, Total), totals (Items, Sub Total, Discount Rs./% linked, Total, Paid, Balance), payment (exactly Cash F3, Card F4, Online F7, Credit; split payment; keypad), actions (Save & Print F1, Save F2, Hold F10, New F12, held-bills list). A sales data layer records sales, deducts stock earliest-expiry-first, holds/resumes/discards bills, numbers invoices, and feeds the Dashboard Today's sales/profit. POS becomes a permission-matrix row (`pos`: all four roles Full). Settings gets a "Point of sale" section (line discount on/off, bill discount on/off, one default discount %, maximum %, "Hide sidebar when POS opens"). Any line or bill discount other than the default opens an Admin-credentials dialog (active Admin only, even for a signed-in Admin, one approval per change); the approver name and time are stored on the sale, never the password. Phase B (F-2.10) buttons do not exist in Phase A.

## 4. Data Model & Migrations
- No database, no migrations. In-memory models; data lives only for the session and resets on refresh. Rollback: not applicable.
- Money in integer cents (`money.util.ts`, `Rs. 1,234.00`, right-aligned, two decimals); percentages as numbers 0-100; dates ISO via `date.util.ts`; half-up rounding documented once in `pos-totals.util.ts`.
- Sales, held bills, customers and reps are stored; totals shown on screen are always recomputed from lines, payments and the discount. Stock is the single source in `ProductDataService`; a sale's `batchAllocations` record where stock came from.
- POS settings are new fields on `AppSettings` with seed defaults (0% default, 20% max: placeholders per A20). Sessions with an older settings object fall back to these defaults, never crash.
- Today's sales/profit on the Dashboard = seed history plus saved POS sales for today (profit = sum of line revenue minus batch cost).
- Credentials are never part of any model or signal that outlives the approval call.

## 5. API Contract (draft)
No HTTP API. The contract is the abstract `SalesDataService` plus `PosService`, `PosSaleService`, `PosDiscountApprovalService`, `PosFullscreenService`. Routes:

| Route | Purpose | Access |
|---|---|---|
| `/pos` | Till screen | POS view/full (all four roles Full by default; session matrix decides, AC-80 to AC-85) |
| Receipt view (in `/pos`, dialog or print section) | Printable receipt | Same as `/pos` |
| Discount approval | Dialog inside `/pos` | Anyone with POS access may request; only active Admin credentials approve |

POS selling requires `canWrite(POS)`; a View user can open the till but cannot save, hold or change discounts (service-level check, not UI only).

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data; client-side gating is UX only (stated in the story). Controls must still be written correctly so a real backend can enforce the same rules later. The sensitive item is the Admin credential typed into the approval dialog; second are money and stock integrity.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | A non-Admin guesses or reuses an Admin login to approve discounts; approver identity forged by the form; sale attributed to someone else. | Approval verifies username+password server-side-style in `AuthService.verifyCredentials` using `constantTimeEqual`; only an ACTIVE user whose role is ADMIN is accepted (re-read from `UserDataService`, not from a cached or client-supplied role); approver id/name/time are set by the service, never taken from the dialog; failed attempts reuse the sign-in failure throttle; input length capped (`SIGN_IN_MAX_INPUT_LENGTH`); verification never changes the signed-in session; cashier/actor read from the session inside `PosSaleService`. |
| **T**ampering (integrity) | Y | Crafted quantity/price/discount/payment (NaN, negative, `1e9`, 3+ decimals), discount applied without approval by calling the setter directly, discount above max via paste, price edited client-side, stock oversold between add and save, double submit creating two sales, shared-reference mutation of seeds, held bill resumed with stale prices or discount. | One validation util (`pos-validation.util`, `pos-discount.util`) used by both UI and services; the discount setter in `PosService` only accepts a value together with an approval token for non-default values (state machine, not a UI check); maximum enforced before the dialog and again at save; unit price is read from fresh product data at save, not trusted from the line; `PosSaleService` re-reads products, re-validates, allocates FEFO and computes copies first, then writes stock+sale in one synchronous block; in-flight guard and save-button disable; integer cents; deep copies from data services; resumed held bills are re-priced and re-validated against fresh stock and settings; keypad util rejects second decimal point and over two decimals. |
| **R**epudiation | Y (low) | An unapproved or disputed discount, or "who sold this", cannot be traced. | Each sale stores the actor (cashier), the approver name and time per approved discount (line and bill both recorded, AC-96, AC-104), rep, and `createdAt`. No password stored. Session-only limitation documented. |
| **I**nformation Disclosure | Y | Password visible/kept (signal, form value, DOM, console, history); profit and sales amounts shown to roles that should not see them; receipt/toasts leaking totals; customer names in logs. | Password input `type="password"`, `autocomplete="off"`, form value cleared on every close path (success, fail, cancel, Esc, destroy) and never copied into a signal, service field or error message; no `console.*`; nothing in `localStorage`/`sessionStorage`; profit is not shown on the till; Dashboard profit visibility unchanged (existing rules); toasts name the invoice number only, never amounts or credentials; no values in query params or route state; no `[innerHTML]`, no `bypassSecurityTrust*`, receipt rendered by template binding and printed with `window.print()` (no `document.write`). |
| **D**enial of Service | Y (low) | Huge search strings, thousands of lines, rapid F-key repeat, rapid approval attempts, key handler leaks after leaving the till. | Search term and approval inputs length-capped, result list capped; line count and quantity bounded in validation; computed totals O(lines); in-flight guard on save/hold; approval failure throttle; global key handlers registered only while the POS component is alive and removed in `ngOnDestroy`/`DestroyRef`; `takeUntilDestroyed` on subscriptions. |
| **E**levation of Privilege | Y | A Manager/Cashier approves their own discount; Admin approval bypassed by deep-link or direct service call; user without POS access opens `/pos` or sells; View-only user saves; matrix edited mid-session; discount above max exceeds even for Admin. | `moduleAccessGuard` + `moduleAccessActivateGuard` on `/pos` (AC-83); `canWrite(POS)` re-checked inside `PosSaleService` save/hold/resume/discard and in discount-change entry; the approval service accepts ADMIN role only (Manager, Pharmacist, Cashier, inactive Admin rejected, AC-98); a signed-in Admin is not auto-approved (A20-2, always asks); maximum has no override; permissions read from the live matrix (AC-85); `normaliseMatrix` keeps Admin FULL for POS and a missing POS key defaults to NONE for non-admin; F-key handlers ignore events when the till is not the active page (AC-78). |

### 6.1 Assets & Trust Boundaries
- Sensitive data: Admin username and password in the approval dialog; sales totals and customer names; the discount-approval audit trail; stock levels.
- Trust boundary crossings: dialog input to `AuthService.verifyCredentials` (credential check); till UI to `PosSaleService` (stock+sale write); settings to POS defaults; browser Fullscreen and print APIs; keyboard events to till actions.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A01 (access control, route guard, role check), A02/A07 (credential handling, no storage, throttle, constant-time compare), A03 (injection: no `[innerHTML]`, CSV not applicable), A04 (insecure design: single state machine for discounts), A08 (data integrity: fresh-data revalidation, atomic write), A09 (audit fields on sales). ## 9. Risks & Trade-offs
- R1: Mock credentials in dev (`mock-credentials.ts`) are the approver source; prod file differs. Mitigation: use the same `matchCredentials` path as sign-in so behaviour is identical in both builds.
- R2: Session-only sales mean the Dashboard figure resets on refresh. Mitigation: documented; zero state handled (AC-14).
- R3: "Only Admin approves, even a signed-in Admin" and "one default for both line and bill" are unconfirmed beyond the story assumptions; both are isolated (role check in one function, one setting) so a later change is cheap.
- R4: Fullscreen and F-keys vary by browser (F11 is browser-owned; some keys cannot be fully suppressed). Mitigation: listen to `fullscreenchange` for real state; `preventDefault` for the handled keys on the till; document F11 as browser-handled.
- R5: Stock deduction is a deliberate exception to "only a GRN changes stock" (A11); the write must be atomic with the sale to avoid drift.
- R6: Phase B reuses the sale model; keep `Sale` extensible (return/quotation links are NOT added now).

# Implementation Plan 3.1 — PWA Shell

- **Workstream:** 3 — F-3.1 PWA shell (S-3.1.1, S-3.1.2, S-3.1.3)
- **User Story:** `docs/user-stories/3.1_PWA_SHELL_USER_STORY.md`
- **Status:** Draft
- **Author:** Sanjeewa (Team Lead)
- **Created:** 2026-11-23

## 1. Summary
Make `frontend-app/` an installable, offline-loading PWA using `@angular/pwa` / `@angular/service-worker`: manifest (ShopDesk name, theme colour, standalone display, icons), `ngsw-config.json` caching the app shell, fonts and icons only (API calls never cached), service worker registered in production builds only. Add a non-blocking "new version available" notice (SwUpdate) that applies the update only on user choice or next start, never reloading mid-sale, and an Install affordance driven by `beforeinstallprompt`. Frontend only. No screen, rule or design change.

## 2. Exemplars / Reference Pattern
- Backend exemplar: n/a (no backend work).
- Frontend exemplar: existing standalone-component and service patterns in `frontend-app/src/app/core/services/` (e.g. `theme-preference.service.ts`) and `shared/components/toast-host/` for the notice UI; `app.config.ts` for provider registration. Follow `docs/development-standards/FRONTEND_STANDARDS.md` sections selected via INDEX.md (services, components, a11y, testing, security/CSP).

## 4. Data Model & Migrations
- Entity changes: none. No IndexedDB or business data stored; only app files in Cache Storage.

## 5. API Contract (draft — finalised in API_DOC)
None. Service worker must not intercept or cache any API traffic (no `dataGroups`; navigation requests for non-file URLs fall through to index only for app routes).

## 6. Threat Model (STRIDE-lite — MANDATORY)
| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing | N | No new auth surface; sample sign-in unchanged | Not applicable; real auth is F-3.5 |
| **T**ampering | Y | Poisoned or stale SW cache could serve altered or outdated app code; SW script itself is a high-value target | HTTPS-only origin (SW requires secure context); Angular ngsw hash-verifies cached assets against `ngsw.json`; same-origin only; no third-party scripts; CSP kept strict (`script-src 'self'`, no `unsafe-eval`) |
| **R**epudiation | N | No privileged actions added | Not applicable |
| **I**nformation Disclosure | Y | Caching responses could expose business data on shared devices or serve stale live data as current (AC-8) | `ngsw-config.json` has no `dataGroups`; API/auth responses never cached; no tokens, PII or business data in Cache Storage; no logging of install/update events with user data |
| **D**enial of Service | Y | Bad SW/cache could brick the app offline; endless update/reload loop | Update applied only on user action or next start (no auto reload loop); `registerWhenStable` registration; documented kill-switch path; cache size bounded to build output |
| **E**levation of Privilege | N | No role-specific behaviour; SW has no access beyond same-origin fetch | Notice/Install shown identically to all roles; SW scope kept to `/` |

### 6.1 Assets & Trust Boundaries
- Sensitive data in this feature: none new (app code only).
- Trust boundary crossings: browser to origin server for SW script, `ngsw.json`, manifest.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A05 (security misconfiguration: CSP, caching rules), A08 (software/data integrity: SW and cached assets), A02 (no sensitive data cached), A06 (new dependency `@angular/service-worker` must match Angular version, no known vulns).

## 7. Test Strategy
- Unit: `PwaUpdateService` (update ready sets signal; apply only on call; no reload without user action; SW-disabled no-op), `PwaInstallService` (event captured, prompt, appinstalled clears, unsupported browser), `PwaNoticeComponent` (shown/hidden, dismiss, keyboard, aria, does not block controls), `app.config` provides SW only when not dev.
- Config checks: unit/script test asserting `ngsw-config.json` contains no `dataGroups` and manifest has required fields (name, theme_color, display=standalone, 192/512 icons).
- Manual/E2E evidence (recorded in DoD): production build served over localhost, install offered, offline reopen loads every module route, sample sign-in works offline, open bill survives update notice, dev build has no SW (AC-1..AC-14).
- Negative: SW disabled in dev; live data requests not served from cache offline; update never auto-reloads with an open bill.
- Existing suites (`app.component.spec.ts`, routes spec, a11y/contrast checks) must still pass.

## 8. Observability
- Client console only in dev; no analytics. No structured server logs (no backend). No PII logged.

## 9. Risks & Trade-offs
- R1: Existing CSP (`font-src 'self'`) must hold; fonts must be self-hosted. Developer verifies and bundles fonts if any external reference exists.
- R2: App initializer awaits `permissionService.load()` / `restoreSession()`; confirm these work offline with mock data (useMockData) so offline open succeeds.
- R3: Update mid-sale: never use `activateUpdate` + `location.reload()` automatically; only on explicit click; next-start behaviour relies on SW default activation.
- R4: Icon art: derive from `favicon.svg` and design-system theme colour; confirm colour from `docs/design/ShopDesk-design-system.md`.

## 10. Out of Scope
- Offline business data (F-3.2), sync status (F-3.4), real auth (F-3.5), backend/hosting (F-3.3, F-3.6), screen changes, first-ever offline visit, native mobile app.

## 1. Summary
The repo is a standalone Angular app (`frontend-app/`) with no backend and no HTTP layer. Per the confirmed working decisions, the "API" is a service layer inside `frontend-app/` that talks to a simulated product server through an abstract `ProductSyncServer` boundary (so a real HTTP server can replace the mock later with no change to the service or its results). `PosProductSyncService.sync()` splits the product list into batches of 500 (min 1), runs batches strictly in sequence, in each batch sends the app's products plus app-only stock deltas and receives server values, then applies them (server wins on every field except stock; stock = server's resulting stock after the app's delta). It returns total products, batch count and per-batch status, stops on the first failed batch or an unreachable server naming succeeded and failed batches, is idempotent on re-run (per-product operation ids, deduped by the server), keeps no log, and is gated by POS role rules (FR-POS-12). No UI (S-2.10.10), no authentication (A42, S-2.10.11), no real server. The contract is documented in `docs/api-docs/`.

## 4. Data Model & Migrations
- No database, no migrations. Product list stays in the existing in-memory `ProductDataService`; the mock server and sync-state store are in-memory and session-only. Rollback: not applicable (remove files and the DI binding).
- Idempotency design: for each product the app tracks `lastSyncedStock` and `opSeq`. Stock delta = current stock minus `lastSyncedStock`. Operation id = `{matchKey}:{opSeq}`. The server applies a delta at most once per operation id and replays the stored result on a repeat. The app advances `lastSyncedStock`/`opSeq` only after a confirmed batch, so a failed or re-run batch re-sends the same operation id and is never applied twice (AC-13). A sale made mid-sync after a batch is built shows up as a new delta next run.
- Only completed batches are saved to the app product list (AC-9); an unreachable server changes nothing (AC-10). If the sync fails to save a batch locally after the server confirmed it, the batch is reported failed and the unchanged baseline guarantees a safe re-send.

## 5. API Contract (draft — finalised in API_DOC)
Internal service operations (no HTTP route exists in this app); the `ProductSyncServer` boundary mirrors what a real REST call would be.

| Operation | Purpose | AuthZ |
|---|---|---|
| `PosProductSyncService.sync(onProgress?)` | Run whole-list two-way sync in batches of 500; returns total products, batch count, per-batch status, or a clear failure | `canWrite(POS)` (Admin, Manager, Cashier, Pharmacist per FR-POS-12), re-checked inside the service |
| `ProductSyncServer.syncBatch(request)` | Send one batch of up to 500 records with stock deltas and operation ids; receive server values and resulting stock | None (dev only, A42; production auth is S-2.10.11) |

Contract is fully detailed in `docs/api-docs/2.10.9_UPDATE_PRODUCTS_SYNC_API_API_DOC.md`.

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend yet, mock server, unauthenticated by decision (A42). Client gating is UX-level; controls are written as a real server/service would enforce them. Sensitive data: cost and selling prices, stock levels (no customer or patient data).

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | Caller runs the sync without being a POS user; server call has no authentication (A42); actor not tied to a real session. | Service re-checks live session via `PosWriteGuard` (`canWrite(POS)`) on every call, never trusts a caller-supplied user; the no-auth server boundary is isolated behind `ProductSyncServer` and documented as DEV ONLY with S-2.10.11 as a release blocker; real-server binding stays `notConfigured` outside mock mode, so unauthenticated mode cannot reach production by default. |
| **T**ampering (integrity) | Y | Malformed or hostile server reply (negative/NaN price or stock, duplicate or unknown keys, huge strings) corrupts products; stock double-applied on retry; stock overwritten and a sale lost; partial batch applied. | `product-sync-validation.util.ts` validates every response before any write (finite, non-negative, integer cents, length caps, count match, no duplicates); operation-id idempotency with server dedupe and baseline advanced only after confirmation (AC-13); delta computed before overwrite so sales are pushed first (AC-7); per-batch atomic save; stop on first failure (AC-9). |
| **R**epudiation | Partially (N for audit trail) | Who ran the sync is not recorded. | Intentionally no log or audit trail (A44, AC-14); only the returned result for that run exists. Actor read from session for the guard only. Flagged to user in A44. |
| **I**nformation Disclosure | Y | Cost price, selling price and stock leak through error messages, `console.*`, storage or the result object; failure message echoes server internals. | Messages are fixed, human-written strings naming batch numbers and counts only (no product names, prices or raw server errors); no `console.*`, no `localStorage`/`sessionStorage`, no URL or route state; result carries counts and statuses, not product data; mock seed is fictional. |
| **D**enial of Service | Y (low) | Very large list or repeated clicks run overlapping syncs; huge server reply; endless server calls. | Single-flight busy guard (`BUSY_MESSAGE`); batch size fixed at 500; max records per response checked equals request; sequential, no retry loops (A38); max total product cap in the util to refuse absurd inputs with a clear message. |
| **E**levation of Privilege | Y | User without POS access (e.g. View-only, no module access) triggers a write-style sync; client-side hiding is bypassed by calling the service. | Role check inside `PosProductSyncService` (not only in templates) via `canWrite(POS)`; denied returns a permission message with nothing changed (AC-12); no admin-only bypass path; mock-failure test hooks are not reachable from the production binding. |

## 7. Test Strategy
- Utils at band edges: batching 0 (empty), 1, 389, 500, 501, 1200 (500/500/200); merge (server wins on each field; app-only and server-only products; stock = server resulting stock); delta calc; validation (NaN, negative, fractional cents, duplicate key, unknown key, count mismatch, oversized string).
- Server mock: applies a delta once per operation id; repeat id replays; unreachable and batch-fail hooks.
- Service: AC-1 summary; AC-5 progress callback order (completed x of y); AC-7 sale not lost; AC-9 stop at failed batch, earlier batches stay applied, message names succeeded and failed batches; AC-10 unreachable changes nothing; AC-11 empty message and no batches; AC-12 each allowed role passes, View-only/no-access/unauthenticated refused; AC-13 re-run after failure and after full success never double-applies; AC-14 no history retained (no state beyond baseline store); busy double-submit refused.
- Negative tests MUST cover: unauthenticated, no POS access, wrong role, invalid/malformed server data, oversized data, unreachable server, failed batch.
- Per project rule, agents do not auto-run the suite; the user runs `npm test` and the build.

## 9. Risks & Trade-offs
- R1: Not a real HTTP API; real server (OQ41-1) unknown. Mitigation: `ProductSyncServer` boundary and API doc contract so a real client replaces the mock only.
- R2: No authentication (A42). Mitigation: dev only, S-2.10.11 is a release blocker, real binding unconfigured.
- R3: Baseline stock tracking is session-only, so a refresh loses the "already sent" record. Accepted with all other in-memory data in this app; the server's operation-id dedupe plus a conservative first-run baseline (current stock equals last known server stock for seeded data) avoids double-apply. Flag to user.
- R4: Match key is `barcode`, falling back to `sku`; duplicate or blank keys in the app are reported as a batch-level failure rather than guessed.
- R5: A44 (no log) removes post-run diagnosis. Accepted, flagged in story.

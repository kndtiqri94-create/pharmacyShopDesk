### Security Findings (OWASP Top 10 2021)
No Critical or High findings. Informational and Medium/Low items (none blocking):

1. **Severity:** Medium — **OWASP:** A04 (also touches A01) — **[FE]** `frontend-app/src/app/core/services/user-admin.service.ts:112-116`, `core/services/role-admin.service.ts:20-24`, `features/modules/users/edit-roles-panel/edit-roles-panel.component.html:24-45`  
   **Vulnerability:** Create user, change role, disable and save-permissions are authorised by `canWrite(ModuleKey.USERS)`, not by role Admin. Story section 5 says "Only Admin may create, change or disable users and change what each role can do", but AC-44 lets Admin set any non-Admin cell to Full, including the Users row. If Admin ever grants Manager Full on Users, that Manager can create a new Admin user with a temporary password they chose, edit the permission table, and disable or demote other Admins. Own-role change and self-disable are blocked, but this is still an escalation path. It requires a deliberate Admin action, so it is a design gap, not an exploitable bug.  
   **Remediation (recommended, not blocking):** Either keep the Users row (and ideally Settings) non-editable for non-Admin roles in Edit roles, or reject in `UserAdminService` any assignment of the Admin role, and any change to an Admin user, unless the acting user is Admin. Raise with Shiham/Thilina if the story text should be clarified.

2. **Severity:** Low — **OWASP:** A02 — **[FE]** `core/services/auth/session-credential-store.service.ts:4-28`  
   **Vulnerability:** Temporary passwords and Quick PINs are held as plaintext strings in an in-memory `Map` for the page lifetime. This matches Plan section 6 and the existing plaintext `MOCK_CREDENTIALS`, there is no read-back getter, nothing reaches storage or logs, and the store is only consulted when `MOCK_AUTH_ENABLED` (`auth.service.ts:52-55`). Residual risk is limited to a memory dump of a sample app with fictional data.  
   **Remediation:** None required now. When real authentication replaces mock auth, this store must be deleted, not ported.

3. **Severity:** Low — **OWASP:** A04 — **[FE]** `core/services/user-admin.service.ts:44-85`  
   **Vulnerability:** `createUser` has no service-level re-entrancy guard, unlike `SupplierPaymentService.busy`. The UI guards it (`add-user-panel.component.ts:84-85` sets `saving` synchronously) and the username uniqueness check rejects a duplicate. No exploit found.  
   **Remediation:** Optional: add the same `busy` flag for symmetry.

### Non-blocking Suggestions
1. **Users-row delegation (Medium, A01/A04).** See Security Finding 1. Restrict who can assign or alter Admin, or lock the Users row for non-Admin roles.
2. **Checkbox vs Toggle for "Change password at first sign-in".** `docs/design/ShopDesk-design-system.md` (Users & roles) says "toggle", and F-2.2 `product-form.component.html:264-271` already uses `app-toggle` for two flags inside a Save form, so the developer's "Toggle is instant-apply only" reasoning is inconsistent with the codebase. AC-38 only says "the option", so the AC is met. Prefer `app-toggle` for design fidelity and consistency, or get Thilina or Shiham to confirm the checkbox.
3. **Stale server error in Record payment dialog.** `record-payment-dialog.component.ts:48-53` returns `serverError` first, and `onInput` (line 55-58) does not clear it, so after a server-side rejection the old message stays while the user edits the amount until they submit again. Clear it on input (emit an event or clear in the parent).
4. **Mixed money formats for the same figure.** Supplier panel, list and PO side card use two decimals (`Rs. 11,600.00`); the Suppliers subtitle and the GRN "Unpaid to suppliers" tile use `formatRupees` (whole rupees unless there are paise). Values agree, formats differ. Consider one format for supplier-level figures.
5. **Plan drift.** Plan section 6 and `user-validation` Plan text say password max 128; code and DoD say 100. Add one line to the Plan or Completion Notes so future readers see the decision (already in DoD Deviations).
6. **`SessionCredentialStore` extras.** `pin` and `mustChangePassword` are stored but never read. This is accepted by OQ4, but delete them with the store when real auth lands.
7. **Service re-entrancy.** Add a `busy` guard to `UserAdminService.createUser` for symmetry with `SupplierPaymentService` (Security Finding 3).
8. **Team Lead housekeeping (DoD.30).** Story `Status:` is still `Ready`; Sanjeewa should set it per the pipeline after this verdict.
9. **Test evidence.** DoD.19 (814 of 814) and DoD.20 lint/format/build/contrast results are the developer's reports. I did not re-run them per FRONTEND_STANDARDS "Running tests". The user should run `npm test`, `npm run lint` and `npm run build:prod` before merge.

#### Opinions on the DoD "Deviations" section
1. **Seed data changes (GRN-0205/0206 added, stored `outstandingCents` removed, 7 F-2.3 specs updated): ACCEPT.** Plan 3.4 explicitly required removing the stored duplicate and a supplier with several unpaid GRNs of different dates. I checked the diff: spec changes are count, amount and ordering updates only (GRN totals 5 to 7, tiles Rs. 11,220 to Rs. 20,520 and Rs. 6,100 to Rs. 14,400, Lanka Pharma Rs. 3,300 to Rs. 11,600), and the old `toBeTrue()` and fixed-total assertions were replaced by derived-from-GRN assertions plus new seed-coverage checks. No behavioural assertion was weakened. The `app-shell` placeholder test moving from Suppliers to Settings is necessary now that Suppliers is a real screen.
2. **New PO supplier side card now two decimals (3 spec strings): ACCEPT.** Needed so AC-10 (`Rs. 0.00`) and AC-17 (same figure everywhere) read identically, and the design doc shows `Rs. 18,900.00`. The change is minimal (`formatRupeesExact` swap). See Suggestion 4 on the remaining format mix.
3. **Password limit 8 to 100, not 128: ACCEPT.** Correct call. Sign-in rejects input over 100 (`SIGN_IN_MAX_INPUT_LENGTH`), so a 101 to 128 character password could never be used. The story only sets the minimum. Record it in the Plan for traceability.
4. **Checkbox instead of Toggle for "Change password at first sign-in": DO NOT FULLY ACCEPT, non-blocking.** The design doc names a toggle, and F-2.2's product form uses `app-toggle` inside a Save form, so the "instant-apply only" rationale does not hold in this codebase. The AC says "the option", so it passes. Recommend switching to `app-toggle` or getting product sign-off; no re-review needed for either.
5. **Side panels do not close on backdrop click: ACCEPT, with a note.** The FRONTEND_STANDARDS modal rule says backdrop click and Escape should share `close()`, but that section describes the `lb-modal` pattern of a different app (class names and reference modal do not exist in this repo, and ShopDesk has its own `sd-` design system). Not closing form panels on an accidental click avoids losing typed data, and native `<dialog>` + `showModal()` still gives Escape, focus trap and focus return (`dialog.util.ts`, `side-panel.component.ts:39-42`). The lint reason cited is real, but a `click` handler on the dialog with an `event.target === dialog` check plus the existing Escape path would also satisfy it, so this is a UX call. The confirm dialogs (Disable user, Record payment) could safely close on backdrop click if the team wants to align with the standard later.

Other deviations (6 to 13) are consistent with the Plan or reasonable: R5 own-role change rejection (PASS, no AC conflict), R6 Disabled marker on Employees and excluded from Can log in (PASS, consistent), disabled sign-in reason after a correct password only (good security call), Admin and Manager row-action sets (PASS, matches AC-31).

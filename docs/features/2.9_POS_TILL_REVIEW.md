## Iteration 1

### Verdict
**CHANGES_REQUESTED**

### Summary
Reviewed the full frontend-only change set (about 100 new files and about 60 modified files under `frontend-app/src/`, matching story 9.5 and `git status`). Backend standards are N/A. The implementation is strong. It follows the payroll and settings exemplars: standalone components with signals, pure utils with specs, one model per file, and every component in its own folder with a spec. The security-critical paths hold up. The approval service re-reads the user and requires an ACTIVE ADMIN. Approvals are frozen, single-use tokens bound to scope, item and value. The password is read once from the DOM, cleared before the check and on every close path, and never stored. `verifyCredentials` does not touch the session. The sale build re-reads fresh products, re-prices, re-validates, allocates FEFO and then writes stock (`saveAll`, all-or-nothing) and the sale in one synchronous chain. `canWrite(POS)` is re-checked in every service. The maximum has no override. Key handlers live only while the till component is alive. A grep for `console`, `innerHTML`, `bypassSecurityTrust`, storage, `document.write` and `eval` over the POS code found nothing. One blocking defect remains, an access-control and session issue on sign-out (finding 1). Several developer deviations need a user decision (see Non-blocking Suggestions and the AC table). The test suite was not run (project rule); specs were judged by reading and look meaningful, with negative cases covered.

### Blocking Findings
1. **[FE]** `frontend-app/src/app/features/modules/pos/pos-leave.guard.ts:4`, `pos.component.ts:134-140` and `core/services/auth/auth.service.ts:81-85` — *Rule violated:* Plan §6 (Elevation / Information Disclosure: signed-out users must not keep access), OWASP A01/A07 (logout must end access), Story AC-24 intent (guard is for losing an unsaved bill, not for blocking sign-out).
   **Problem:** `signOut()` clears the user signal first and then navigates to `/sign-in`. The `canDeactivate` leave guard intercepts that navigation when the bill has lines and shows "Leave the till?". If the cashier chooses "Stay on the till", they remain on `/pos` while signed out. Products, stock levels, held bills (customer names and totals) and the unsaved bill stay on screen. `redirectWhenAccessLost` returns early when not signed in, so nothing else redirects. A walk-up user sees a signed-out till. The `PosService` singleton is not reset until the component is destroyed.
   **Required change:** Do not let the leave guard block sign-out or loss of session. Return `true` from `confirmLeave()` when `!authService.isSignedIn()`, and clear the bill. Alternatively have `signOut` bypass the guard. Add a spec: signing out with an unsaved bill leaves the till, shows no prompt and clears the bill.

### Security Findings (OWASP Top 10 2021)
1. **Severity:** Medium — **OWASP:** A01 / A07 — **[FE]** `pos-leave.guard.ts:4`, `auth.service.ts:81`
   **Vulnerability:** Sign-out can be cancelled by the unsaved-bill prompt, leaving till data visible to a signed-out person at a shared counter (see Blocking 1).
   **Remediation:** As Blocking 1. This is echoed there because the till is a shared-terminal screen.
2. **Severity:** Low — **OWASP:** A07 — **[FE]** `auth.service.ts:70-79`
   **Vulnerability:** `verifyCredentials` resets the shared `consecutiveFailures` counter on any valid pair, including a valid non-Admin. A Cashier who knows their own password can alternate a valid attempt with guesses at an Admin password and never reach the throttle threshold. The context is a session-only mock, so impact is low.
   **Remediation:** Keep a separate failure counter for approval attempts, or reset it only when the matched user is an active Admin. Non-blocking.
3. **Severity:** Low — **OWASP:** A08 — **[FE]** `core/utils/pos-discount.util.ts:105-124`, `pos-sale-build.util.ts:174-193`
   **Vulnerability:** At save, approvals are verified structurally (scope, item, percent), not by token. The developer documented this (9.4 item 6). It is acceptable for a mock store, but it must be enforced server-side when a backend exists.
   **Remediation:** Add a note to the Phase B or backend backlog. Non-blocking.

No Critical or High findings.

### Non-blocking Suggestions
1. **User decision (AC-13/AC-14):** In mock mode the clock is fixed at 2026-09-21 and `SALES_SEED` has a non-zero row for that day. Today's sales is therefore seed plus saved sales, so it never shows zero and does not equal "the sum of saved sales". This follows Plan §4 but contradicts the literal AC wording. The user should confirm, or the seed's "today" row should be dropped or reduced to zero.
2. **User decision (AC-10/AC-31):** An invoice number is reserved when a bill starts, so abandoned bills leave gaps. Numbers are unique and rising, but "sequential" may mean gapless for invoices. Please confirm that gaps are acceptable.
3. **User decision (deviation 13):** FEFO is always used for sales. The Settings switch "Sell the earliest-expiring batch first" is ignored by the POS and becomes misleading. Either honour the switch or relabel it.
4. **Accepted deviations:** AC-23 (the first allowed page when there is no Dashboard), AC-24 (Refresh reloads till data and does not reload the browser, with a route guard and `beforeunload`), AC-72 (auto-hold, which the AC allows), bill date not in the future, and No. of Items counting lines are acceptable as documented.
5. `getDailySales` only adjusts seed dates, so a sale on a day outside the seed range would not appear in the chart. This is fine today because the mock clock equals the seed end date.
6. The sidebar-hidden state is set after `open()` resolves, so the sidebar may flash briefly. Consider setting it earlier.
7. `pos-bill-header` captures `today` at construction, so it goes stale past midnight. This is trivial.
8. There are no specs for `pos-leave.guard.ts` or `pos.routes.ts`. Add them with the Blocking 1 fix.
9. Browser checks (fullscreen with Esc/F11, `:has()` print stylesheet, widths, screen reader, 52px on touch) are unverified. Do a manual pass before release.

## Iteration 2

### Verdict
**APPROVED**

### Summary
Re-reviewed the fixes for iteration 1. Blocking 1 is resolved. `confirmLeave()` in `pos.component.ts:136-140` now returns `true` and calls `posService.close()` when `!authService.isSignedIn()`. `signOut()` clears the user signal before it navigates, so the leave guard no longer holds a signed-out person on the till, and the unsaved bill is cleared. The spec "leaves without a prompt and clears the bill once the user has signed out" (`pos.component.spec.ts:291-300`) covers it. New specs `pos-leave.guard.spec.ts` (allows and blocks) and `pos.routes.spec.ts` (lazy route, POS module key, `canDeactivate` is `[posLeaveGuard]`) close Suggestion 8. Security Finding 2 (Low) is also resolved. `verifyCredentials` now uses a separate `approvalFailures` counter (`auth.service.ts:29,72-85`). A failed match increments it and throttles. Only a valid, ACTIVE Admin pair resets it, so a Cashier's valid password no longer clears the Admin-guessing throttle. `consecutiveFailures` for sign-in is untouched and the two counters do not interact. `signIn` and the session remain unchanged by `verifyCredentials`. No new issues were found. The test suite was not run (project rule).

### Regression check (new security pass)
- Clearing the bill on sign-out: `close()` releases the pristine invoice number, resets the bill and flags the till as not started. It is only reached when signed out, and `ngOnDestroy` calls it again, which is idempotent. A bill of a signed-out cashier is discarded, which is the intended behaviour. No sale is written.
- Throttle: a valid non-Admin pair neither increments nor resets the counter. This is correct, because the approval service rejects non-Admins itself. A wrong-password guess against an Admin account increments the counter.
- Note (Low, non-blocking): a failed approval throttle delays only after the threshold, and the counter is per service instance (session). That is acceptable for the mock store.
- Held bills stay in the `PosService` signal after close. They are reloaded on the next open and are not displayed while signed out. Non-blocking.

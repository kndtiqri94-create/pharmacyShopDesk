## 1. Summary
A new `backend-app/` Node service (Fastify 5, Prisma 7, PostgreSQL, TypeScript, zod) that stores every ShopDesk module's data, validates every write with rules mirroring the frontend, keeps stock as an append-only movement ledger, and offers per-record REST endpoints plus batch sync (`push` / `pull`) and the S-2.10.9 Update Products batch contract. Working stack is the user's direction C4 (Fastify, Prisma, PostgreSQL) while PRD OQ42 stays open.

## 2. Exemplars / Reference Pattern
- Backend: no TypeScript service exists yet in this repo, and `docs/development-standards/BACKEND_STANDARDS.md` targets Azure Functions + SQL Server (OQ42 gap, C5), so there is no applicable exemplar. Applied from the standards where they still make sense: layered separation (routes → services → store), DTO validation at the edge, readonly collaborators, low cognitive complexity, no secrets in code, Prisma migration SQL committed and not auto-applied (`backend.prisma` tag; policy copied to `backend-app/prisma/MIGRATION_POLICY.md`).

- Business-rule exemplars ported: `utils/pos-due.util.ts` (dues), `utils/pos-cash-ledger.util.ts` (cash book), `utils/product-validation.util.ts` and `bank-account-validation.util.ts` (field limits, uniqueness).

## 4. Data Model & Migrations
- **`entities`** (one table, PK `collection + id`): `unique_key` (case-folded natural key, unique per collection; SKU, bank + account no, invoice/GRN/PO/return/receipt/hold/quotation numbers, user name, employee code, attendance/entitlement/payroll pairs), `date_key` (business date for range reads), `data` JSONB (the DTO exactly as the frontend model), `ord` (creation order), `seq` (last change), `deleted` tombstone (frees the unique key). `collection` equals the Dexie table name so devices map one-to-one.
- **`stock_movements`**: typed append-only ledger: `id` (device-generated, PK; duplicate insert skipped), `seq` unique, `product_id`, `batch_id` ('' = product level), `type`, `qty_delta`, `ref_id`, `user_id`, `device_code`, `occurred_at`.
- **`processed_changes`**: `change_id` PK, outcome; makes a resent sync change a no-op.
- **`change_seq`** sequence: one cursor space for entity changes and movements.
- Stock rule (mirrors the app): stored product/batch quantity is the BASE; current stock = base + sum(movements). REST product saves carry current figures and the difference becomes ADJUSTMENT movements (a new product's opening stock is one movement, as in the app). Sync product rows carry the device's BASE; existing server base is never overwritten.
- Trade-off recorded: JSONB documents with indexed natural keys instead of fully normalised tables. It keeps one validated contract per collection shared with the Dexie schema and makes sync generic. Normalising hot reporting paths (sales lines, batches) is a later, additive migration.
- Migration SQL generated with `prisma migrate diff` and committed; not applied to any shared database. Rollback: drop the three tables and the sequence (baseline only).

## 6. Threat Model (STRIDE-lite — MANDATORY)
| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing | Y | Anyone on the network calling the API | Bearer token required on every `/api/v1` route; constant-time compare of SHA-256 digests; production refuses to start without a 32+ char token, with `ALLOW_INSECURE_DEV`, or with `STORE=memory`. Stop-gap: real auth is F-3.5 (release blocker FR-DEP-4). |
| **T**ampering | Y | Altered or replayed requests; invalid or inconsistent data; double-posting | zod validation on every body, query and param (limits mirror UI); sale/return arithmetic checks; immutable posted records; unique keys enforced in the database; device-id idempotency for movements and sync changes; HTTPS only in production. |
| **R**epudiation | Y | Who changed what | Request id on every log line; sync outcomes persisted per change id and device code; movements keep device code, user id and device time. Full audit trail of user actions is accepted as out of scope (A44) until F-3.5 identities exist. |
| **I**nformation Disclosure | Y | Sale, pay and personal data leaking via errors, logs, CORS | Uniform error body with no internals; unexpected errors logged server-side only; log redaction of `authorization` and `cookie`; request bodies never logged; helmet headers; CORS allow-list only; user records carry no password field (schema strips it); config errors never echo secrets. |
| **D**enial of Service | Y | Flooding, huge bodies, huge pages | Rate limit 600/min per client; 2 MB body limit; sync push max 500 changes, movements max 500, pull limit max 500, page size max 500, array caps in schemas; DB transaction timeout 15 s. |
| **E**levation of Privilege | Y | A low-role user using the API directly | Role matrix cannot be enforced yet (no identities); the shared token grants full access and is documented as such. Mitigation: F-3.5 enforces Full/View/No on the server; the API is not exposed publicly before then. |

## 7. Test Strategy
- 53 automated tests; the same suites run on the in-memory store (`npm test`) and on a real throwaway PostgreSQL through Prisma (`npm run test:pg`, applies the committed migration).
- Coverage by story: foundation (config, health, errors, auth, HTTPS, CORS, body limits), master data, stock ledger and GRN, POS (idempotent sale, negative stock, immutability, arithmetic, dues, cash book, counter lock), HR, sync (resend, two devices, server wins, tombstones, cursor paging, rejections, flagged clash), Update Products batch.

## 9. Risks & Trade-offs (and recorded assumptions)
- A1 (OQ42): Fastify + Prisma + PostgreSQL is used as the working stack per user direction C4. `BACKEND_STANDARDS.md` and the backend templates are unchanged and still describe Azure Functions + SQL Server; the standards update is left to the owner decision.
- A2 (OQ47): a sync push never rejects a sale for stock reasons; stock may go negative and is listed at `GET /stock/negative`. Only malformed/unusable changes are rejected. Sale invoice-number clashes are kept and flagged (`unique_key_clash_flagged`) instead of rejected.
- A3 (OQ48): the S-2.10.9 contract is kept verbatim as `POST /api/v1/products/sync-batch` so the app's `ProductSyncServer` can be bound to it with no change; operation ids are applied once through the ledger (`opsync:{operationId}` movement id plus an internal `_productSyncOps` record); server values win; stock floors at zero. Manual Update Products remains as a full refresh; automatic sync (F-3.4) uses push/pull. Deprecating it is a Product Owner decision.
- A4: Conflict rule: devices send `baseSeq` (server `seq` last seen). Server newer than `baseSeq`, or `baseSeq` absent for an existing record, means server wins (reported `duplicate`/`server_wins`). Posted (immutable) records never change.
- A5: Single shared-token auth until F-3.5.
- A6: Cash book `time` is the UTC clock time from the stored timestamp; the app formats in local time.
- R1: JSONB model lacks relational integrity (e.g. a sale referencing a missing product is accepted so that devices can push in any order). Mitigation: referential checks can be added as non-blocking flags later.
- R2: Concurrent product edits are serialised by an advisory lock per product (PostgreSQL) so ledger sums stay correct.
- R3 (closed): the Prisma 6 CLI toolchain audit findings were cleared by upgrading to Prisma 7.10.1 (driver adapter, `prisma.config.ts`) and overriding the transitive `effect` to a patched version.

## 1. Summary
Add an outbox (a Dexie table written in the same IndexedDB transaction as every local change), a connectivity service, and a sync engine that pushes the outbox in order in batches to `POST /api/v1/sync/push` and then pulls `GET /api/v1/sync/pull`, on reconnect and every 60 seconds while online and automatic sync is on (A46). The pretend `SyncDataService` status becomes derived from real queue and connection state; the sync pill gains a Needs attention state; Settings, Backup & sync gets real last-sync time, pending count, Sync now, Back up now (A50), a working automatic-sync toggle, a Needs attention list (read-only), a data-loss note, and a sign-out confirmation when anything is unsent. The manual Update Products refresh is bound to the real `POST /api/v1/products/sync-batch` and flushes the outbox first (OQ48). Frontend-only; backend (F-3.3) and hosting (F-3.6) are unchanged.

### 1.1 Decisions fixed in this plan (user confirmed A46, Needs attention read-only, OQ47/OQ48 as risk)
- **D1 Atomic enqueue (AC-1).** The existing `db.afterWrite(entity, id, op)` seam runs AFTER the write and outside any transaction, so it cannot satisfy AC-1. Replace it with an in-transaction enqueue: `LocalCollection` writes (and every direct-table writer: `writeDocument`, product service, stock ledger, multi-table sale/GRN/return transactions) run inside `db.transaction('rw', <tables>, db.outbox)` and append the outbox row in that same transaction. A guard test fails if any local write path touches a synced table without an outbox row.
- **D2 Snapshot payload.** Each outbox row stores a structured-clone snapshot of the record at write time (for `products`: the stored BASE row; for stock: the movement), so replay order equals user order (AC-3) even if the record changes again before sending. Accepted: PII duplicated at rest for the short time a change is waiting (see section 6).
- **D3 Order and back-off.** Outbox is FIFO by auto-increment `seq`. Because order must be preserved, a transient failure at the head holds the whole queue and backs off globally (1s doubling to 5 min cap, plus jitter), reset on first success or on reconnect. Rejected rows leave the queue (status `rejected`) and never block later rows.
- **D4 Push then pull.** Pull runs only after the push drains (accepted, duplicate or rejected for every row). Pulled records whose id still has a waiting outbox row are skipped (not overwritten); everything else is server-wins (AC-9, AC-26). Pulled `delete` never removes a `sales` or `saleReturns` row (AC-11).
- **D5 Stock only via movements.** Pulled movements are inserted by id if absent through the ledger append path (local `seq` assigned locally; server `seq` ignored); pulled `products` rows replace master fields but never stock base. No pull code writes a stock total (AC-10).
- **D6 Pill precedence.** SYNCING > NEEDS_ATTENTION (count of refused) > OFFLINE (count waiting) > ONLINE. Online with changes waiting while auto-sync is off or between runs shows "Online - N waiting to send" so the pill never claims "all saved" when it is not (AC-14/15; flagged as a small assumption).
- **D7 One engine per device.** `navigator.locks.request('shopdesk-sync', { ifAvailable: true })` so only one tab runs an exchange; fallback to a Dexie meta lease with expiry where Web Locks are missing. Duplicate sends from a second tab are still safe (server idempotent, AC-8). Status is read from Dexie `liveQuery` so every tab shows the same counts.
- **D8 Connectivity.** `ConnectivityService` = `navigator.onLine` + `online`/`offline` events, downgraded to offline when a request fails at network level and restored on the next success; the 60 s timer and the `online` event both trigger a run. Never blocks UI (AC-5).
- **D9 Refused reasons.** Server `reason`/`message` map through a fixed code-to-plain-words table (`sync-reason-text.ts`); unknown codes show a generic sentence; raw server messages and field paths are not displayed or logged (story section 5).
- **D10 Transport.** Angular `HttpClient` (`provideHttpClient(withFetch())`), base URL `environment.apiBaseUrl`, HTTPS required in production builds. Bearer token interceptor attaches `environment.apiAuthToken` ONLY to requests whose URL starts with `apiBaseUrl`. 401 is non-retryable: queue stays, status shows "cannot reach the central record (not authorised)" in Settings; no row is rejected on 401. 429/5xx/network are transient (D3). The stop-gap token being visible in a browser bundle is an accepted residual risk until F-3.5 (section 6, R3).

## 4. Data Model & Migrations
- Dexie `version(2)`: new `outbox` table (`++seq` order key, unique `changeId` = `crypto.randomUUID()` per change, `status` index for counts, `entity`). v1 stores untouched; upgrade test proves v1 rows survive and that pre-existing unsent v1 data is NOT back-filled into the outbox (starting data is seed/sample; real device data first exists after this release, OQ43).
- `meta` keys added: `autoSyncEnabled` (default true), `lastSyncAt`, `pullCursor` (default 0), `syncLease` (fallback lock).
- Outbox row ids: `changeId` is the server idempotency key and is generated once at enqueue; it is never regenerated on retry.
- Rejected rows are retained (status `rejected`) until a future workstream adds handling; no automatic purge. Accepted/duplicate rows are deleted in the same transaction that records `lastSyncAt`/cursor progress where applicable.
- Rollback: switch `dataSource` back to `mock`; v2 table is additive and ignored by v1 code (Dexie opens higher version; downgrade is not supported, noted in DoD).

## 6. Threat Model (STRIDE-lite — MANDATORY)
| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing | Y | Stop-gap shared bearer token is the only server auth until F-3.5; token ships in the browser bundle; anyone with it can push as any device; `deviceCode` is self-declared | Token never committed (placeholder in repo, injected at build); attached only to `apiBaseUrl` by interceptor (no leakage to other origins); HTTPS-only in production (`https_required` honoured); token and request bodies never logged; residual risk R3 documented for PO until F-3.5; no new sign-in bypass |
| **T**ampering | Y | Outbox/DB editable via DevTools; replay/duplicate sends; reorder; partial batch; local rows overwritten by pull; remote delete of completed sales | Server validates every change (schemas, business rules) and is idempotent per `changeId`; `changeId` stable across retries; FIFO by `seq`; atomic enqueue (D1) with guard test; pull never overwrites ids with waiting changes (D4); pulled deletes never remove sales/returns (AC-11); stock never overwritten, only movements by unique id (D5); batch size capped |
| **R**epudiation | Y (low) | Cannot tell who made a queued/refused change | Outbox rows keep `createdAt`, entity, id; records and movements already carry userId/deviceCode; refused list shows what/when/reason; no new audit UI |
| **I**nformation Disclosure | Y | Sales, dues, payroll, bank data queued in plain IndexedDB (duplicated in outbox snapshots) and sent over network; error/log leakage; Needs attention exposing more than the user may see; passwords | HTTPS only in prod; no PII or payloads in `console.*`, errors or telemetry (counts/codes only); refused list shows human text from fixed table (D9), never raw server messages or field paths; list/sign-out warning show counts and entity labels only, gated behind the existing signed-in shell; user records already strip passwords (3.2) and the guard test asserts no password/hash/token is ever enqueued; no data in localStorage; ngsw never caches API responses |
| **D**enial of Service | Y | Tight retry loop hammering server or battery; huge queue; unbounded pull; multi-tab stampede; UI blocked by sync | Exponential back-off with jitter and 5 min cap, honours 429; batch <= 100 per request (server cap 500); pull `limit` <= 500 loop with `hasMore`; single-engine lock (D7); engine work is async and never on the UI path; pill and Settings never block; quota error on enqueue surfaces a clear error (existing `QuotaExceededError` handling) and the originating write rolls back together with its outbox row |
| **E**levation of Privilege | Y (low) | Sync could re-apply data a user lacks permission to see/edit; Sync now/Back up now exposed to all roles; settings changes by wrong role | Engine acts only on rows already written by permitted local actions; pulled data goes into the same tables the role-gated services read; Sync now / Back up now / toggle follow the existing Settings module access (`module-write.guard` / `PermissionWriteDirective`), no new admin shortcuts; server per-role enforcement is F-3.5 (out of scope) |

### 6.1 Assets & Trust Boundaries
- Sensitive data: sales and items, customer dues, cash figures, payroll/employee/bank records, stop-gap API token.
- Trust boundaries: browser (IndexedDB, unencrypted, shared-PC risk, OQ44) to central API over the internet (new in this workstream); tab to tab on the same profile.

### 6.2 Pre-emptive OWASP mapping
- Likely in play: A01 (module access on sync actions), A02 (PII at rest/transit, HTTPS), A04 (insecure design: atomic enqueue, ordering, idempotency, merge rules), A05 (misconfiguration: environment token, CORS origins), A07 (stop-gap auth), A08 (data integrity: replay, server-wins, no stock overwrite), A09 (logging without PII). Reviewer still performs a full A01-A10 pass.

## 7. Test Strategy
- **Unit (Karma/Jasmine, fake-indexeddb):** outbox atomicity (writing a record and failing mid-transaction leaves neither row nor outbox row; AC-1); guard test that every synced entity write creates an outbox row; ordering and batching (AC-3); back-off sequence and reset (AC-4); transport error mapping incl. 401, 429, 5xx, network, 400; apply rules D4/D5 (skip waiting ids, server-wins, never delete sales/returns, movement dedupe by id); reason text mapping; engine single-run guard and lock fallback; status derivation and pill precedence (D6) for every state; Settings component states, toggle takes effect without Save, offline Sync now message, Back up now outcomes; sign-out confirm shown only when pending or rejected exist; Update Products flush-first ordering; v1 to v2 schema upgrade keeps data; interceptor attaches token only to `apiBaseUrl`.
- **Integration (Karma + mocked `HttpTestingController`) against the documented 3.3 payloads:** accepted, duplicate (all reasons), rejected (several codes), whole-batch resend, partial failure resume (AC-25).
- **End-to-end (S-3.4.5, REQUIRED real browser, not fake-backed):** Playwright (Chromium, built app via `ng build` served statically) against the real `backend-app` running with its in-memory store, using Playwright `context.setOffline()` and a second isolated browser context as the second device. Scenarios: (1) offline sale, reload, still there, then reconnect, exactly one sale and one stock reduction on the server (AC-24); (2) connection dropped mid-exchange (route abort after the push reaches the server but before the reply, then restore), no loss, no double apply (AC-25/AC-8); (3) two devices sell the same item, both converge, stock = start minus both (AC-10); (4) same product price edited on two devices, server value kept on both (AC-26). Lesson from the 3.2 review: fake-indexeddb alone is NOT acceptable for S-3.4.5. If Playwright browsers cannot be installed, the developer returns `BLOCKED: missing <tooling>` rather than downgrading.
- **Negative tests MUST cover:** 401 (no rejection, queue kept), 429/5xx back-off, malformed/oversized server response, rejected change appears in Needs attention and stops retrying, duplicate resend, pulled delete of a sale ignored, sign-out confirm declined, token not sent to a foreign URL, no password field enqueued, quota exceeded rolls back both rows.

## 8. Observability
- Console-free; use the existing no-PII event pattern (as `local-db.*` events in 3.2). Events (fields are counts/codes only): `sync.run.started` (trigger), `sync.run.finished` (pushed, rejected, pulled, ms), `sync.push.failed` (kind, attempt, nextDelayMs), `sync.pull.applied` (count, skipped), `sync.rejected` (reason code), `connectivity.changed` (online).
- Correlation: one `runId` per exchange kept in memory and sent as an `X-Request-Id` header if the server logs it (optional, header only).

## 9. Risks & Trade-offs
- R1: Retrofitting transactional enqueue touches every local write path; a missed path means a silently unsynced change. Mitigation: single synced-entity list + guard test; Code Reviewer maps each service to its enqueue evidence.
- R2: Global head-of-line back-off means one persistently failing transient row stalls everything. Mitigation: only transient failures stall; server rejections leave the queue; 401 shown as a separate state; revisit if OQ47 changes what the server refuses.
- R3: Stop-gap token in the browser bundle is extractable. Accepted until F-3.5; token must not be committed; flagged for PO and Code Reviewer.
- R4: Server-wins can discard a device's non-stock edit made while apart (AC-9/26 by design); skipping pull for ids with waiting changes narrows but does not remove this. Per story, no field-level merge.
- R5: Outbox snapshots duplicate PII at rest briefly; the 3.2 unencrypted-at-rest acceptance (OQ44) is extended.
- R6: Web Locks absent on some browsers; fallback lease may allow rare double-run; server idempotency makes it harmless.
- R7: OQ47 and OQ48 stay open and built to assumption (sales never refused for stock reasons; manual Update Products kept); if the user changes either, Needs attention volume and the refresh flow change.
- R8: E2E needs Playwright plus the backend running; adds CI weight. CI wiring for the release gate is deferred to F-3.6 (S-3.6.6); a local `npm run e2e` script is delivered here.
- R9: Pill precedence D6 (Online with N waiting) is a small interpretation of AC-14; flagged for confirmation at this gate.

## 10. Out of Scope
- Real sign-in, sessions, per-role server enforcement (F-3.5); hosting, TLS, DB backups, monitoring, CI workflow for e2e (F-3.6); editing/resending a refused change; field-level merge; device-to-device or multi-branch sync; encryption at rest; any screen other than the pill, Backup & sync section and the sign-out confirmation; any change in `backend-app/`.

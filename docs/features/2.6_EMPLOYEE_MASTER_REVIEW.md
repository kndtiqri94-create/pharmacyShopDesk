### Summary
Reviewed all frontend changes for F-2.6 (frontend-app only; backend and DevOps are N/A and confirmed absent): the employee model, enums and seed, the `employee-*` utils, `EmployeeAdminService`, `EmployeeExportService`, the Employee list and the Create/Edit/View form with its section children, the routes and `moduleWriteGuard.viewOnlyRedirect`, the Users & roles `employeeId` preselect, the shared DataTable/Pagination opt-in inputs, and the deletion of the Staff table. The code is of high quality and follows the F-2.4 users module pattern (utils with field-keyed errors and first-error focus, admin service that re-checks `canWrite` and reads fresh data, copies computed before save, in-flight guard, signals and standalone components). The Plan §6 threat model controls are all implemented and verifiable. No Critical/High security issues were found. One blocking finding remains. The mobile rule accepts 10-digit numbers starting with 0, which contradicts the user-confirmed AC-28. The error text still says "9 digits", so the code, message and AC disagree, and the story records no approval of the change. Everything else is non-blocking. Build, lint and 1181/1181 tests were run by the user; I ran `npm audit --omit=dev` myself (0 vulnerabilities), which closes DoD.21.

### Blocking Findings
> Every item blocks approval. Critical/High OWASP findings are also echoed here.

1. **[FE]** `frontend-app/src/app/core/utils/employee-validation.util.ts:184-189` (`isMobile`) and `:262-264` (error text) — *Rule violated:* Story AC-28 ("a Mobile number that is not nine digits ... rejected with a message stating what is expected, example 77XXXXXXX"); Story §3.1 valid values ("Mobile is nine digits"); Story §Open Items item (3), where the user asked the PO to confirm the nine-digit rule; Plan §3.3 ("mobile 9 digits after stripping spaces").  
   **Problem:** `isMobile` also accepts 10 digits when the first is `0`. The story has no PO or user approval for this deviation (Dev Agent Record §9.4 only lists it as a deviation). The wording of AC-28 is not met. The message "Enter a mobile number of 9 digits, like 77XXXXXXX" tells the user a number the validator accepts is wrong. The value is stored as typed (spaces stripped only), so `0771234567` and `771234567` are saved as two different formats in `Employee.phone`. That field feeds the keyword search, the list, the CSV/PDF export and Attendance, and the same person can no longer be matched by one search term.  
   **Required change:** Choose one.  
   (a) Remove the 10-digit branch so the rule is exactly nine digits, as in AC-28 and the plan, and update the spec.  
   (b) Get the PO/user to approve the wider rule. Then update AC-28 and §3.1 in the story via the BA/PO, make the error message state both accepted forms, and normalise the stored value to one form. For example, strip a leading `0` on save so every `phone` is nine digits, and add a spec for it.

### Security Findings (OWASP Top 10 2021)
> Full scan for A01–A10 + insecure-code patterns. Critical/High severity = blocking.

No Critical, High or Medium findings. Items checked and clean:
- A grep of the employees feature, `core/services/employee-*` and `core/utils/employee-*` (non-spec) finds no `innerHTML`, `bypassSecurityTrust*`, `console.*`, `localStorage`, `sessionStorage`, `eval`, `new Function` or `any`.
- CSV formula neutralisation is applied to every cell, including cells in the header row (`employee-export.util.ts:23,36-43`).
- PDF text is restricted to printable ASCII, with `\`, `(` and `)` escaped (`:81-86`), so user text cannot inject PDF operators.
- The export columns are whitelisted to the list columns (`:6-15,45-56`), so no pay fields are exported (AC-53).
- Object URLs are revoked in `finally` (`employee-export.service.ts:65-75`).
- The photo is validated by MIME, extension and size (`employee-image.util.ts:19-24`), and the result is re-checked against a data-URL prefix (`:26-41`). The validator re-checks the prefix again before save (`employee-validation.util.ts:209-211,412-414`).
- The `viewOnlyRedirect` pattern comes from static route data. Param values are passed as URL segments to `createUrlTree` (which encodes them), and an empty segment makes it fall back to access-denied (`module-write.guard.ts:8-30`). It is not an open redirect.
- The `/users?employeeId=` value is only used if it matches an unlinked employee and the user can edit (`users.component.ts:163-172`).

1. **Severity:** Low — **OWASP:** A04 — **[FE]** `employee-form.component.ts` (no `canDeactivate`; the Cancel prompt only)  
   **Vulnerability:** Browser back or a sidebar click discards unsaved edits without a prompt. Data-integrity nuisance only, with no confidentiality or privilege impact. Documented as a deviation, so not blocking.  
   **Remediation:** Optional: add a `canDeactivate` guard that reuses `isDraftDirty`.

### Non-blocking Suggestions
1. **Attendance excludes Inactive employees** (`core/utils/employee-list-filter.util.ts`, `buildAttendanceRows`). Accepted on merit. Inactive staff should not be marked present, and it is consistent with AC-8. Their history stays visible in the list. Keep it documented as a deviation.
2. **Shared DataTable `paginate` and Pagination `showSummary` opt-in inputs.** Accepted. Both default to the previous behaviour (`paginate = true`, `showSummary = true`), so there is no regression for existing consumers, and each input has spec coverage.
3. **`moduleWriteGuard.viewOnlyRedirect`.** Accepted. It is generic, data-driven, safe against empty params, and covered by an updated guard spec. This satisfies AC-57 and the Plan §3.4 intent.
4. **`as Employee` cast in `employee-admin.service.ts:139` (`newBase`).** The partial object is cast to `Employee`. Prefer building a fully typed base, or having `fromDraft` return the complete `Employee`, so the compiler catches a missed field.
5. **PDF replaces non-ASCII characters with `?`** (`employee-export.util.ts:81-86`). Names and addresses with non-ASCII characters lose them in the PDF only (the CSV is UTF-8 with a BOM). Acceptable for the in-house PDF, but mention it in the "sample only" notes.
6. **Unused exports.** `FULL_TIME`, `PART_TIME` and `EmployeeLogin` in `employee-list-filter.util.ts` are exported but used only inside the file. Consider un-exporting them.
7. **Manual browser checks** (widths 1440/1280/1024/768/360, keyboard walkthrough, light/dark contrast) are honestly recorded as not verified. This is non-blocking. The DoD template has no manual-browser boxes, and the Plan §7 items are recorded as pending. Run them before release.

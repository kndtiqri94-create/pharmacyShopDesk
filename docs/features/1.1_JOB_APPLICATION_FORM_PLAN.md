## 1. Summary
Build a standalone Angular candidate-facing screen that renders the single advertised role and an "Apply for this role" form (Full name, Email, CV file picker/drag-drop, optional Cover note with a 500-char counter), matching `docs/design/Job Application Page.dc.html`. The form enforces required-field + email-format validation with per-field and summary-banner errors, transitions through submitting → success ("Application sent" + "Start again") or failure (visible error + retry) states, and persists the submitted application to `localStorage` only (CV captured as file name/size metadata, never binary content). On reload, a previously successful submission on that device must restore the success state instead of a blank form. This is a frontend-only, no-auth, no-backend-call slice (PRD NG1/NG5) — F-1.2's backend persistence demo is a separate, non-integrated artifact and is out of scope here.

## 6. Threat Model (STRIDE-lite — MANDATORY)
> Address every letter below. Keep each row 1–2 lines. Reviewer validates these are implemented.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | N | No authentication/identity concept in this screen (PRD NG1); anyone with the URL can submit. | N/A — accepted by design; no session/identity to spoof. |
| **T**ampering (integrity) | Y | A candidate (or any script on the page) can directly edit the `localStorage` entry to fabricate a fake "submitted" state, or tamper with in-flight form data via devtools. | Treat `localStorage` as untrusted client state: on read, validate the stored JSON against an expected shape/schema (`schemaVersion`, required string/number fields) before rendering the success state; if the shape is invalid, fall back to a blank form rather than trusting it blindly. This is a demo, so full tamper-proofing is out of scope, but malformed data must not crash the app. |
| **R**epudiation | N | No audit trail or multi-party dispute concept for this demo (single anonymous candidate, single device, no admin view). | N/A. |
| **I**nformation Disclosure | Y | Candidate PII (full name, email, CV file name, cover note text) is persisted in browser `localStorage`, which is readable by any script/extension in the same origin and survives until manually cleared. | Store only the minimum needed fields (CV name/size only, never file bytes, per PRD Constraints); do not log form field values to the browser console in production builds; no field values are sent over the network in this phase (NG5) so there is no transmission-exposure surface to mitigate here. |
| **D**enial of Service | Y | Oversized CV files, extremely long cover notes, or a full/unavailable `localStorage` (quota exceeded, private-browsing restrictions) could break the UI. | Enforce the 500-character cap in the UI/validator (AC-12) and the CV accept/size constraints from FR-JOBAPP-1 (.pdf/.doc/.docx, up to 10MB) client-side before persistence; wrap all `localStorage` read/write calls in try/catch and route any failure (quota exceeded, storage disabled) through the same visible error/retry state as AC-9/AC-10 rather than letting it throw unhandled. |
| **E**levation of Privilege | N | No roles/permissions or privileged actions exist in this single anonymous-candidate screen. | N/A. |

### 6.1 Assets & Trust Boundaries
- Sensitive data in this feature: candidate full name, email address, CV file name/size (not file content), optional free-text cover note — all classified as low-sensitivity demo PII, stored client-side only.
- Trust boundary crossings: none in this phase — the browser tab/origin is the only trust boundary; there is no network call to a backend or third party (PRD NG5). The `localStorage` API itself is the only "external" boundary (shared with any other script running in the same origin).

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A03:2021 (Injection — cover note free text rendered back to the user must be output-encoded/sanitised, not inserted via unsafe HTML binding) and A04:2021 (Insecure Design — treating client-side `localStorage` as authoritative "submitted" state without integrity checking, mitigated above under Tampering). Reviewer will still do a full A01–A10 pass.

## 7. Test Strategy
- Unit tests: `job-application-storage.service.spec.ts` (save/read/clear, malformed-JSON fallback, quota-exceeded handling), `job-application-submit.service.spec.ts` (success path, forced-failure path, retry re-uses same in-memory data), each validator (`required`, `email-format`, `max-length-500`) as isolated `ValidatorFn` specs.
- Integration tests: N/A (no backend/API integration in this workstream).
- Frontend tests: `job-application-page.component.spec.ts` covering the state machine transitions (default → validating-blocked → submitting → success, and default → submitting → error → retry → success), and `job-application-form.component.spec.ts` covering per-field + summary-banner error rendering (AC-3, AC-4, AC-5), live char counter (AC-12), and reload-restore behaviour (AC-11, via a pre-seeded `localStorage` fixture in the spec).
- Negative tests MUST cover: submit attempted with each required field individually missing/invalid (AC-3, AC-4); malformed/corrupted `localStorage` payload on load (must not crash, falls back to blank form); simulated `localStorage` write failure (must show the visible error/retry state, not a silent failure or thrown exception); over-limit cover note input (must not exceed 500 chars) and oversized/wrong-type CV selection (must be rejected client-side per FR-JOBAPP-1 constraints).
- (No unauthenticated/wrong-tenant/wrong-role negative tests apply — this screen has no auth or tenancy concept, per PRD NG1.)

## 9. Risks & Trade-offs
- R1: OQ1 (submit-failure trigger mechanism) is not yet confirmed by the stakeholder — the User Story captures a labelled assumption (a built-in, demo-only failure-injection affordance) so this workstream is not blocked. Mitigation: implement the failure trigger behind the isolated `job-application-submit.service.ts` so swapping the trigger mechanism later does not touch UI/validation code or invalidate AC-9/AC-10 (which describe the outcome, not the trigger).
- R2: No pre-existing `frontend-app` scaffold exists in this repo yet — Hasika must scaffold a fresh Angular app for this workstream. Mitigation: scaffold with the latest stable Angular CLI per `GETTING_STARTED.md` guidance, applying only the coding-standards patterns (not versions/auth) from `docs/development-standards/template/frontend-app/`.
- R3: Treating `localStorage` as the source of truth for "already submitted" state is inherently spoofable/tamperable by the end user (see Threat Model, Tampering row); accepted as a demo-scope trade-off since there is no backend/session in this phase.

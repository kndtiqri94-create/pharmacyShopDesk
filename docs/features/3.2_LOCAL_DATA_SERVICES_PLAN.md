## 1. Summary
Add Dexie (IndexedDB) implementations of every abstract data service under `frontend-app/src/app/core/services/data/`, selected by a build flag in `data-providers.ts`; the in-memory services stay for tests and development. Screens do not change (A48). Stock becomes batch quantity plus an ordered ledger of movements, each with a device-generated ID. Every created record gets a device-generated ID. Invoice numbering is made collision-free across devices (decision in 1.1). Frontend-only; no backend work.

### 1.1 Decision — OQ45 invoice numbering (fixed here; flagged for PO review)
Each device gets a persistent short **device code** (3 uppercase base-32 chars, e.g. `K7M`, generated once on first run and stored in the local meta table, with a settings-level override for the owner to set a readable till label e.g. `T1`). New invoice format: `INV-<DEVICE>-<NNNN>` (e.g. `INV-K7M-0001`), NNNN is a per-device sequence that only increases (counter stored in a meta table and incremented in the same transaction as the sale write). Two devices therefore can never issue the same number, with no coordination needed. Existing `INV-NNNN` numbers (seed data and any in-memory build) remain valid; `isInvoiceNumber`/`invoiceSequence` accept both forms. The in-memory service keeps `INV-NNNN` unless the build is local. Held bill numbers `H-NNN` get the same device infix. Reviewer note: this rule is a planning decision per S-3.2.4; Shiham should confirm the format before F-3.3 mirrors it.

## 4. Data Model & Migrations
- Dexie schema v1: one object store per aggregate keyed by `id` (string), indexes on lookup fields only (sku, barcode, invoiceNo, bank+accountNo compound for uniqueness, employeeId, date). `stockMovements` store keyed by device-generated `id` with a monotonically increasing local `seq` index (ordering) plus `batchId`, `productId`, `createdAt`, `type`, `refId`, `qtyDelta` (never a replacement total, AC-10). `meta` store: deviceCode, invoiceCounter, holdCounter, schemaVersion, seededAt.
- Upgrades: each future `db.version(n).stores(...).upgrade(tx => ...)`; test proves v1 data survives a v2 stub upgrade (AC-2).
- Money stored in the same numeric representation the in-memory services use (no new rounding rules).
- No passwords: user records strip any password/hash field on write; unit test asserts none present (AC-7).
- Stock: reads compute `batch.qty + sum(movements)`; single movement written inside the same Dexie transaction as the originating sale/return/GRN/adjustment (atomic, exactly once; retry-safe by unique movement ID).
- Backfill: first-run seed only. Rollback: flag back to `mock`; local DB left untouched.

## 5. API Contract
None. Records are written with device IDs and `createdAt`/`updatedAt`, structured so S-3.4.1 can add an outbox hook (a single `afterWrite(entityType, id, op)` seam in the local write path; no queue built here).

## 6. Threat Model (STRIDE-lite — MANDATORY)
| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing | Y (low) | Anyone with the unlocked device/browser profile can use local data; sign-in is still mock until F-3.5 | Keep existing route guards untouched; no new auth bypass; local services never expose a "skip auth" path; documented residual risk until F-3.5/OQ44 |
| **T**ampering | Y | Users can edit IndexedDB via DevTools; duplicated/invalid writes; double stock deduction | Same validation as in-memory enforced inside local services (not only UI); unique constraints (SKU, bank+accountNo) enforced in transaction; one movement per change in the same transaction with unique ID; stock never stored as a replacement total; server revalidates later (F-3.3) |
| **R**epudiation | Y (low) | Device sales without who/when | Every record keeps existing created-by/at fields; movements carry userId, device code, timestamp; no new audit UI |
| **I**nformation Disclosure | Y | Customer, payroll, bank, sales data now persisted unencrypted in the browser; passwords must not persist; logs | No passwords/hashes/tokens stored (test AC-7); no business data in `console.*` or errors; persistence warning if storage may be cleared; data held only in IndexedDB (never localStorage, never in service-worker caches; ngsw API caching remains off); document that clearing site data / shared PCs need OQ44 |
| **D**enial of Service | Y (low) | Quota exhaustion, huge reads, long transactions blocking UI | Request persistent storage; handle `QuotaExceededError` with a clear user error (no silent loss); index-based queries, no full-table scans on hot paths (POS product lookup); bounded page sizes where existing contract has them |
| **E**levation of Privilege | Y (low) | Role checks bypassed by reading/writing local tables directly | UI/role guards unchanged; local services do not add admin shortcuts; roles table is data only, permission checks continue through existing role service; no `eval`/dynamic code; no role-limited local data (deferred, OQ44) |

### 6.1 Assets & Trust Boundaries
- Sensitive data: customers and dues, employees and payroll, bank account details, sales/cash figures, user/role records.
- Boundary: the browser profile on a possibly shared till PC (IndexedDB is readable by anyone with the profile); no network boundary added in this workstream.

### 6.2 Pre-emptive OWASP mapping
- Likely in play: A01 (broken access control: local bypass), A02 (cryptographic failures: unencrypted PII at rest, accepted risk, documented), A04 (insecure design: invoice collisions, double stock), A08 (data integrity: movement idempotency, upgrades), A09 (logging: no PII in logs). Reviewer still performs a full A01-A10 pass.

## 7. Test Strategy
- Unit/contract: every data service contract suite runs against in-memory AND local (AC-15); duplicate SKU, duplicate bank+account, validation messages, day-locked errors, FEFO, dues, counter close.
- Stock ledger: exactly one movement per sale/return/GRN/adjustment; derived stock correct; two-device simulation sums both sales (AC-10).
- IDs and invoices: uniqueness over N generated IDs; two device codes never collide; legacy `INV-NNNN` still parsed.
- Database: upgrade v1->v2 preserves data; `persist()` granted vs refused shows/hides warning; quota error handled.
- Security negatives: no password fields in stored user rows; no data written to localStorage; invalid/oversized input rejected by the same validators.
- E2E (S-3.2.6): offline sale, reload, restart, stock reduced once, totals unchanged.
- Existing screen specs keep passing unchanged (AC-16).

## 8. Observability
- Console-free; use existing logging abstraction if present (no PII). Events: `local-db.opened`, `local-db.upgrade`, `storage.persist.denied`, `local-db.quota-exceeded` (fields: schemaVersion/error code only).

## 9. Risks & Trade-offs
- R1: Async Dexie vs sync in-memory behaviour differences (e.g. synchronous reads inside signals). Mitigation: contracts already return Observables; contract suites catch drift.
- R2: Dexie transaction scope across Observable chains (auto-commit pitfalls). Mitigation: wrap each write in a single `db.transaction('rw', ...)` using native promises only inside it.
- R3: Invoice format change affects screens/receipts that assume 4 digits (`isInvoiceNumber`). Mitigation: grep all consumers; keep legacy form valid; update only the util and its callers' tests.
- R4: Unencrypted PII at rest and shared PCs (OQ44 open). Accepted for this workstream, flagged for PO.
- R5: Large seeded data on first run slows startup. Mitigation: seed in one bulk transaction once, flagged in meta.
- R6: OQ46 offline scope still proposed; broad scope chosen per story.

## 10. Out of Scope
- Outbox/queue, sync, sync pill (F-3.4); server, auth, hosting (F-3.3/3.5/3.6); screen or rule changes; role-limited local data and offline re-sign-in (OQ44); encryption at rest; conflict merging; real data import; "needs connection" messages.

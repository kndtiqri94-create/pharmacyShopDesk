## 4. Data Model & Migrations
- No database, no migrations. In-memory models only. Dates ISO via `date.util.ts`; days stored as numbers (whole days, shown with two decimals).
- `LeaveRequest` carries a `status`; Utilized = sum of Approved days, Pending Approval = sum of Pending days, per employee + leave type + year. Rejected/Cancelled count in neither. Balance never stored; always computed.
- On leave today is derived (Approved request with fromDate <= today <= toDate). The stored `EmployeeStatus.ON_LEAVE` from F-2.6 is retained for compatibility but no longer drives counts; the seed's existing on-leave employee gets a matching Approved request (AC-8).
- Leave history is kept when an employee becomes Inactive. Data services return deep copies. Everything resets on refresh. Rollback strategy: not applicable.

## 5. API Contract (draft)
No HTTP API. The contract is the leave data services returning `Observable`s plus `LeaveAdminService`. Routes:

| Route | Purpose | Access |
|---|---|---|
| `/employees` (Leave tab) | Request list, approve / reject / cancel | Admin Full, Manager View; others none |
| `/employees/leave/apply` | Leave application page + Leave Balance | Admin Full; Manager View-only redirects to `/employees` |

Approve/reject: Admin, or a person whose sign-in is linked to the chosen approver and who can open Employees; never the applicant. Cancel and Apply: Admin. The session permission matrix decides (editable in Users and roles).

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data, client-side gating is UX only (stated in the story). Controls must be correct so a real backend can enforce the same rules later.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | Acting as another approver; choosing yourself as approver; applying for someone else without rights; forged request id / status through form or URL. | Actor identity read from the signed-in session inside `LeaveAdminService`, never from input. `canDecide` links approver to the real session user via the linked user account; applicant can never decide their own request. Status, days, ids, createdAt and decidedAt are service-set. |
| **T**ampering (integrity) | Y | Crafted dates (31 Feb, reversed, year-spanning), huge or fractional day counts, overlap or over-balance bypass by double submit or stale form, deciding an already decided request, changing a request after approval, shared-reference mutation of seeds, attachment type spoof. | All parsing/bounds in `leave-validation.util.ts`; overlap and balance re-checked against fresh data inside the service; in-flight guard; transition table in `leave-status.util.ts` (terminal states final); copies computed before save; deep copies from data services; attachment checked by MIME + extension + 2 MB; comments length capped. |
| **R**epudiation | Y (low) | No audit trail of who approved, rejected or cancelled. | Request stores approver, approver comment, status and `decidedAt`; deciding actor is not otherwise logged in a session-only frontend. Documented limitation. |
| **I**nformation Disclosure | Y | Leave reasons, medical leave and comments visible to roles without access; PII in notifications; attachment names leaking. | Route guards on all leave routes (Pharmacist / Cashier stopped by URL, AC-47/48); Manager sees requests read-only. Toasts name the employee and outcome only (never reason, comments, attachment name). No `[innerHTML]`, no `bypassSecurityTrust*`, no `console.*`, nothing in `localStorage` / `sessionStorage`. Attachment is never read or uploaded; only a name is kept in memory. |
| **D**enial of Service | Y (low) | Huge comment text, very long date ranges, many requests, rapid clicks, large attachment. | Max lengths; range limited to one leave year; attachment <= 2 MB check before accepting; list paginated 10/25/50; in-flight guard; `takeUntilDestroyed` on subscriptions. |
| **E**levation of Privilege | Y | Manager or Cashier applying, approving or cancelling by direct URL or by invoking handlers; a Manager approving a request not assigned to them; changed role matrix not honoured; approving a past or started request via cancel. | `moduleAccessGuard` + `moduleWriteGuard` (View-only redirected) on `leave/apply`; `PermissionService.canWrite` re-checked inside `apply` and `cancel`; `canDecide` enforced inside `decide`; write controls hidden with `*appCanWrite` / role check; permissions read from the live matrix (AC-50); Approved leave can be cancelled only before it starts. |

## 12. Stabilise flaky F-2.6 spec
- Spec: `frontend-app/src/app/features/modules/employees/employee-form/employee-form.component.spec.ts`, test "sends a read-only user away from the create page".
- Root cause (from reading the code): `EmployeeFormComponent.ngOnInit` redirects a read-only user on `create`/`edit` and returns before `initialize()`, so `loaded()` and `notFound()` never become true. The shared `render()` helper then polls for up to 400 iterations of `setTimeout(5)` waiting for a state that cannot happen. Under headless Chrome timer clamping and machine load that loop can exceed Jasmine's 5000 ms limit, which makes the test intermittently time out.
- Fix: make the helper's wait condition match the real behaviour. In the redirect case wait on a condition that does occur (the `navigate` spy having been called, or the component's own redirect), or give `render()` an option such as `expectRedirect` that skips the load poll; keep the assertion `navigate` toHaveBeenCalledWith(['/employees']). Optionally replace the polling loop with `fixture.whenStable()` plus a bounded check. Do not simply raise the timeout. Add a short comment explaining why the redirect path never loads.
- Acceptance: the spec passes repeatedly (run the employee-form spec file at least 5 times headless) and the full suite is stable.

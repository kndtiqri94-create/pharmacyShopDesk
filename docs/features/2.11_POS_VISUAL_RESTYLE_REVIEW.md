### Blocking Findings

1. **[FE]** `frontend-app/src/app/features/modules/pos/pos-bill-lines/pos-bill-lines.component.scss:1-5` and `shared/components/data-table/data-table.component.scss:21-22` — *Rule violated:* Story AC-14 ("each row is 46px high") and Plan §3.4 ("row height 46px via `--sd-control-lg`"); also Story §3.1 S-2.11.3 ("keeping the compact table feel").
   **Problem:** `td` height is set to 46px (`--sd-table-row-height`) but `--sd-table-cell-padding-y` is `--sd-space-1` (4px top and bottom), the line inputs and the Details/Remove buttons are themselves `min-height: 46px` (52px on coarse pointers), and `td` has a 1px top border. With `box-sizing: border-box`, a table-cell `height` is only a minimum, so the content (46px + 8px padding + 1px border, about 55px; about 61px on touch) pushes each row well above 46px. The Completion Note ("rows are 46px") is therefore inaccurate. The spec added in `pos-bill-lines.component.spec.ts` (`parseFloat(getComputedStyle(cell).height) >= 46`) cannot catch this because it uses `>=`.
   **Required change:** Make the row actually 46px on fine pointers. For example set `--sd-table-cell-padding-y: 0` for the POS bill lines so the 46px controls fill the cell, or drop the control height to fit within 46px minus padding. Tighten the spec to assert the rendered row height (`tr.getBoundingClientRect().height`) is about 46 to 47px on fine pointers (and about 52 to 53px, or an agreed value, on coarse pointers). If the intended meaning of AC-14 is instead "controls are 46px", get Shiham/Sanjeewa to amend AC-14 and the Plan and record the decision, then fix the Completion Note and DoD.2 evidence.

## Iteration 2

### Verdict
**APPROVED**

### Summary
Re-review of iteration 1 finding 1 (row height) plus a fresh security, threat model and DoD pass. `pos-bill-lines.component.scss:1-5` now sets `--sd-table-cell-padding-y: 0` on the host, and the custom property is read by `data-table.component.scss:22` (`padding: var(--sd-table-cell-padding-y, var(--sd-space-3)) var(--sd-space-5)`), so it inherits into the table cells while other screens keep the default. CSS logic by pointer type: fine pointer, controls are `--sd-control-lg` (46px) with zero vertical padding plus the 1px `td` border-top, so the row is about 47px (46px of content and the 1px border; the spec window of 46 to 47.5px matches). Coarse pointer, `.line-input` is `--sd-control-touch` (52px, scss:41-45) and the buttons are `xl` on coarse, so the row is about 53px (spec window 52 to 53.5px). The spec (`pos-bill-lines.component.spec.ts:245-260`) now asserts `tr.getBoundingClientRect().height` with a two-sided bound and branches on `matchMedia('(pointer: coarse)')`. It only exercises the branch of the pointer type in the test browser (fine, in headless CI), so the coarse branch is verified by CSS reasoning, not by execution. This is acceptable: the coarse rule is a plain min-height override with the same zero padding. The 1px border means "46px" is 47px rendered; judged within the intent of AC-14 (compact 46px rows) and documented in DoD.2. No regressions found: other screens do not set the variables, so the data-table defaults are unchanged; no other file changed since iteration 1 in the reviewed scope.

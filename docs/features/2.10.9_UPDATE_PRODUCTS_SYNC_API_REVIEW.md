### Security Findings (OWASP Top 10 2021)
No Critical or High findings.

1. **Severity:** Low — **OWASP:** A04 — **[BE]** `services/data/product-sync-state.store.ts:13`, `utils/product-sync-merge.util.ts:46`
   **Vulnerability:** The operation id is `{matchKey}:{opSeq}` and `opSeq` is session-only. After a page refresh (or on a second terminal) the ids restart at `key:0`. Against a persistent real server, a reused id would replay a stale stored stock result or be refused for a different delta. This is the documented R3 and API-doc open item. It is only a data-integrity risk, not exploitable, and the mock server also resets on refresh.
   **Remediation:** Before binding a real server, persist the baseline or make operation ids unique per original attempt (for example, a durable run or session nonce stored with the baseline).

2. **Severity:** Low — **OWASP:** A07/A09 (user-accepted) — **[BE]** `services/data/product-sync-server.ts`
   **Vulnerability:** The server boundary has no authentication (A42) and there is no log or audit trail (A44). Both are user-accepted for dev only.
   **Remediation:** None now. S-2.10.11 is the release blocker. Add auditing before production.

### Non-blocking Suggestions
1. **Stale-write window.** `applyResponse` (`pos-product-sync.service.ts:186-204`) reads the latest products, then awaits `addedProductsClash` before `saveAll`. With the synchronous in-memory data this is harmless. Once product data becomes asynchronous (HTTP), a sale landing in that gap would be overwritten. Re-read, or run the clash check before reading `latest`, when the real data service arrives.
2. **Partial local save.** `saveAll` followed by per-product `save` (lines 199-202) is not atomic. If a server-only `save` threw after `saveAll`, the app stock would be overwritten while the baseline stays old. The SKU pre-check (`addedProductsClash`) makes this unlikely, and the operation-id guard turns the damage into a refused batch rather than a double-apply. Consider confirming baselines straight after `saveAll`, or saving added products first. The API doc line 117 ("A batch that fails ... saving writes nothing") slightly overstates this.
3. **Unconfirmed-apply wedge (documented).** If the server applied a batch and the app did not confirm it, and the same product's stock changes again, the reused operation id arrives with a different delta and the batch is refused on every re-run (`in-memory-product-sync-server.ts:83-85`). The app has no in-session recovery path. This is accepted and documented in the API doc, but it needs a design before the real server (durable baseline or server-reported applied delta).
4. **First-run semantics.** With no baseline the delta is 0, so stock changes made before the very first sync are replaced by the server stock. This is documented and consistent with "since the last sync". The user should know this before S-2.10.10 exposes the button.
5. **Dead code.** `ProductSyncStateStore.seed` is not called outside specs. Remove it or wire it in.
6. **Product-level pre-validation.** The app does not pre-check name length (200), key length (64) or stock bounds before sending. An over-long product name makes the whole batch fail with a generic message. Consider a product-specific refusal like `SYNC_BAD_KEYS_MESSAGE`.
7. **Plan wording.** The plan lists failure reasons `denied | empty | unreachable | batch-failed | busy`. The code adds `invalid` (documented in the API doc and story). No action needed, but update the plan on the next edit.
8. **Tests not run.** Per project rule the user must run `npm test` and `ng build` before closing. Type-check and lint are clean.

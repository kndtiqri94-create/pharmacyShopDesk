## 1. Summary
Frontend only. Create a new Angular app at `frontend-app/` (repo root) by copying `docs/development-standards/template/frontend-app/` (template is never edited), stripped of Azure AD/MSAL, Graph, Quill, Bootstrap, Toastr and the budget/user sample code. Build, in order: design tokens (light and dark, CSS custom properties, sidebar dark in both), shared presentation components (Icon, Button, Badge, Card, StatCard, Avatar, Alert, DataTable, Pagination, Chips, Tabs, Field plus 12-column form grid, Toggle, Breadcrumb, progress bar), a mock data layer (domain models, abstract service interfaces, in-memory implementations seeded from the design's sample conventions), the AppShell (grouped sidebar, top bar, UI-only sync pill, theme switch, nine lazy-loaded module routes with placeholder pages, not-found page), sign-in with mock session and auth guard, and role/permission gating from one permission matrix (Full / View / No access). Desktop-first at 1280px and wider, responsive below. Hex values are approximate (OQ1) and live only in the tokens file. Ctrl K search is a visual control that shows a "sample only" message (AC-34, OQ8). Non-core buttons show a "sample only" message (OQ4).

## 4. Data Model & Migrations
- No database, no migrations. In-memory domain models only. Money as integer cents or fixed-2-decimal numbers (developer picks one, documented, used everywhere via `money.util.ts`). Dates stored as ISO strings; formatting only in `date.util.ts`.
- Seed (AC-25 to AC-30): products with and without batch tracking, one product each of Out of stock / Low stock / Expiring soon / In stock; batches ordered earliest expiry first; POs in every status with at least one overdue; GRNs in every status and payment state; an owing supplier and an inactive supplier (Lanka Pharma, City Medicals, Health Plus Ltd, MediCare Distributors, Ceylon Surgical); employees (Kamal Silva, Dilani Fernando, Ruwani Jayawardena, Suresh Kumar, Tharindu Silva); one app user per role (Admin shown as "Owner": Nimal Perera, NP); reload transactions in each status and a float above and below Rs. 10,000; settings defaults (expiry alert 60 days, default reorder level, low-float Rs. 10,000, sidebar low-stock count); sync state.
- Session changes persist in memory for the session; reload resets to seed (AC-28). Seed is deep-cloned on construction so tests are isolated.
- Rollback strategy: not applicable.

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, no real credentials, fictional data. Client-side gating is UX only and not real security in this phase; the story states this. The controls below still must be correct so a real backend can later enforce the same rules.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y | Anyone can forge a session by editing browser storage or calling the guard-less route; sample passwords are visible in the bundle. | Session stores only a user id (never password, never a role-bearing token); on load the role is re-derived from the user data service, unknown id means signed out. Sample credentials live in one `mock-credentials.ts` referenced only when `environment.mockAuthEnabled` is true; README and sign-in code state "sample sign-in, not real security". Production environment file must set `mockAuthEnabled: false` and the app then shows a clear "sign-in not configured" state instead of accepting sample logins (reviewer checks `environment.prod.ts`). Failed sign-in uses one generic message and identical timing path for unknown user and wrong password (AC-42). |
| **T**ampering (integrity) | Y | Edited storage changes the role; users change the theme key to inject odd values; in-memory data mutated by shared references. | Role never read from storage. Theme value validated against the enum before applying; invalid falls back to light. Data services return copies, never the seed or internal array references; seed deep-cloned. Permission matrix exposed read-only (readonly signals). |
| **R**epudiation | N | No privileged server action exists; nothing to audit in this phase. | None required. An audit hook for sign-in/sign-out is out of scope until a real backend exists. |
| **I**nformation Disclosure | Y | Password shown or logged; username enumeration; module content visible to a role without access; sensitive text in console; tokens in localStorage. | Password field `type=password` by default, toggle has accessible name, password never logged, never stored, field cleared on failure. Generic failure message (AC-42). `moduleAccessGuard` blocks the lazy route BEFORE loading the module chunk (use `canMatch`/`canActivate` plus lazy `loadChildren`), so content is never rendered or fetched for No access. Sidebar built from `PermissionService` so No-access modules are absent (AC-51). No `console.log` of user or session objects (lint rule). Only the session user id is persisted: `sessionStorage` by default, `localStorage` only when "Keep me signed in" is ticked (AC-47). |
| **D**enial of Service | Y (low) | Large in-memory lists freeze the UI; unbounded failed-sign-in loop; Ctrl K handler spam. | DataTable paginates above 10 rows with a hard page-size cap; seed sizes small and bounded. Failed sign-in attempts get a short client-side delay after 5 consecutive failures (UX only, noted not real protection). Global keyboard listener registered once, removed on destroy. |
| **E**levation of Privilege | Y | Typing a restricted URL; View role seeing write actions; menu and routes disagreeing; matrix change not applied. | `moduleAccessGuard` on every module route reading `PermissionService`; `*appCanWrite` directive and `canWrite` for action visibility (View hides create/edit/delete); one matrix source feeds sidebar, guard and actions (AC-56) with a spec iterating every role x module asserting the three agree. Matrix held in a signal so later matrix edits take effect without re-login (AC-54). Wildcard route goes to not-found, never to an unguarded module. Guard returns a UrlTree to access-denied, never renders the module. |

### 6.1 Assets & Trust Boundaries
- Sensitive data in this feature: sample sign-in credentials, the signed-in person's name and role, session user id. No real PII, financial or health data; all fictional.
- Trust boundary crossings: browser storage (session id, theme) to the app (treated as untrusted input); mock credentials in the shipped bundle (mock builds only). No network boundary.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A01 (broken access control, route and action gating), A02 (credentials in bundle), A04 (insecure design: client-only gating documented), A05 (misconfiguration: prod environment flags, viewport zoom, CSP-friendly output), A07 (identification and authentication failures: enumeration, session handling), A03 (XSS: no `bypassSecurityTrust*`, no `[innerHTML]` with data). Reviewer still does a full A01 to A10 pass.

## 7. Test Strategy
(The user runs `npm test` manually; developers write the specs but do not auto-run the suite, per FRONTEND_STANDARDS.md.)
- Unit tests: `PermissionService` (full matrix, role x module, signal update on matrix change, `firstAllowedPath`), `AuthService` (success, wrong password, unknown user same message, empty fields, sign-out, persistence rules, tampered storage), guards (`authGuard` redirect with return URL, `moduleAccessGuard` per level, sign-in guard), utils (money, date, stock status, FEFO ordering), in-memory data services (seed coverage per AC-27, copies not references, session-only changes, reset on new instance), `ThemePreferenceService` (persist, invalid value fallback).
- Component tests: every shared component (variants, sizes, a11y names, content rules: sentence-case buttons, badge always has text, DataTable right-align and max 3 actions, pagination threshold at 10 vs 11 rows, Field error replaces hint, Tabs max 5), `Sidebar` (groups, count badges, hidden No-access items per role), `SignIn` (AC-40 to AC-45), `AppShell` (collapse behaviour at breakpoints, menu closes on navigation AC-12), `SyncPill` (exactly one state, offline shows pending count), `GlobalSearch` (Ctrl K shows sample-only message, no search).
- Responsive: component specs assert class/attribute toggles for each breakpoint (no pixel screenshot testing in this feature); manual checklist at 1440, 1280, 1024, 768, 360 widths recorded in the DoD.
- Negative tests MUST cover: unauthenticated route access, wrong role route access (each No-access module for each role), invalid input (empty/oversized username and password, over-long values truncated or rejected at a sensible max length, e.g. 100), tampered storage, unknown route.
- Accessibility: keyboard-only walk-through of shell, sign-in, table, tabs, chips, toggle; contrast check of token pairs in both themes (a spec computing ratios from `_tokens.scss` values or a documented tooling run, 4.5:1 text and 3:1 controls/focus).

## 9. Risks & Trade-offs
Decisions flagged for stakeholder review:
- **R1 Breakpoints and smallest width (OQ5; Team Lead's choice, please review):** Desktop >= 1280px (232px sidebar visible, fluid content, form grid 12 columns with 320px summary beside it). Laptop and tablet landscape 1024 to 1279px: sidebar becomes an off-canvas drawer behind a labelled "Menu" button, content full width, form grid 12 columns but summary moves below. Tablet portrait 768 to 1023px: drawer sidebar, form grid reflows to 6 columns, stat cards 2 per row. Mobile below 768px: drawer sidebar, form grid 1 column, stat cards 1 per row, DataTable scrolls sideways with first column sticky (stack mode available per table). Smallest supported width: 360px. Touch targets at least 44px for sidebar items and row actions below 1024px (46px `lg` control and 52px keypad tiles per design). Hex/breakpoint values live in `_tokens.scss` and `_breakpoints.scss`, so changing them is a one-file edit.
- **R2 Authentication standard conflict:** FRONTEND_STANDARDS.md prescribes Azure AD/MSAL and `MsalGuard`. The approved story requires a mock session and a custom guard (FR-AUTH-1, 2). Plan removes MSAL and implements `authGuard` behind an `AuthService` interface so a real provider can replace it later. Code Reviewer should treat the story as the governing requirement for this deviation.
- **R3 i18n conflict:** the standard describes nb-NO/en-GB runtime bundles; the story and PRD say English only. Plan omits ngx-translate and keeps strings in templates (English). If the stakeholder wants translation-ready copy now, adding it later costs a pass over every template; confirm acceptable.
- **R4 UI library:** standard mentions Angular Material theming, but the design forbids stock Material look (custom tokens, no gradients, own focus ring). Plan builds custom components on Angular CDK only where useful (focus trap for the drawer, overlay not needed); `material.module.ts` removed. Confirm acceptable.
- **R5 Test runner:** standards text says Vitest; template ships Karma/Jasmine. Plan keeps whatever the copied template `package.json` pins and does not migrate runners in this feature.
- **R6 Persistence of session:** "Keep me signed in" uses `localStorage` (user id only) versus `sessionStorage` otherwise; theme choice is kept for the session only (AC-4).
- **R7 Contrast of approximate colours (OQ1):** the approximate palette may fail 4.5:1 in dark theme; developer adjusts token values minimally to pass and flags each adjusted value in Completion Notes.
- **R8 Largest-scope risk:** about 50 files of components; developer should build in the order tokens, shared components, mock data, shell, auth, permissions, committing nothing (user commits).

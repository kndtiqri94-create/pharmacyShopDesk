## 1. Summary
Frontend only, inside `frontend-app/`. Extend the in-memory `Employee` model and seed (code, title, first/middle/last name, email, DOB, mobile, location, address, EPF/ETF flags, salary type, basic salary, allowance lines, over time rate, commission %, product and invoice discount %, monthly target, Consider as Customer, Create user account, custom fields 1-4, Status Active/Inactive, photo). Replace the Staff tab table on the Employees page with the Employee list (Keyword / Location / Created at / Status filters with Filter and Reset, columns Image, EMP Code, Name, Address, Mobile, Email, DOB, Location, Status, Action; page size 10/25/50; "Showing a to b of N entries"; Export CSV and Export PDF; primary Add employee). Add a Create / Edit / View employee form (Basic details, Address, Employee Salaries and Allowances, More Information, photo upload with preview) with full validation, unsaved-change confirm, and Admin-write / Manager-read-only / others-blocked access. Delete deactivates instead of removing when the employee has a linked user (payroll history will join in F-2.8). Create user account only reminds and pre-selects the employee in Users. All data is session-only through the F-2.1 abstract in-memory data services. Attendance and Leave tabs and stat cards stay, and must keep agreeing with the list (AC-6, AC-59, AC-60). Design reference (layout and fields only, ShopDesk design system governs, A8): `docs/design/hr-reference/1.png` to `4.png`.

## 4. Data Model & Migrations
- No database, no migrations. In-memory models only. Money in integer cents, formatted only through `money.util.ts` (`Rs. 1,234.00`); dates ISO strings via `date.util.ts`. Percentages stored as numbers 0-100.
- `Employee` additions: `title`, `firstName`, `middleName`, `lastName`, `email`, `dateOfBirth | null`, `location`, address (`addressLine1`, `addressLine2`, `city`, `suburb`, `state`, `country`, `zip`), `calculateEpf`, `calculateEtf`, `salaryType`, `basicSalaryCents`, `allowances: EmployeeAllowance[]`, `overTimeRateCents`, `commissionRate`, `productDiscountRate`, `invoiceDiscountRate`, `monthlyTargetCents`, `considerAsCustomer`, `createUserAccount`, `customField1..4`, `photoDataUrl | null`, `createdAt`. Commission, discounts, target and Consider as Customer are stored only; no other module reads them (AC-5, agreement spec).
- Unique EMP Code across all employees including Inactive, compared case-insensitively. An employee has at most one linked user (`userId`).
- Delete rule: no history gives removal; linked user (or later payroll history) gives status INACTIVE with explanatory message.
- Photo kept as an in-memory data URL for the session only; reset on refresh (AC-7, AC-48).
- Data services return deep copies. Rollback strategy: not applicable.

## 5. API Contract (draft)
No HTTP API. The contract is the abstract data services returning `Observable`s plus `EmployeeAdminService` and `EmployeeExportService`. Routes under the Employees module:

| Route | Purpose | Access |
|---|---|---|
| `/employees` (Staff tab) | Employee list and export | Admin Full, Manager View; Pharmacist / Cashier none |
| `/employees/new` | Create employee | Write access (Admin) else redirect |
| `/employees/:id` | View-only form | View access or better |
| `/employees/:id/edit` | Edit employee | Write access (Admin); View-only users redirected to `/employees/:id` |
| `/users?employeeId=…` | Add user panel with employee preselected | Existing Users access |

Session permission matrix decides (editable in Users and roles, AC-58). Salary and allowance sections: editable with write access, read-only with view access.

## 6. Threat Model (STRIDE-lite — MANDATORY)
Context: no backend, fictional data, client-side gating is UX only (stated in the story). Controls must be correct so a real backend can enforce the same rules later.

| STRIDE | Applies? | Risk in this feature | Mitigation / control |
|---|---|---|---|
| **S**poofing (identity) | Y (low) | Record attributed to the wrong actor; forged `userId` link or `createdAt` through form values or query parameter. | Sign-in inherited from F-2.1. Service sets `id`, `createdAt` and `userId`; they are never read from form input. `employeeId` query parameter on `/users` is validated against `availableEmployees` before it preselects anything. |
| **T**ampering (integrity) | Y | Crafted values (NaN, negative, scientific notation, huge), duplicate EMP Code by case or whitespace, second user link, double-click saving twice, stale form saving over a newer record, unsaved edits applied by accident, shared-reference mutation of seeds, edit by direct URL without write access. | All parsing/bounds in `employee-validation.util.ts`; uniqueness re-checked against freshly read data inside `EmployeeAdminService`; in-flight guard; copies computed before save; draft held only in the form component and written only by Save; deep copies from data services; `canWrite` re-checked in the service; `moduleWriteGuard` on `new` and `:id/edit`. |
| **R**epudiation | Y (low) | No audit trail of employee changes, deletions or deactivations in this phase. | Documented limitation for a session-only frontend. `createdAt` retained. No audit fields invented. |
| **I**nformation Disclosure | Y | Personal data (DOB, mobile, email, address, photo) and pay details (basic salary, allowances, rates, targets) shown to roles without access; pay data leaking into exports or toasts; PII in notifications; exported files kept in memory. | `moduleAccessGuard` on every employee route (Pharmacist / Cashier stopped by URL, AC-44, AC-56). Salary/allowance section read-only without write access, never rendered for no access. Export columns whitelisted to the list columns, no pay fields (AC-53), covered by a spec. Toasts name the employee only (no mobile/email/salary). No `[innerHTML]`, no `bypassSecurityTrust*`, no `console.*`, nothing in `localStorage` / `sessionStorage`. Blob object URLs revoked after download. Photo is previewed via an `img` bound to a data URL created from a validated PNG/JPEG only. |
| **D**enial of Service | Y (low) | Oversized photo, huge text in fields, huge allowance list, very large export, rapid clicks. | Photo <= 2 MB and MIME + extension checked before reading; max lengths on every text input; cap on allowance lines per employee (suggest 20) with message; list paginated 10/25/50; export is built only from the in-memory filtered rows; button in-flight guard; `takeUntilDestroyed` on subscriptions. |
| **E**levation of Privilege | Y | Manager editing or deleting via direct URL or hand-called handler; Pharmacist/Cashier reaching form; non-image file smuggled as photo; CSV formula injection executing in Excel on the recipient's machine (privilege via spreadsheet); changed role matrix not honoured. | `moduleAccessGuard` + `moduleWriteGuard` on routes; `PermissionService.canWrite` re-checked inside `EmployeeAdminService` (create, update, remove) and write controls hidden with `*appCanWrite`; permissions read from the live matrix so Users and roles edits apply in-session (AC-58). CSV cells starting with `=`, `+`, `-`, `@`, tab or CR are neutralised. File type validated by MIME and extension. |

### 6.1 Assets & Trust Boundaries
- Sensitive data: employees' personal details (names, DOB, mobile, email, address, photo) and pay details (basic salary, allowances, over time, EPF/ETF, commission, discounts, targets). All fictional.
- Trust boundaries: URL (route params, query params), every form input, the selected image file are untrusted. The exported file leaves the app to the user's device (CSV injection boundary). No browser storage used.

### 6.2 Pre-emptive OWASP mapping
- Likely-in-play: A01 (route and action gating, direct-URL edit, Manager read-only), A03 (injection: CSV formula injection, XSS via names/addresses/custom fields rendered only by interpolation, file type), A04 (insecure design: client-only gating documented, duplicate code race, delete without history loss), A05 (no debug output), A08 (data integrity: server-set fields), A09 (limited audit, documented). Reviewer still does a full A01 to A10 pass.

## 9. Risks & Trade-offs
- R1 **Status model:** story says Active/Inactive, the existing enum is ACTIVE/ON_LEAVE and feeds the Leave tab. Plan: add INACTIVE, keep ON_LEAVE for F-2.7. Form offers Active/Inactive only; a seeded On leave employee keeps its word "On leave" in the list, and the Status filter matches Active/Inactive literally (On leave rows show only under All). Flagged for user awareness.
- R2 **Legacy fields:** `name`, `phone`, `jobTitle`, `shift`, `employmentType` are consumed by Attendance, Leave, stat cards and Users. They are kept; `name` is derived by the service and `phone` is the mobile. New fields do not duplicate them. Job title, shift and employment type are not editable on the new form (not in the story), so new employees get neutral defaults. Flagged.
- R3 **Form placement:** story says "opened over the list" but AC-57 requires direct links. Plan: dedicated child routes (`new`, `:id`, `:id/edit`) with Cancel returning to the list, instead of a side panel. Flagged as a decision to confirm.
- R4 **PDF without a library:** no PDF dependency exists. A small in-house text-table PDF builder keeps dependencies and the license log untouched; layout is plain. If it proves unreliable, fall back to the "sample only" message (OQ10, AC-52). No dependency may be added without Team Lead approval.
- R5 **CSV injection:** exported names/addresses come from user input; neutralised per section 6.
- R6 **Create user account flag vs Users:** flag only reminds and preselects; "Can log in" stays derived from real users (assumption in story).
- R7 **Client-only gating** documented limitation in the story.
- R8 **Payroll history unknown until F-2.8:** `employee-history.util` returns linked-user only; F-2.8 extends it.

## 10. Out of Scope
- Leave management (F-2.7) and Payroll (F-2.8); real effects of commission, discounts, target, Consider as Customer; creating a real user account; real image storage; extra locations; bulk import/delete; restoring a removed employee; real EPF/ETF/tax rates; exact colours (OQ1), numeric performance targets (OQ6), smallest width (OQ5); other languages; changes to Attendance tab behaviour beyond reading the new data.
